# Dictation Fixes — inspection 1

**Verdict: FAIL. Five findings.** Inspected `origin/main...45f40c1dc` against the mission brief and devthrottle issues #2925–#2929; also inspected `mission/dictation-fixes-docs` against internal issue #2038. I did not use the builders' report as evidence.

## Findings

1. **High — the ready cue's last samples can still reach transcription.** `src/CcDirector.Avalonia/Voice/BatchDictationRecorder.cs:273` computes the blanking end as the number of bytes *already delivered to the recorder* when playback finishes, plus 50 ms. `MicAudioCapture` delivers 50 ms buffers, so the capture callback can be one buffer behind the sound currently reaching the microphone. In that ordinary interleaving, playback ends after 200 ms but only 150 ms have reached `_audio`; the computed end is 200 ms, leaving the required 200–250 ms ring-down audible in both `TranscribeAsync` and background Send's `StopAndGetWavAsync`. If the callback is more than one buffer late, even cue samples survive. The tests in `BatchDictationRecorderReadyCueTests.cs:58` and `:88` emit all 200 ms before invoking the playback-finished callback, so they cannot detect this. The boundary needs to account for capture delivery lag using a clock/position relationship, and a test must hold the last capture buffer until after playback finishes.

2. **Medium — microphone device queries still run on the interface thread.** `src/CcDirector.Avalonia/Voice/SpeakDialog.axaml.cs:339-350` constructs and starts `BatchDictationRecorder` on the UI continuation after resolving the saved device. The production `MicAudioCapture` constructor calls `MicDevices.DescribeDevice` at `src/CcDirector.Avalonia/Voice/MicAudioCapture.cs:175`; for the Windows default this invokes `MMDeviceEnumerator`, and for a concrete device it calls `WaveInEvent.GetCapabilities`. `SpeakDialog.axaml.cs:471` also calls `DescribeDevice` during a microphone switch on the UI thread. This leaves precisely the device query identified in #2929 on the thread that renders GETTING READY, so slow endpoints can still freeze the dialog. `SpeakDialogMicEnumerationOffUiThreadTests` supplies a fake recorder and never executes this production constructor.

3. **Medium — a start that delivers no audio has no per-start diagnostic.** `src/CcDirector.Avalonia/Voice/BatchDictationRecorder.cs:456-459` calls `LogFirstAudio` only from the first nonempty capture callback. On the documented slow/failed-microphone path where no callback arrives, `SpeakDialog.axaml.cs:669-675` logs only a generic timeout without device name or the click/start timings. Thus #2928's “log line exists for every start” fails for the starts most in need of diagnosis. The test `MicStartTimesTests.Recorder_StartToFirstAudio_IsMeasuredWhenTheFirstAudioArrives` exercises only the successful callback path.

4. **Medium — the new web stop tail opens an unhandled inactive-recorder path.** `packages/client-core/src/dictation/recorder.ts:391-409` waits 250 ms, checks only whether `this.recorder` is the same object, then calls `rec.stop()` even if the browser has already changed `rec.state` to `inactive` because the input track ended during that wait. The browser's `stop` event can already have fired before `onstop` is attached; `MediaRecorder.stop()` then throws `InvalidStateError`, and Send/Pause loses the captured clip rather than returning its delivered chunks. The test fake's `stop()` accepts the inactive state, so `recorder.test.ts` does not cover browser behavior at this boundary.

5. **Medium — the internal research still directly calls the cue the owner's speech.** On `mission/dictation-fixes-docs`, `docs/research/transcription/2026-09-09-unspoken-words.md:220-223` still states that the detector-only rule “deletes 14 of the owner's real `Yeah.`s” and that the detector “misses short words.” The following correction explicitly says both are false, but the operative section still presents the false causal claim as fact. Section 7 similarly retains “the owner's real leading interjections” at line 156. Internal #2038's Done-when says no sentence still claims these openings were the owner's speech. The correction needs to replace the false assertions in the main text, with the old interpretation described only as historical context.
