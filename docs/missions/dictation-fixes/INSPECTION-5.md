## Findings

1. **High - a dropped capture buffer makes cue blanking erase the owner's first word.** `src/CcDirector.Avalonia/Voice/BatchDictationRecorder.cs:343-351,567-577` converts the cue's wall-clock end into a position in the *concatenation of delivered buffers*, assuming that byte count advances at the device's byte rate with no missing samples. The production capture explicitly allows a driver or redirection layer to drop incoming audio when buffers run out (`src/CcDirector.Avalonia/Voice/MicAudioCapture.cs:193-199`), and `:271-292` forwards only the bytes actually delivered, without inserting silence for a gap. The arrival-time estimate can still be an upper bound for the first buffer's fill time, but that no longer makes the calculated byte boundary an upper bound on cue audio in this shortened WAV.

   A concrete timeline uses only 50 ms buffers, all delivered no earlier than filled: first buffer `[0,50)` arrives at 50 ms and starts the cue; `[50,100)` arrives at 100 ms; `[100,150)` is dropped; `[150,200)`, `[200,250)` and `[250,300)` arrive at their fill times; the playback end is reported at 250 ms and the 50 ms ring-down ends at 300 ms. The first word starts at wall time 300 ms, but at **PCM position 250 ms** because the missing buffer was omitted. `CueEndByte` computes **PCM position 300 ms** (`C0=50 + (T1-F0)=200 + ring-down=50`), so it zeros the first 50 ms of that word. A temporary test through the production recorder's fake-microphone seam reproduced this: the assertion for the first word byte failed, expected `0x33`, actual `0x00` (1 failed, 0 passed); the temporary test was removed after the run. The committed ready-cue tests use contiguous 50 ms buffers, including their backlog and late-callback cases, so all remain green. A short buffer is safe if its samples are contiguous; a short buffer that represents missing capture has the same failure. This breaks #2925's requirement that samples after the cue remain untouched and the mission's reason to stop losing words.

2. **High - the production playback callback includes a silent output-buffer tail and can erase speech.** `src/CcDirector.Avalonia/Voice/DesktopAudioCue.cs:62-85,111-121` plays a 200 ms cue through NAudio 2.2.1 `WaveOutEvent`, then calls the recorder only from `PlaybackStopped`; `src/CcDirector.Avalonia/Voice/BatchDictationRecorder.cs:323,349-351` treats that callback's wall time as the end of the *audible cue* and adds another 50 ms of ring-down. In the installed NAudio version, `WaveOutEvent` defaults to 300 ms of output buffering in two 150 ms buffers ([source](https://github.com/naudio/NAudio/blob/v2.2.1/NAudio.WinMM/WaveOutEvent.cs)); `WaveOutBuffer.OnDone` fills the unread 100 ms of the cue's second buffer with zeros and still writes the whole buffer to the device ([source](https://github.com/naudio/NAudio/blob/v2.2.1/NAudio.WinMM/WaveOutBuffer.cs)). `PlaybackStopped` follows that buffer's completion. Thus the callback can be about **100 ms after the audible 200 ms cue**, even with prompt thread scheduling. J1 then blanks to about 350 ms from cue start, erasing the first **100 ms of speech** that begins just after the cue's 50 ms ring-down. A further playback-thread delay can erase more.

   The existing Send-before-report test at `src/CcDirector.Avalonia.Tests/BatchDictationRecorderReadyCueTests.cs:372-415,433-444` illustrates the failure rather than guarding it: its audio contains `Words` from 300 to 450 ms, but it delays the report until after the stop tail; the fake clock has reached 450 ms and `MoveToAtLeastMs(250)` cannot move it back. The test asserts that **every byte of those words is zero** and passes. The normal ready-cue tests instead report the end at exactly 200 ms after cue start, so they do not model the production buffer completion. This violates #2925's after-cue preservation and can make a short Send return no words.

## J1 and prior findings rechecked

- With contiguous PCM at the configured byte rate, the J1 estimate is a mathematical upper bound on the first buffer's fill time: every arrival is no earlier than that buffer's fill, so the minimum of `a_k - (C_k-C_0)/byteRate` cannot precede the real `F0`. The first buffer need not be full-size for this to hold. The code computes it at snapshot time, uses `TimeProvider.System` in the production constructor, and injects a clock in the tests. In that continuous model, nearest-byte rounding of the two time spans followed by rounding the final boundary up to a whole PCM16 sample does not push it an additional whole sample into speech. Finding 1 uses exact multiples of a sample, so it is independent of rounding. The ten-second arrival window is applied from the first arrival; a prompt buffer after that window is excluded. If every observed buffer is late, the documented residual cue remains; a short recording also has fewer chances to observe a prompt buffer.
- The first callback's 0, 50, 100 and 150 ms delay cases, capture backlogs at playback end, and both `TranscribeAsync` and background `StopAndGetWavAsync` are exercised with physically ordered, contiguous buffers. Send before the playback-end report waits through the 250 ms stop tail and drain for the report, bounded by the cue allowance; finding 2 shows that a late report can erase the words. An unreported end blanks nothing as ruled. Pause transcribes and disposes its recorder, and Resume builds a fresh recorder and cue. The dialog test still emits its first 50 ms buffer at clock time zero, earlier than it could fill, but the phase 5 recorder tests correct that timing; none models a capture gap.
- Whole-diff review found no additional defect in #2926's service storage of model `Raw` versus gated `Delivered`, #2927's desktop and web stop tails, or #2928-#2929's start-time logging, selector updates, and background device queries. The internal branch changes only the two requested documents, corrects the operative claims about the fourteen cue openings, and leaves `labels-final.json` unchanged.
