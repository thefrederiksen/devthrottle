# Inspection 6 — slice 3, replies without blocking

**FAIL for merge** at `80adce1ed75851928b48e963196c0e3e76aa0a73` (diff `e59622d1...80adce1e -- src tools packages`). Two reply paths can silently lose the answer or its required notice. I inspected the exact detached head and did not change product code.

## Findings, ranked

1. **High — an overdue mark can commit without the no-reply notice, permanently suppressing it.** `src/CcDirector.Gateway/Messaging/FleetMessageStore.cs:388-402` sets `ReplyOverdueAtUtc` before `StageSystemNotice` and saves the mark regardless of that function's return. `StageSystemNotice` returns null when the policy refuses a notice (`:410-427`), including a notice over `MaxTextLength` (`FleetMessagePolicy.cs:167-172`), or when an identical notice is already unread (`FleetMessageStore.cs:254-258`, `FleetMessagePolicy.cs:198-199`). The next scan excludes the marked question at `FleetMessageStore.cs:389-390`; the sender never receives the required notice. The test at `FleetMessageReplyStoreTests.cs:462-479` proves rollback when the save throws, but never makes the *policy* refuse the notice. **Prove:** send a question with the normal limits, advance past its deadline, then call `MarkReplyOverdueWithNotices` with a small `MaxTextLength` so its notice draft is refused. Assert the returned tuple has `Notice == null`, the question has a non-null overdue mark, there is no system row, and a second scan returns no question. This is the same policy-refusal gap as the stuck notice path; a single `SaveChanges` is atomic only over the changes actually staged. It violates brief ruling 10's required notice.

2. **High — the duplicate rule can drop a reply to a distinct question and later falsely report no reply.** `FleetMessageStore.cs:273-278` defines an unread duplicate by recipient, sender and text hash alone; it does not include `InReplyToMessageId`. `FleetMessagePolicy.cs:244-249` drops that duplicate before checking the answered mark, and `FleetMessageStore.cs:216-221` stamps `RepliedAtUtc` only for a queued reply. Thus an unread ordinary message, or a reply to question A, with text `yes` causes a `yes` reply to question B to be dropped. The waiting row answers A or no question at all; B remains unanswered and the overdue scan (`FleetMessageStore.cs:388-402`) later tells its asker no reply arrived. The current duplicate test (`FleetMessageReplyStoreTests.cs:291-302`) repeats the *same* question and misses this case. **Prove:** ask two different questions of the same worker (ten minutes apart), reply `yes` to A without reading the asker's inbox, then reply `yes` to B. The second call returns `duplicate`; B's `RepliedAtUtc` stays null and the only reply row points to A. Advance B's deadline and observe its no-reply notice. This conflicts with ruling 10's answer to the question that was asked.

3. **Medium — asking for a reply can be silently reduced to a plain duplicate.** The same hash lookup (`FleetMessageStore.cs:273-278`) ignores whether the waiting row asked for a reply. On a duplicate send, `FleetMessageService.cs:125-132` returns the waiting row's correlation id, which is null for a plain message; `tools/cc-devthrottle/src/session_ops.py:1578-1595` then prints no correlation line. The handoff acknowledges this as judgement call 8, but `--reply-wanted` has produced neither a reply right nor a refusal explaining that it did not. **Prove:** send an ordinary message, leave it unread, and send the same text with `--reply-wanted` after spacing has elapsed. The answer is a successful duplicate with no correlation id, and the recipient has no question to answer. Ruling 3 requires dropping exact duplicates; ruling 10 requires the reply request to give the record a correlation id. This interaction needs an explicit decision or handling before merge.

## What I checked and found sound

- **Reply permission and destination.** `GatewayEndpoints.cs:3300-3319` gets the replier from the authenticated session key and takes no sender or destination from the body. `FleetMessageStore.cs:188-215` trims and lowercases the supplied message or correlation id, searches only original rows in the bound tenant, and derives the destination from the original sender. `FleetMessagePolicy.cs:227-252` compares session ids without case or surrounding whitespace, refuses everyone except the original recipient, refuses a Gateway notice, and allows only one queued reply. A reply's own id and a no-reply notice's id cannot become a question because they have `InReplyToMessageId` (`FleetMessageStore.cs:195-204`). Broadcast copies carry no reply request (`GatewayEndpoints.cs:3322-3330`). An authenticated session key whose session is missing from the roster **can** reply if its id is the original recipient: `ResolveSenderAsync` may return a null row (`GatewayEndpoints.cs:3176-3182`), `PartyFrom` still uses the authenticated id (`:3187-3194`), and the reply route does not reject a null roster row (`:3307-3317`). An exited asker also need not remain on the roster: the stored sender id is used as the destination (`FleetMessageStore.cs:206-210`). These last two behaviours follow the stored-record delivery model; whether a key remains authenticated after exit is outside this slice's proof. A reply cannot choose a different recipient (`FleetMessagePolicy.cs:239-242`). The route test checks a lost relationship, not an absent asker roster row (`FleetMessageRouteTests.cs:561-577`).

- **Exemptions.** `FleetMessagePolicy.cs:227-252` does not apply hourly or spacing checks to replies; `FleetMessageStore.cs:265-270` excludes replies from later hourly and spacing histories. The store test queues seven replies within one minute and then an ordinary message (`FleetMessageReplyStoreTests.cs:304-335`), using direct store inserts to supply seven questions. One reply per distinct question prevents one id being reused, and the ordinary send policy refuses a session messaging itself (`FleetMessagePolicy.cs:187-188`), so the worker cannot ask itself to mint reply rights. There is **no absolute per-hour cap** on replies from a worker to its supervisor: it can answer any backlog of eligible questions in that hour. For new questions addressed by that supervisor to that worker, the supervisor's ordinary limit is six per rolling hour and ten-minute spacing (`FleetMessageLimits.cs:16-23`, `FleetMessagePolicy.cs:201-221`), so up to six new reply rights can be minted in an hour; older unanswered questions add to that number.

- **Overdue behaviour apart from finding 1.** The scan requires a deadline, correlation id, no reply, and no prior mark (`FleetMessageStore.cs:388-390`), runs under the store lock and saves staged rows once (`:385-403`). A failed save persists neither mark nor notice (`FleetMessageReplyStoreTests.cs:462-479`). A successful notice is queued once (`:340-373`); an answered question is not marked (`:394-406`); a late reply is still queued and marked late, with no second no-reply notice (`:432-458`). The heartbeat runs the overdue scan before reading unread messages for ringing (`FleetDoorbell.cs:222-234`).

- **Tenant, lock, migrations.** Each new store query uses `_db.CreateContext(tenant)` and the entity has a tenant filter (`FleetMessageStore.cs:194,387,362-365`; `GatewayDbContext.cs:1258,1412-1424`). The reply lookup, reply write, overdue scan and notice staging are under `_gate`; the question join on inbox read is inside its locked section (`FleetMessageStore.cs:331-365`). The SQLite and PostgreSQL migrations add the two nullable marks and `(tenant_id, ReplyByUtc)` index (`Data/Migrations/20260917094429_AddFleetMessageReplyMarks.cs:12-29`; `Migrations.Postgres/Migrations/20260917094441_AddFleetMessageReplyMarks.cs:12-32`). Both model snapshots contain both marks and the index. SQLite was exercised; I did not apply the PostgreSQL migration or run these queries on PostgreSQL.

- **Command line and privacy.** `message reply` sends the trimmed id and full text, including newlines, to `fleet/reply`; queued and duplicate answers exit 0, refusals and unconfirmed queued responses exit 1, and blank arguments are usage errors (`session_ops.py:1766-1812`). The new help and error tests check standard error and next steps (`test_message_queue.py:493-525`; `test_help_and_errors_axi.py`). Inbox text is split by newline and escaped for readable non-ASCII output (`session_ops.py:1823-1889`); the route and unit tests pin the answer hint, reply and notice wire fields. The question join requires `SenderSessionId == reader` (`FleetMessageStore.cs:357-365`); the direct-row test proves another reader receives no question text (`FleetMessageReplyStoreTests.cs:522-541`). The pinned action fixture has 87 actions and exactly matches the real `actions --json` output after the test's ten declared later additions are excluded (`test_axi_step_6c_help_and_errors.py:328-354`; independently regenerated: real 97, filtered 87, fixture 87, identical).

- **Pinning limits.** The tests pin the default/minimum/maximum reply windows, `reply` kind, `no-reply` notice value, command line action command, and several wire field names and rendered sentences (`FleetMessageReplyPolicyTests.cs:46-54`; `FleetMessageReplyStoreTests.cs:368-372,383-391`; `FleetMessageRouteTests.cs:519-543`; `test_message_queue.py:608-628`). They do **not** pin every word: the unknown-id suffix and no-reply-wanted refusal are checked by prefix or substring (`FleetMessageReplyStoreTests.cs:235-259`), and CLI success/refusal output tests check fragments (`test_message_queue.py:493-525`). The notice's roster-name variant is pinned for one short name only; changing text or wire strings outside the asserted fragments, or a future long-name policy refusal, can leave these suites green. No other contradiction to brief rulings 1, 3, 9, 10 and 11 was found within this slice.
