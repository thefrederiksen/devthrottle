Mission brief, draft for the owner

Message Load: fewer messages, and none that interrupt

What the mission is for, what I intend to build, and the five questions only you can answer.

Architect session 120 (8fdb130e) on devthrottle-mac-mini. Written 16 September 2026. Branch mission/message-load, worktree ~/ReposFred/devthrottle-message-load, cut from origin/main at 66609c3c. No messages sent, nothing committed, no product code changed.

1. The mission, in one paragraph

Sessions send each other too many messages, and every one of them lands in the middle of the receiving session's work. You said so this morning:

"You have been sending out messages and you really need to stop doing that. ... It needs to be much harder to do this. Messages interrupt what we do and it's really detrimental to the other sessions. ... reduce messaging and probably also implement the queue ... like Kun's firstmate does."

When this mission is finished: a session can message only the sessions it is responsible for, and only a few times an hour. A message never lands mid-work. It waits in a queue and reaches the session at a safe moment, and you can see, on every screen, that it is waiting. The Fleet Manager mission will use this same queue to instruct its sessions, so this is the one channel, not one of two.

2. What happens today, and why it hurts

There is no queue anywhere. When a session runs cc-devthrottle message send, the Gateway types the text straight into the other session's terminal and presses Enter, whatever that session is doing. It checks only that the session has not exited.

The receiving agent is redirected mid-task. Claude Code does not drop text typed while it is working. It holds it and hands it to the model the moment the current tool calls finish, inside the same turn. So the message arrives in the middle of whatever the session was doing and changes its course.

Nobody knows what it does to your unsent text. Open issue 2845: a 19-session fleet stalled for most of a day because a supervisor refused to message sessions that held your unsent approvals.

Messages are one line. Newlines are collapsed. Long messages sit half-typed in the composer and are never sent (the Tutorials mission deadlock of 4 August).

No record. The Gateway keeps no message. A log line and a count are all that exists. Nobody can say afterwards who sent what to whom.

Every session is told to do it. The preamble every session reads at start-up teaches message send and message ask as ordinary tools. The fleet-comms skill says "message those sessions freely".

One rule is already on the books that this mission reverses: on 13 September you ruled that a worker's session report interrupts its supervisor deliberately, because "a signal nobody is obliged to read is a signal that does not exist". The design below keeps that principle. Delivery is automatic, so nobody has to remember to look. It just happens at a safe moment instead of mid-work.

3. What I want to build

Six pieces. Each is small, and each is listed with why it exists. The design copies firstmate where firstmate has already solved the problem, and the one thing this product already does right: a snooze asked for while a session is working waits until the work ends before it lands. The queue uses the same idea.

1 A durable inbox on the Gateway

Every message becomes a record: sender, recipient, text, when it was sent, when it was read. Multi-line text is allowed. The record survives a Director restart and a Gateway restart. The send succeeds when the record is written, not when text reaches a terminal. This is also the audit trail that does not exist today.

2 A doorbell, not the message

The Director types only one short fixed line into the session: "2 messages waiting. Run cc-devthrottle message inbox." The session reads the full text from its inbox. A fixed line cannot be cut at a newline, cannot sit half-typed, and a duplicate does no harm. Nothing is typed into a dead terminal.

3 The Director decides when it is safe

The doorbell is rung only when the session is not working and its composer is empty. The Director decides this, not the Gateway, because the Director can see the terminal. Today's "turn ended" signal is still unreliable (one in six blue flips is a repaint, issue 2853), and the Director is the only place that can check the screen before typing. If your unsent text is in the composer, the doorbell waits.

4 Read means read, and unread gets chased

A message is open until the recipient runs the inbox command. If it stays unread, the Director rings again once per grace period, while the session is idle and the composer is empty. After three unanswered rings the message is marked stuck: the session's row says so, and the sender is told. This catches "delivered but never seen", which today fails silently.

5 Replies without waiting

message ask, which blocks the sender for up to two minutes and returns a scrape of the other session's screen, is removed for agents. In its place, a message can ask for a reply. The reply arrives in the sender's own inbox, and if none comes by the deadline the sender is told. The sender never sits blocked.

6 Much harder to send

The Gateway refuses a message unless the recipient is the session that started the sender, or a session the sender started. Hard rate limits on top. Exact duplicates are dropped. Over the limit, the refusal says "put it in your report". The preamble and the fleet-comms skill are rewritten to say: messages are rare, they queue, and most sessions cannot send one at all. Only you can interrupt a session, from your own screens.

How a message travels afterwards

Send A Manager runs cc-devthrottle message send <worker> "...". The Gateway checks the Manager started that worker and the Manager is under its hourly limit. It writes the record and answers "queued".
Wait The worker is mid-build. Nothing is typed. The worker's row on the Director, Cockpit and phone says "1 message waiting".
Ring The worker finishes its turn and its composer is empty. The Director types the one-line doorbell.
Read The worker runs cc-devthrottle message inbox, gets the full text, and the record is marked read. The row line clears.
Chase If the worker never reads it, the Director rings again after the grace period, then again, then marks it stuck and tells the Manager.

What stays out of this mission

  • Outcomes reported by scripts instead of the model ("a pull request opened", "a session died"). They will ride on this queue, in a later mission.
  • Any new screen. Visibility is one line on the session row, on the Director, Cockpit and phone.
  • Fixing turn detection. The mission works around it by checking the screen; the turn-detection mission fixes the signal itself.
  • The whole-fleet broadcast grant machinery from issue 1229. It stays as it is.

4. Questions for you

My recommendation is first on each. "All recommended" is a complete answer.

1. Who may send

Recommended The strict form, as firstmate does it: a session may message only the session that started it and the sessions it started. No Mission-wide sends. send all only from a supervisor to its own workers. A session nobody started can message nobody. If you want one session to tell another something, you say it in that session yourself.

Alternative Also allow sessions in the same Mission to message each other, rate-limited.

2. Does any agent ever interrupt

Recommended No. Never, not even with a grant. Only you interrupt, from your own screens. This reverses the 13 September ruling that a worker's report interrupts deliberately. Reports go through the queue too.

Alternative Keep one urgent path that needs a human grant, like the whole-fleet broadcast today.

3. How rare

Recommended Six messages per hour per sender. One per recipient per ten minutes. Exact duplicates dropped. Grace period before a second ring: five minutes. Stuck after three rings.

Alternative Give me different numbers. They are constants and can be changed later without redesign.

4. Scope

Recommended Exactly the six pieces in section 3, plus the rewritten preamble and skill, plus the one line on the session row. Nothing more.

Alternative Add the script-reported outcomes now, or add an inbox screen on the Cockpit.

5. A baseline number

The hosted Gateway's activity events table can count messages per recipient per day for the last 30 days. It would let the report say "from N a day to M". Can a worker query that database, or should I skip the measurement?
