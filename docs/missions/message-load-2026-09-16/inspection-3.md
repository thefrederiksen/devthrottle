## Findings, ranked

### Low: concurrent recent reads can make count and page disagree

`src/CcDirector.Gateway/Messaging/FleetMessageStore.cs:197-205,217` runs `Count()` and the ordered `Take(200)` as separate queries before the store lock. If another read marks 201 rows read between them, the count can be zero while the page contains 200; `Math.Max` then reports total 200 and `truncated=false` although another row qualifies. A concurrent purge can produce the opposite discrepancy. This is a metadata race, not a path to mark an unread row twice or leave it unread: unread rows are selected and marked under the lock at `:208-216`. **Prove it:** pause the first reader after `Count()`, mark 201 rows read through a second reader, then release the first page query and inspect `recentTotal` and `truncated`. The current SQLite tests do not cover this interleaving. It does not remove the 200-row resource bound or breach the stated count-before-page design ruling.

### Accepted limit: acknowledgement precedes response delivery

`src/CcDirector.Gateway/Messaging/FleetMessageStore.cs:171-176,211-216` saves `ReadAtUtc` before the caller builds or sends the response. A dropped response leaves the plain inbox empty; `--all` can recover at most the newest 200 reads within 24 hours, if the recipient asks. This is the interval explicitly accepted in inspection-2 ruling 2 and is stated in command help at `tools/cc-devthrottle/src/cli.py:1760-1763`. **Prove it:** drop the response after `SaveChanges`, retry normally and with `--all`, then advance beyond 24 hours. This inspection did not inject an HTTP failure.
