# Slice 1 inspection 2

**Verdict: FAIL for merge.** The two high severity boundaries from inspection 1 hold on this tree, but the new unbounded `--all` read can make an authenticated session repeatedly load, track, serialize and return a large 24-hour inbox on the shared Gateway. The fix round also leaves the read-before-response loss interval; its agreed 24-hour recovery is useful but conditional. An empty broadcast still reports success without a queued or waiting message.

## Findings, ranked by severity

### Medium: an unbounded `--all` read can exhaust shared Gateway resources

`src/CcDirector.Gateway/Messaging/FleetMessageStore.cs:174-180` materializes **every** read row in the last 24 hours with `ToList()`, without a row or byte bound. `:171-189` holds the store lock while loading it and tracking those entities; `FleetMessageService.cs:123-130` then makes another DTO list, and `GatewayEndpoints.cs:3361-3372` serializes the response. The index at `GatewayDbContext.cs:789` helps find rows but does not bound result size. The text limit is 16,000 characters per record (`FleetMessageLimits.cs:40-42`). The six-per-hour limit applies per sender (`FleetMessagePolicy.cs:166-173`), so many workers can fill one supervisor's inbox; `--all` can be repeated while the same rows remain inside the read window. This is an authenticated, same-tenant denial-of-service path, not a cross-tenant read.

**Prove it:** Fill one session's inbox from many workers with large distinct messages, read it, then repeatedly request `GET /fleet/inbox?all=true` with that session key. Measure Gateway allocation, request time and concurrent inbox latency as the 24-hour row count grows. The existing 30-row test (`FleetMessageStoreTests`) proves recovery past the old cap, not a safe upper bound. A live load test was not run here.

### Medium: read acknowledgement can still precede delivery of the text

Inspection-1 finding 3 is **partially closed under the Architect's 24-hour ruling**, not eliminated. `FleetMessageStore.cs:182-188` commits `ReadAtUtc` before `FleetMessageService.cs:123-131` builds the response and before HTTP serialization. A dropped response makes the ordinary next read omit the message. `--all` can recover it for 24 hours measured from `ReadAtUtc` (`FleetMessageStore.cs:169-179`), if the recipient knows to ask and can complete that read. After 24 hours it is outside the recovery query. This is the protocol's remaining loss interval, disclosed here rather than counted as a new violation of the accepted ruling.

**Prove it:** Abort the request after `SaveChanges` and before the client receives the body. Retry without `all`, then with it; advance the clock beyond 24 hours and retry with it again. The store tests cover the time boundary in SQLite, not a failed HTTP response.

### Low: the Gateway's `none` spelling is not pinned across the client contract

`SpawnOrigin.cs:44,111-117` uses `SpawnOrigin.UserOwned` to recognize a standalone spawn. `SpawnOriginTests.cs:90-97,159-164` supply that same constant, while the command line independently sends the literal `"none"` (`tools/cc-devthrottle/src/session_ops.py:1573-1582`, pinned in `test_spawn_ops.py:134,143,212`). Changing only the Gateway constant to another literal would leave both suites green separately but make the command line's `--standalone` request return 400 at `SpawnOrigin.cs:120-133`. The current spelling is correct; this is a regression-test gap in a cross-component contract.

**Prove it:** Change only `UserOwned` to another word, build and run the touched Gateway tests plus command line tests; both sides' tests follow their own value. This inspection did not edit product code.

### Low: an empty broadcast still exits successfully with nothing queued or waiting

`tools/cc-devthrottle/src/session_ops.py:1262-1264` returns before the queued/duplicate exit rule at `:1279-1280` when `results` is empty. The new help sentence at `cli.py:1750` says exit 1 when nothing was queued and nothing was waiting. The all-duplicate case is now consistent, but inspection-1 finding 5 remains open for an empty recipient set.

**Prove it:** Return `{"results":[]}` for `message send all` and inspect the exit code; it is 0. `test_message_queue.py:160-167` already asserts exit 0 for this case, so this is a contract conflict between the new help sentence and an existing test, not an untested branch.

## Inspection-1 findings and other checks

1. **Verdict answer: closed.** `SessionKeyGuard.cs:125-159` rejects the exact four-segment `POST /sessions/{sid}/turn-verdict/answer` before its allow list, after lower-casing structural segments (`:114-123`). No inspected HTTP path lets a session key invoke the Gateway's prompt tunnel command directly. This census does not cover later internal automation that can itself send a prompt.
2. **Invented supervisor: closed for session-key spawns.** Both spawn doors call `SpawnOrigin.TryEstablish` (`GatewayEndpoints.cs:3900-3938`; `MachineEndpoints.cs:425-454`). A session credential is read from authenticated request items, stamps `ParentSessionId`, and overwrites origin (`SpawnOrigin.cs:82-90`). The controller is trimmed, parsed as a GUID and compared as a GUID to that credential's `SessionId`; a different GUID is 403, malformed spelling is 400, and an equal GUID in upper case, braces or another parseable GUID format is stored in the credential's canonical spelling (`:92-155`). Body `Origin`, `OriginSurface`, `ParentSessionId` and other fields do not select a different controller. Literal `none` sets a null controller (`:111-117`), so `--standalone` creates no supervisor relationship. The relayed Director arm carries no session identity and accepts the body's controller (`:76-84`); the owner's device arm clears both parent and controller (`:61-70`). These are credential distinctions, not bypasses available to a session key. The route test proves a stranger's id is refused before `create` (`FleetMessageRouteTests.cs:425-446`). The Director create path was not exercised live here.
3. **Read-then-lost: partially closed as described above.** The old latest-20 limit is gone; recent reads use `ReadAtUtc >= now - 24 hours` (`FleetMessageStore.cs:164-179`) and the service passes the configured window (`FleetMessageService.cs:121-124`). The predicate is provider-neutral EF: on Postgres it translates in substance to `WHERE tenant_id = @tenant AND RecipientSessionId = @recipient AND ReadAtUtc IS NOT NULL AND ReadAtUtc >= @readSince ORDER BY ReadAtUtc DESC, CreatedAtUtc DESC`. The tenant predicate comes from the context query filter (`GatewayDbContext.cs:1207,1353-1362`); the Postgres migration has the recipient/read-time index (`20260916195948_AddFleetMessages.cs:55-60`). There is no SQLite-only function in this query. This translation is an inference from the LINQ mapping; this inspection did not execute it against Postgres.
4. **Text cap and policy advice: closed.** The default 16,000 cap and 24-hour window are asserted against literals (`FleetMessagePolicyTests.cs:51-64`), as are the two advice sentences (`:71-82`). The boundary test uses literal lengths (`:303-310`). `SpawnOrigin.NamedAnotherOwner` is likewise pinned (`SpawnOriginTests.cs:127-136`), the needs-manager refusal is pinned (`FleetMessageRouteTests.cs:478-486`), and the broadcast exit sentence is pinned separately in the command line test (`test_message_queue.py:300-303,321-326`). Apart from the `none` seam above, no changed numeric default or approved advice sentence in this fix round can be changed alone while these tests stay green. Free-form comments and unasserted explanatory error text can change without a test failure.
5. **Broadcast exit: partially closed.** `_report_broadcast` exits 0 if any row was queued or duplicate, 1 when both sets are empty (`session_ops.py:1265-1280`); the docstring and command help state that outcome (`:1241-1251`; `cli.py:1750`). An all-duplicate result is tested (`test_message_queue.py:306-318`). The empty-recipient case remains open as ranked above.

**Needs-manager:** The 500 claim is supported: the former `.RequireAuthorization()` metadata had no matching ASP.NET authorization middleware, and restoring it made the route tests answer 500 per the fix-round record (`handoff.md:209-217`). The current route has no such marker (`GatewayEndpoints.cs:2728-2771`). A session key cannot raise another session's hand by these variations. A host deliberately configured with authentication disabled has no host-wide wall, as before this fix.

## Restore command facts

`DrainRestoreCommand.Build` only **writes** a command into the drain record; it never executes one (`src/CcDirector.ControlApi/Drain/DrainRestoreCommand.cs:23-70`). It writes `--standalone` for a seat with no controller (`:54-55`), a placeholder `--controlled-by <the new id ...>` for a controller restarted in the same drain (`:56-57`), or the existing controller id for one on another Director (`:58-59`). The director-restart conduct says the owner executes the protected **restart** (`director-restart`, step 7, lines 438-457). Its step 8, lines 468-477 and 503-512, assigns **restore** to the session that comes back to the index; the recorded restore run was performed by a fresh session (`:667-675`). The Director supplies captured facts and the command; it does not currently execute the restore command automatically (`:695-700`).

The builder's blanket claim that the owner pin refuses **every** restore is false. A restored mission head with `--standalone` goes through the `none` arm. A session restoring a controlled seat under some *other* session's id with its own session key is refused 403 at `SpawnOrigin.cs:136-151`; that part of the breakage is real for the documented restore operator. If the restoring session is itself the named controller, GUID equality allows it. An owner credential is not subject to the session pin, and a Director-relayed spawn is in the separate arm. No live restart or restore was performed in this inspection.
