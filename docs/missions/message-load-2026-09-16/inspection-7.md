# Inspection 7 — slice 6, restore is a Director act

**Verdict: FAIL for merge.** A session key can use captured workspace judgments to select an arbitrary owner for a restored worker, and can restore a live captured seat without a drain. The retry and concurrent Director paths can also start one seat twice. These defeat the spawn owner pin and the skill draft's once-only promise.

## Findings, ranked

### Critical — a session key can name another session as owner through `restoredSessionId`

`SessionKeyGuard.cs:519-533` admits a session key to workspace PUT and restore. `WorkspaceEndpoints.cs:185-218` accepts its PUT. `WorkspaceStore.cs:289-319` restores the captured `ReportsTo` but explicitly leaves `RestoredSessionId` as caller-written judgment; `WorkspaceValidation.cs:436` only caps its length. `DirectorRestore.cs:373-374` treats that field on the captured boss seat as the worker's new owner, and `:397-420` sends it in the Director's create. `SpawnOrigin.cs:73-84` skips the session-key owner pin because the create carries the Director's credential. This contradicts brief ruling 1, the boundary established in inspection 2, and judgment call 1's claim that a session cannot choose an owner.

**Prove it:** Capture a Director with boss B and worker W reporting to B. Using an unrelated session key in the same account, GET the captured workspace, PUT B's `restoredSessionId` to the ID of unrelated session X, set W's restore decision and handover path, then POST restore with `seats:[W]`. B is excluded from the run as already restored; W is created with `controllerSessionId=X`. X can be a live session the caller did not start. A nonexistent X may be refused later by the Director, but a live X is sufficient to cross the boundary. The existing route test proves ordinary owner resolution, not this writable judgment seam.

### High — a captured live fleet can be restored without having drained

The session-key guard admits capture (`SessionKeyGuard.cs:523-524`) and restore (`:529-533`). Capture reads an observed *live* fleet (`WorkspaceEndpoints.cs:259-305`). A writer may set the restore decision and handover path (`WorkspaceStore.cs:318-319`). `DirectorRestore.SelectTargets` checks only captured origin, decision and absent restored ID (`DirectorRestore.cs:294-307`); it checks neither `drainState` nor whether the captured session is still alive. The same-machine check (`WorkspaceEndpoints.cs:113-123`) does not prevent a second copy on that machine. This contradicts the draft skill's claim that a seat comes back once.

**Prove it:** Capture a running seat, PUT `restore.decision=restore`, its required command and a handover path, and POST restore to its current Director with that session key. The old session remains running while a new session is created. An authored workspace is refused, but capture followed by judgment edits is enough.

### High — timeout and interrupted commit can start a seat twice

The Director answers 202 before creating seats (`ControlApiHost.cs:1181-1192`). If it dies after create but before workspace save (`DirectorRestore.cs:224-273`), the record has no restored ID; `SelectTargets` admits it again (`:303-307`). A client timeout is explicitly marked “MAY have been started” (`:233-238,279-282`), but the failure is only advisory and the same selection admits a retry. The command itself suggests asking again (`machine_ops.py:1113-1114`). The ten-second HTTP timeout is `GatewayClient.cs:107-115`. The Gateway losing the tunnel after 202 gives the caller a pending result until the wait expires (`machine_ops.py:1133-1151,1175-1182`); it cannot tell whether a create landed. This is a duplicate-start risk despite judgment call 5 and the draft skill's “asking twice is safe” sentence.

**Prove it:** Make `SpawnOnThisDirectorAsync` complete the Gateway create and then time out before the response, or stop the Director immediately after create and before `SaveWorkspaceAsync`. Ask for the seat again. The timeout unit test (`DirectorRestoreTests.cs:242-253`) asserts the warning and other-seat progress but never retries the uncertain seat.

### High — the one-at-a-time gate is per process, not per workspace

`DirectorRestore.cs:95-136` has a static gate inside one Director process. Two Directors on the captured machine both pass the Gateway's machine comparison (`WorkspaceEndpoints.cs:107-123`), both read a workspace with no restored IDs (`DirectorRestore.cs:145-156,197-208`), and both can create the same seats. Their subsequent saves use the latest stored provenance but retain caller judgments (`WorkspaceStore.cs:253-319`), so the last write can hide the other create. The class comment acknowledges this at `DirectorRestore.cs:88-91`. The single-Director race is refused by `ControlApiHost.cs:1162-1165`; the cross-Director race is not.

**Prove it:** Register two Directors on one machine, pause each after `PrepareAsync`, release them together, and count `create` commands and surviving workspace IDs. Replay after a fully saved success is refused for a named seat (`DirectorRestore.cs:320-323`) or skipped for an all-seat request (`:303-309`); the unsafe windows are before that durable mark.

### Medium — outside and blocked owners are assumed alive

For a captured `ReportsTo` outside this workspace, `DirectorRestore.cs:369-370` uses the old ID without a roster check. For a boss recorded blocked and never closed, `:376-380` does the same. A different Director may have since stopped the outside owner, or a blocked owner may have been closed by hand without updating the workspace, as judgment call 4 acknowledges. In either case the worker can start under a dead ID. `WorkspaceStore.cs:309` does protect the original `ReportsTo` from PUT edits, so this is a liveness gap, not the arbitrary-owner route above.

**Prove it:** Capture a worker whose owner runs outside the drained Director, stop that owner, then restore the worker. Repeat with a boss recorded blocked and no `closedAtUtc`, then close it by hand before restoring its worker.

### Low — `--wait-seconds 0` exits successfully on acceptance, before restoration

`machine_ops.py:1116-1127` returns immediately on a 202, with exit 0 and only “TAKEN”, while `cli.py:1324-1329` says exit 0 only when every seat came back. The default waiting path correctly exits 1 for failed or pending seats (`machine_ops.py:1133-1182`). This is an explicit ask-only mode, but the exit promise needs to distinguish acceptance from completion.

**Prove it:** Accept a restore whose first seat will fail and run with `--wait-seconds 0`; observe exit 0 and no seat result.

## Other questions checked

- **Reporting chain, depth three:** A (root) starts with user owner. B reports to A but its spawn fails, for example “repository not found”. C reports to B and is never spawned: its failure says B “could not be brought back” and includes B's reason. D reports to C and is never spawned: its failure includes C's propagated reason. A sibling E reporting to A still starts under A's new ID. `OrderSeniorsFirst` sorts by depth then drain order (`DirectorRestore.cs:333-356`); `ResolveOwner` uses the newly saved owner ID, or `failedHere` (`:363-389`). A dependent seat selected without its owner first fails “has not been brought back yet”; a closed or undecided owner gives its decision in the failure. The live-owner exceptions are in the medium finding.
- **Account and machine:** The restore route's Director lookup is tenant-scoped at `GatewayHost.cs:3999-4007`; another account's Director returns 404 (`WorkspaceEndpoints.cs:107-111`). A Director on a different named machine returns 409 (`:113-123`). This is a comparison of registered machine names; both blank values bypass it. The workstation credential is read by `GatewayClient.cs:107-115`, then used for the create at `:389-405`. A session key sent directly to the spawn door still reaches `SpawnOrigin`'s restriction (`GatewayEndpoints.cs:3944-3971`); the restore route itself makes the Director use its credential. I did not establish that a session process can read or reuse the Director's credential file; the restore route already grants the practical owner-naming path described above.
