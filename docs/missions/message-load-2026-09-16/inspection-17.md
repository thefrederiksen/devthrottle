The second probe establishes that a recorded 800 ms decision cannot hide an actual rung-timed call.
2. **Threshold on this platform.** I temporarily printed the handler gap and ran the unmodified test 20 separate times in Release. All 20 passed. Observed gaps in ms: **806.246, 807.435, 815.766, 806.904, 810.615, 808.654, 812.928, 807.011, 807.283, 806.684, 815.827, 812.698, 806.901, 812.340, 808.774, 808.704, 813.502, 809.455, 813.766, 809.838**. Minimum **806.246**, maximum **815.827**. The 700 ms threshold leaves over 100 ms below the requested 800 ms and distinguishes the 20 ms rung. Timer coalescing delays a callback; it does not account for one firing 100 ms early. These runs give evidence for this macOS/.NET 10 runtime, not a universal guarantee against every timer implementation or clock anomaly. The test's 20 second `Eventually` cap remains a separate bounded-wait risk under an extreme runner stall.
3. **Timestamp synchronization.** `SendAsync` takes `_stamps`, appends the monotonic timestamp, releases it, then increments `_calls` with `Interlocked`. The getter takes only `_stamps`. No path takes the counter as a lock or acquires locks in the opposite order, so there is no lock cycle. Once the test sees `Calls >= 2`, both timestamps have already been appended and their lock released; the getter cannot see only one. The timestamps measure handler entry order. The retry path here is serial, so that order is the first call followed by its re-attempt.

**Finding 1 — launch-window tests rely on a finite unsynchronized registration window.** In `The_SAME_key_works_the_moment_the_registration_lands`, I temporarily awaited the registration before the supposed early request, modeling a continuation that resumed after the 50 ms registration. The Release test failed at `Assert.False(earlyContinued)` with `Actual: True`. A 150 ms extra delay did not reproduce the failure on one attempt because the registration task itself was also delayed, so the explicit await is the decisive ordering probe, not evidence of an ordinary 150 ms stall. The same ordering hazard exists with the 30 s delays, though I did not reproduce a spontaneous 30 s stall. The three tests share one root finding; the 50 ms case is the practical risk. The original file was restored and the two named baseline tests passed (2/2).
