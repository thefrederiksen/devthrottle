# Inspection 4: slice 2 doorbell

## Verdict: FAIL for merge

The local safety check is useful, and the three selected test suites pass. It does not establish the ruling 7 guarantee under concurrent input or all screen shapes. The stuck notice can also be lost after the message has been marked stuck. These are code findings; the saved live runs cover the recorded 120 by 40 screens and do not exercise these schedules.

## Findings, ranked

1. **High: a line can enter a working turn.** `DoorbellSafety.Check` trusts a sampled activity value and two sampled frames (`src/CcDirector.Core/Sessions/FleetDoorbellRinger.cs:30-46`, `src/CcDirector.Core/Drivers/DoorbellSafety.cs:142-164`), then `SendTextAsync` starts without a lock or another state check (`FleetDoorbellRinger.cs:67-78`). A false settled edge caused by a repaint asks the Director (`src/CcDirector.Gateway/GatewayHost.cs:3091-3099`); a current Working state or visible `esc to interrupt` catches it. If both the Director state and visible footer lag, the check allows it. The same window exists between tool calls: a turn may start after the second frame and before the first input byte. A ring arriving during static thinking is caught only while the activity state remains Working or the footer marker remains visible; the two identical frames add no evidence of activity. The sampling interval is 120 ms (`FleetDoorbellRinger.cs:24-25`); the unguarded interval runs from the last sample through the send, and the send includes the submit verifier's eight 1.2-second beats (`src/CcDirector.Core/Input/SubmitVerifier.cs:47-61,104-139`). Reproduce with a controlled session that starts a turn after frame two, or holds a working but marker-free static screen with activity incorrectly Idle, then invokes `ring`. The recorded mid-turn run only proves the visible-marker case (`slice-2-evidence/run1-mid-turn/timeline.txt:4-11`). This contradicts ruling 7's unconditional “rings only if the session is not working.”

2. **High: whitespace-only drafts are read as empty.** Both readers trim the prompt content and call a zero-length result empty (`src/CcDirector.Core/Drivers/DoorbellSafety.cs:222-226,242-250`). A real space or tab after either prompt glyph is therefore indistinguishable from an empty composer in the rendered rows. Reproduce by cloning either captured idle fixture, placing spaces after the prompt glyph in both frames, and calling `Check`; it returns `Ring=true` while the composer holds owner input. The 13 captures have ordinary text, a two-line draft, and a collapsed paste, but no whitespace-only draft (`src/CcDirector.Core.Tests/TestData/doorbell/README.md:12-25`). The framed reader correctly retains visible continuation text and the collapsed paste (`DoorbellSafety.cs:223-226`); the cursor reader correctly treats non-placeholder visible text as held (`DoorbellSafety.cs:246-250`). An unknown placeholder suggestion is treated as text, so it delays a ring. A wrapped long draft and a narrow terminal were not captured; a wrap that leaves the visible prompt and continuations blank, or moves the working marker above the bottom eight rows, may be misread (`DoorbellSafety.cs:187-189,203-231,281-287`). That last case is an untested screen-shape risk, not a reproduced capture failure.

3. **High: a stuck mark can permanently lose its sender notice.** `MarkStuckAndNotify` commits all stuck marks first and sends notices afterward (`src/CcDirector.Gateway/Messaging/FleetDoorbell.cs:269-285`; `src/CcDirector.Gateway/Messaging/FleetMessageStore.cs:300-311`). A process stop or `Send` exception after the commit leaves `StuckAtUtc` set; the next heartbeat excludes the row, so no notice is retried. Reproduce with a message due to be stuck and a message service/store that throws on notice enqueue after `MarkStuck`, then sweep again. This violates ruling 11's sender-notice result. A dead sender is still an allowed notice recipient: the send uses the stored sender id with no live-roster check (`FleetDoorbell.cs:276-284`); it remains queued but cannot ring while disconnected. A notice about a notice cannot loop because system notices have null `SenderSessionId` (`src/CcDirector.Gateway/Messaging/FleetMessageStore.cs:111-123`) and the loop skips null (`FleetDoorbell.cs:276`). Repeated successful sweeps do not duplicate one notice because the stuck transition is under the store lock. A failure between mark and send is the exception.

4. **Medium: the submit exception fallback proves less than `rung`.** On `PromptNotSubmittedException`, the Director equates an empty composer with successful submission (`src/CcDirector.Core/Sessions/FleetDoorbellRinger.cs:75-91,104-107`). Empty can also result from a TUI clearing or discarding the line without starting a turn, or from a concurrent owner action. The recipient then sees no doorbell but the Gateway counts a ring (`src/CcDirector.Gateway/Messaging/FleetDoorbell.cs:254-258`); after three such outcomes it can receive a stuck record without three seen rings. Conversely, `SubmitVerifier` may send up to eight extra Enters during a short answer (`src/CcDirector.Core/Input/SubmitVerifier.cs:109-138`). If the initial submit succeeded, a later Enter can submit the same line only if it has been reintroduced to the composer; otherwise it can submit newly typed owner text. The saved pre-fix run shows four visible lines for three counted rings, and the later run shows three (`slice-2-evidence/README.md:81-96`); neither distinguishes a discarded line from a submitted short turn or closes the concurrent owner-input case. Prove with an instrumented backend that clears without submitting, and separately with a short-turn backend plus a new composer draft during a dead beat. This is the limitation of judgement call 11.

5. **Medium: the store does not itself enforce the ring cap or recipient association.** The ordinary single-host path computes due ids with the cap (`src/CcDirector.Gateway/Messaging/FleetDoorbell.cs:30-46,217-222`) and serializes per session with `_inFlight` (`FleetDoorbell.cs:200-213`), so it normally stops at three. `MarkRung` only rechecks unread and unstuck, then increments; it does not recheck due, cap, or recipient (`src/CcDirector.Gateway/Messaging/FleetMessageStore.cs:269-288`). Two Gateway processes or a direct stale call can record more than three. A read between ring and `MarkRung` wins under the store lock and leaves count unchanged (`FleetMessageStore.cs:208-224,275-288`), although the recipient may already have seen the line. A perpetual deferral, unreachable Director, unknown reader, or exited session remains open without ever reaching three counted answers (`FleetDoorbell.cs:224-262`). Prove the store gap by calling `MarkRung` four times on one unread row, or passing an id from a different recipient within the same tenant. Both `MarkRung` and `MarkStuck` do use `CreateContext(tenant)` and `_gate`; the tenant boundary and same-process read race are sound (`FleetMessageStore.cs:275-311`).

6. **Medium: heartbeat work grows with backlog and can miss its cadence.** Every 15-second tick enumerates all open recipient ids, scans every rung open row for stuck, and fetches every open message for each recipient (`src/CcDirector.Gateway/Messaging/FleetDoorbell.cs:186-195,215-222,269-273`; `src/CcDirector.Gateway/Messaging/FleetMessageStore.cs:240-261,300-311`). None of those queries has a limit. For 40 recipients, a tick performs one distinct-recipient query, one unbounded stuck-candidate fetch, and at least 40 open-message fetches. If all are due and connected it adds 40 count queries and up to 40 sequential tunnel calls (`FleetDoorbell.cs:246-247`); one slow call delays later sessions, while the host drops overlapping ticks (`src/CcDirector.Gateway/GatewayHost.cs:574-595`). An absent roster target returns before `_ring`, so a disconnected Director receives no tunnel call (`FleetDoorbell.cs:224-229`; `GatewayHost.cs:1933-1939`). Measure with 40 due sessions and a delayed ring delegate; assert the tail session's wait and the number of skipped timer passes. This is a latency and load risk, not a failing 40-session measurement.

7. **Low: approved constants and wire strings have uneven guards.** The default five-minute grace and cap of three are asserted directly (`src/CcDirector.Gateway.UnitTests/Messaging/FleetDoorbellTests.cs:458-459`), and the doorbell line has exact string assertions (`src/CcDirector.Core.UnitTests/Sessions/DoorbellSafetyTests.cs:274-281`), so those edits redden the selected suites. The named defer reason constants are mostly asserted through the same constants on both sides (`DoorbellSafetyTests.cs:69-83,154-170`; `src/CcDirector.Gateway.Contracts/FleetMessageRequests.cs:191-208`); changing a constant's literal while keeping all call sites together can leave these suites green and change the wire contract. The Gateway logs but does not validate a deferred reason (`FleetDoorbell.cs:260-262`). Prove by changing one reason literal, rerunning the selected suites, and inspecting the serialized response.

## Checked and found sound

- The Gateway's Working, Starting, and Exited roster states avoid a tunnel call (`src/CcDirector.Gateway/Messaging/FleetDoorbell.cs:231-242`); the Director independently checks its own state and both frames (`src/CcDirector.Core/Drivers/DoorbellSafety.cs:146-164`). This catches the recorded active-screen case, including an empty composer while the footer says `esc to interrupt`.
- On the captured 120 by 40 screens, framed prompts with owner text, continuation text, and the collapsed paste defer; the visible cursor placeholder alone is accepted; selected menus defer (`src/CcDirector.Core.Tests/TestData/doorbell/README.md:1-25`; `src/CcDirector.Core/Drivers/DoorbellSafety.cs:203-250`). The capture set has no live working frame for the cursor-based reader and does not test other terminal widths.
- `ring` is registered in the Director command verb map (`src/CcDirector.ControlApi/SessionCommandExecutor.cs:83-110`) and reached by the tunnel dispatcher (`src/CcDirector.ControlApi/ControlApiHost.cs:995-1018`). The local Control API exposes explicit HTTP routes; I found no local HTTP route mapping this verb. Direct in-process callers of `DispatchAsync` can invoke it, but a machine-local HTTP caller has no generic verb route in this code.
- A ring only carries unread count; message text stays in the inbox (`src/CcDirector.Gateway/GatewayHost.cs:551-569`; `src/CcDirector.Core/Drivers/DoorbellSafety.cs:290-302`). Inbox read marks rows read and clears stuck under the same store lock (`src/CcDirector.Gateway/Messaging/FleetMessageStore.cs:208-224`). A system notice bypasses relationship and rate checks via the system exemption (`src/CcDirector.Gateway/Messaging/FleetMessageService.cs:66-92`).
- Ruling 15 is already contradicted by the acknowledged Gateway snooze law, and the architect assigned that correction to slice 2b (`handoff.md:766-784`). The dictation lock is also assigned to slice 2b there. Neither correction is present in this inspected slice; both remain merge prerequisites under the brief. Ruling 14's broad wording is narrower in implementation: unsupported reader layouts defer indefinitely (`src/CcDirector.Core/Drivers/DoorbellSafety.cs:191-200`). The architect accepted that narrower coverage pending the row-line slice (`handoff.md:779-784`).
