# Inspection 11 — restore fix round, row line, and words on the final branch

**Verdict: FAIL for merge.** The restore mark route still lets a same-account workstation device key that does not own the lease impersonate its Director, and the final tree still contains current-tense instructions for retired messaging behavior. The row line implementation and the other five inspection-7 repairs held under the checks below.

## Findings, ranked

### High — a different workstation device key can forge a restore mark under another Director's lease

`src/CcDirector.Gateway/Api/WorkspaceEndpoints.cs:201-225,419-429` admits a workstation credential as a “Director credential” without binding that credential to the Director named by the mark. `src/CcDirector.Core/Sessions/SessionOrigin.cs:101-107` maps every device type other than phone and browser to `unknown`, which passes this gate. `src/CcDirector.Gateway/Workspaces/WorkspaceStore.cs:452-455` checks only the caller-supplied `mark.DirectorId` against the lease, and `:495-505` accepts a `restored` mark naming any new session ID, without requiring a matching started token or a real create. Thus another same-account workstation key can write `restoredSessionId`, `restore.failure`, `attemptedAtUtc`, and the started token while a real Director holds the lease. It can also send `finished` to release that lease (`:460-463`). This contradicts inspection-7 ruling 1's statement that a device key may set only a decision and handover path, and ruling 4's lease-holder boundary. The code's narrower trust assumption is recorded in `handoff.md` as judgment call 5, but that does not change the ruling.

**Prove it:** Enroll two workstation devices in one account. Have Director A take a captured workspace's lease, then use device B's key to POST `/gateway/workspaces/{id}/restore/marks` with `directorId` equal to A, `kind=restored`, a captured boss seat ID, and `restoredSessionId` equal to a live unrelated session X. Read the workspace: X is recorded without a create or token. Restore its worker alone after closing the captured seat; `DirectorRestore.ResolveOwner` reads the boss's recorded restored ID (`src/CcDirector.ControlApi/Drain/DirectorRestore.cs:556-615`) and can name X as the worker's owner. A phone or browser key receives 403, but that test does not exercise a second workstation key. The existing route suite uses one workstation key for its fake Director (`src/CcDirector.Gateway.Tests/WorkspaceRestoreRouteTests.cs:74-84`) and tests only session and browser refusals (`:347-364`).

### Medium — the sessions law page still describes the removed blocking ask as surviving

`docs/new_architecture/sessions.html:487-503` correctly dates the 16 September queue ruling and says it replaced the 13 September interrupt ruling. `:1331-1354` dates the 17 September snooze exception. Yet `:1657` says the ask-and-wait verb is “surviving”, names `cc-devthrottle message ask`, and describes its present behavior. That is a current-tense contradiction on the same page. The old verb is explicitly removed by `docs/missions/message-load-2026-09-16/brief.md:80-84` and the Gateway now refuses it at `src/CcDirector.Gateway/Api/GatewayEndpoints.cs:3253-3265`.

**Prove it:** Read the three cited passages together and run the command help or the Gateway refusal test. The retired-words guard remains green because its `TaughtFiles` inventory (`src/CcDirector.Core.UnitTests/Skills/RetiredMessagingWordsTests.cs:103-124`) does not include `sessions.html`.

### Medium — active source text and repository instructions still teach the old words

The whole-tree sweep, excluding only `docs/missions/` history, finds `tools/cc-ship/src/fleet.py:114-119` saying fleet text truncates at the first newline; `src/CcDirector.Gateway.Contracts/FleetMessaging.cs:36-39` explaining a live `message ask` flow; `packages/client-core/src/sessions/tree.ts:42-45` and `src/CcDirector.Gateway.Contracts/SessionTree.cs:99-102` saying `--controlled-by` takes any session ID; and `ARCHITECT-HANDOVER.md:43-46` instructing a one-line fleet reply because of newline truncation. `missions/stop-a-session/worker-e-director-window.md:3-5` and its sibling briefs still say messages interrupt the receiving session. Older plans and reviews also offer `message ask`, for example `docs/MISSION-source-control-tab-2026-07-23.md:60-64`. These are not under the excluded `docs/missions/` directory. The comment in `FleetMessaging.cs` is especially misleading because it documents a callable method's parameter in the present tense.

**Prove it:** Run `rg -n -i 'message ask|interrupts the session that receives|truncate at the first newline|--controlled-by takes any' --glob '!docs/missions/**' .` and inspect the cited hits. The existing retired-words test scans a fixed subset (`RetiredMessagingWordsTests.cs:103-124`), so these can remain while it stays green. The sweep also has hits that *describe retirement* rather than offer old behavior; those are not findings.

## Checked and found sound

- **Inspection-7 findings 1–6, except the device-key route above:** `WorkspaceStore.RestoreStoredMarks` restores the stored IDs, failure, attempt time, token, and Director fields over ordinary PUTs (`src/CcDirector.Gateway/Workspaces/WorkspaceStore.cs:322-365`). Session keys cannot reach the mark route, and phone/browser keys are refused there (`WorkspaceEndpoints.cs:195-225`). A reachable captured seat is refused even when its written drain state says closed; a listed seat on an unreachable Director needs a recorded close (`src/CcDirector.ControlApi/Drain/DirectorRestore.cs:445-455`). A started mark precedes create, and uncertain results retain it; an unforced retry is blocked, while `--force-seat` only applies after the two-minute in-progress window and cannot revive a seat with a recorded restored ID (`:352-394,458-524`). The create route records a matching token after the Director confirms a create (`src/CcDirector.Gateway/Api/GatewayEndpoints.cs:4036-4049`); a crash between create and record remains a disclosed unresolved start, not a blind retry. The lease is checked and renewed on marks, expires after 15 minutes, and the finished mark releases it (`WorkspaceStore.cs:384-414,452-465`). Outside, blocked, and earlier-restored owners are checked against the reachable roster before a new worker starts (`DirectorRestore.cs:556-615`). The ask-only command prints “ACCEPTED, NOT WAITED” and exits 3 (`tools/cc-devthrottle/src/machine_ops.py:1132-1147`). An explicit `--force-seat` after checking the roster can duplicate an unrecorded prior start; that is the override the ruling permits.
- **Row line:** The Gateway counts unread messages by recipient, kind, and stuck state in one tenant-scoped grouped query per fold, then stamps each row by its session ID (`src/CcDirector.Gateway/Messaging/FleetMessageStore.cs:479-518`, `FleetInboxLineFold.cs:114-135`). `GatewayDatabase.CreateContext(tenant)` sets the tenant and `GatewayDbContext` filters `FleetMessageEntity` by it (`src/CcDirector.Gateway/Data/GatewayDatabase.cs:490-507`, `GatewayDbContext.cs:1318,1488`). Thus a 40-session push has one inbox query, not 40. Every stamp assigns a string or null, clearing stale lines after a read. The Director rail, Cockpit, and phone render `InboxLine` directly (`src/CcDirector.Avalonia/SessionViewModel.cs:647-654`, `apps/cockpit/src/sessions/SessionRoster.tsx:455`, `apps/mobile/src/pages/Home.tsx:796`). The merge kept both `inboxLines` and `writes` in the fold; the push supplies the inbox source, while the color/label trace deliberately skips the inbox read (`src/CcDirector.Gateway/Fleet/DisplayFold.cs:100-116`, `src/CcDirector.Gateway/Api/GatewayEndpoints.cs:5384-5390,5492-5496`). The integration kept `inboxLines` and `workspaces` as named `GatewayEndpoints.Map` inputs (`GatewayEndpoints.cs:270`). The query count is bounded, though this review did not benchmark the grouped query against a large inbox or PostgreSQL.

The fleet-comms skill says six per rolling hour, one per recipient per ten minutes, five-minute re-ring, three rings, 24-hour `--all` with a 200 cap, and a default 60-minute reply window (`src/CcDirector.Gateway/Skills/Content/fleet-comms.skill.md:176-222`), matching `src/CcDirector.Gateway/Messaging/FleetMessageLimits.cs:16-55`.
