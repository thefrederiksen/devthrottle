## Findings, ranked

1. **High — unverified cleanup can erase owner input.** `DoorbellSafety.ComposerHoldsExactly` removes *all* Unicode whitespace from both strings before comparing them (`src/CcDirector.Core/Drivers/DoorbellSafety.cs:317-324`). `TakeBackUnverifiedAsync` then sends `line.Length` Backspaces after that comparison (`src/CcDirector.Core/Sessions/FleetDoorbellRinger.cs:231-245`). If the doorbell is parked and the owner adds a trailing space, tab, or non-breaking space, the comparison still says the composer holds exactly the doorbell. Cleanup erases the owner's added character and may leave some of the doorbell behind. This contradicts inspection-4 ruling 2's “EXACTLY the doorbell line” and “anything else, leave it.” Prove with a scripted frame whose composer holds `FleetDoorbellLine.For(1) + " "` (also try `\t` and `\u00a0`), an unverified submit, and an erase recorder. Assert that `EraseAsync` is never called. A narrow screen wrap is another reason to compare a structured composer reading rather than delete every whitespace character: the current squeeze also equates owner-inserted internal spaces with wrap separators. The existing wrapped-line test covers only the unextended line.

2. **High — a stuck mark can commit without its required notice.** `MarkStuckWithNotices` sets `StuckAtUtc` before it asks policy about the notice, then saves the mark even when `verdict.Queued` is false (`src/CcDirector.Gateway/Messaging/FleetMessageStore.cs:405-430`). The system exemption still enforces unread duplicate and text rules (`src/CcDirector.Gateway/Messaging/FleetMessagePolicy.cs:133-138,160-164`). A pre-existing identical unread system notice, or a notice whose interpolated recipient name makes it exceed `MaxTextLength`, makes policy refuse the notice. The mark commits, and later sweeps exclude the row at `FleetMessageStore.cs:401-403`; the sender never gets this stuck notice. This contradicts inspection-4 ruling 4 and brief ruling 11. Prove by preloading the exact notice text as an unread system record, then running `MarkStuckAndNotify`: the resulting stuck row has no new notice. Repeat with a roster name long enough to make the notice fail the text limit. A thrown roster read *does* leave both uncommitted, as the existing test shows. An absent sender session is different: its id remains a valid notice recipient and the record queues, though it cannot ring until the session reconnects (`src/CcDirector.Gateway/Messaging/FleetDoorbell.cs:409-417`).

3. **Medium — a stale dictation lock can silently delay rings, and judgement call 5 misstates its lifetime.** The new host lock reads `IsSessionLocked` (`src/CcDirector.Gateway/GatewayHost.cs:1945-1952`), which reflects a PENDING record (`src/CcDirector.Gateway/Voice/VoiceUploadStore.cs:1123-1142`), and the due message is merely deferred (`src/CcDirector.Gateway/Messaging/FleetDoorbell.cs:346-353`). Contrary to judgement call 5's “never expires,” an existing Gateway timer runs every six hours and abandons PENDING records after 24 hours without directory activity (`GatewayHost.cs:850-880,4633-4657`; `VoiceUploadStore.cs:584-637`). In a functioning host the stale lock lasts up to roughly 30 hours, not forever. A failed or stopped sweep can leave it indefinitely; the sweep catches and logs failures rather than releasing the lock. The lock itself need not be visible on the row: `DictationPhase.For` shows “Uploading from phone” only while the record is also progressing (`src/CcDirector.Gateway/Transcription/DictationPhase.cs:38-54`), while the doorbell uses PENDING alone. Prove with a PENDING record past the progress window but below the stale sweep age: `DictationStatusFor` is null while a due ring returns `DeferredDictation`. This is an observability gap, not evidence that the ordinary stale sweep fails.

4. **Medium — the approved snooze exception conflicts with the current owner law; its attribution can be lost.** The Gateway keeps an armed snooze on `WorkingOrigin == "agent"` (`src/CcDirector.Gateway/Snooze/SnoozeLandingObserver.cs:125-140`), while `docs/new_architecture/sessions.html:1321,1350,1564` says any Working edge ends it, explicitly including another session's message. The handoff says the owner was asked to decide this conflict; it is still an open merge decision, not an accidental implementation choice. Agent work can also be reported as unexplained work: `SetActivityState` clears the origin on any settled detector edge (`src/CcDirector.Core/Sessions/Session.cs:3019-3043`); a false settled flicker followed by Working without a new submission yields null, so the Gateway deletes the snooze. This is acknowledged in judgement call 7. Prove by feeding Working(agent), a settled flicker, then Working(null) while an armed snooze exists. The reverse owner-as-agent case is guarded by the unchanged `LastOwnerTurnAtUtc` check, which runs before the exception (`SnoozeLandingObserver.cs:104-108`); owner text and raw Enter still stamp that fact (`Session.cs:2411-2429,2759-2769`). A newer Director with this field absent also falls through to clearing, not keeping.

5. **Low — submit verification remains a screen inference.** `ShowsDoorbellSubmitted` accepts any new row containing the marker, or the working marker, once the composer no longer contains the marker (`src/CcDirector.Core/Drivers/DoorbellSafety.cs:294-315`). An older doorbell row already visible does *not* spoof it because the baseline count is taken before typing (`src/CcDirector.Core/Sessions/FleetDoorbellRinger.cs:155-163`); the existing test covers that. An older row that enters the visible frame after a scroll or reflow can raise the count, and a concurrent turn can raise the working marker, even if this Enter was swallowed and the interface cleared the line. Prove with a scripted backend that clears the composer after Enter but reveals an older marker row, or starts an unrelated turn. The selected tests and the saved live runs do not exercise either schedule. This qualifies the “verified” screen witness in judgement call 2; it is not proof of a second Enter.

## Inspection-4 closure audit and other checked paths

1. **Last look: closed to its stated limit.** The third frame is taken through `mayTypeNow` at the start of `DoorbellSubmitAsync`, immediately before `WriteTextAsync` (`FleetDoorbellRinger.cs:155-163`; `src/CcDirector.Core/Drivers/TerminalSubmit.cs:231-236`). `SameFrame` compares every row by ordinal content and compares cursor row, column, and visibility; it does not compare object identity (`FleetDoorbellRinger.cs:194-215`). A turn can still begin after that call and before the first byte, exactly the residual accepted in brief ruling 7. The two initial frames are individually checked, not required to be identical.
2. **Submit: reopened by finding 1; otherwise one Enter.** The doorbell protocol writes one `DoorbellEnter`, has no nudge loop, and watches the screen (`TerminalSubmit.cs:208-264`). An empty composer after an unverified submit returns `not-submitted` without erasing; visible nonmatching text is left alone (`FleetDoorbellRinger.cs:231-253`). A pre-existing transcript row alone does not satisfy the increased-count witness. Finding 5 states the remaining inference limit.
3. **Whitespace: closed for the captured readers, with screen-shape limits.** After one prompt separator, visible tabs or non-breaking spaces remain text; trimmed spaces move the cursor beyond column 2 and are held; a hidden cursor defers as unreadable (`DoorbellSafety.cs:239-291`). A blank continuation with its cursor is held. A narrow screen that removes the framed prompt or moves the working marker outside the bottom scan defers when no composer can be found, but an untested layout that resembles an empty framed composer remains a screen-reader limit. The live evidence includes three spaces at `slice-2-evidence/fix-round/run2/02b-whitespace-draft.json`, not tab, non-breaking space, or narrow width.
4. **Stuck atomicity: reopened by finding 2.** One `SaveChanges` and the pre-save failure seam protect against a throw before persistence (`FleetMessageStore.cs:396-430`); they do not enforce a notice when policy returns a refusal.
5. **Store cap and recipient: closed.** `MarkRungMany` validates the recipient and cap from the read, and repeats unread, unstuck, and cap predicates in its one update (`FleetMessageStore.cs:291-338`). Thus a row read moments earlier cannot be incremented after a competing read/stuck/cap change that commits first. The tenant context is used for the read and update. No cross-process transaction test was run.
6. **Heartbeat: closed as ruled, with throughput limit.** The sweep reads stuck candidates at the cap and unread scheduling data without text; the ring pass uses eight concurrent calls with a five-second wait and cancellation (`FleetDoorbell.cs:218-275,385-399`). `GatewayHost.SendCommandAsync` passes that token to SignalR `InvokeAsync` (`GatewayHost.cs:5304-5335`), so a hung Director cannot hold a heartbeat slot indefinitely. Forty all-hung recipients can still take roughly five batches of five seconds, longer than the 15-second cadence. The one-statement update repeats its safety predicates as above. The saved command counter and selected tests cover SQLite, not hosted PostgreSQL.
7. **Wire strings: closed for the named contract.** The `ring` verb, outcomes, and every deferral reason have literal assertions on both sides (`src/CcDirector.Gateway.UnitTests/FleetDoorbellExecutorTests.cs:29-35,111-120`; `src/CcDirector.Gateway.UnitTests/Messaging/FleetDoorbellTests.cs:547-553`), and the Gateway rejects an unknown deferred reason or outcome (`FleetDoorbell.cs:364-379`). The exact doorbell line, default five-minute grace/three-ring cap, heartbeat's 15-second cadence, eight-way parallelism, and five-second timeout are asserted in the selected suites. Values that can change while these suites stay green include the 120 ms frame gap, 10-second watch, 10 erase polls, bottom-screen scan depth, six-hour dictation sweep cadence, and 24-hour stale age; their related tests exercise behavior without pinning those literals. These are operational tunables, not proof that the pinned wire strings drift.

The saved fix-round runs cover a 120-by-40 terminal, one-minute proof grace, and SQLite. They show a mid-turn defer, live spaces holding the composer, three verified rings followed by a sender notice, and a doorbell turn preserving a snooze followed by owner input clearing it. They do not cover the refusal, whitespace-extension, narrow-screen, or screen-reflow counterexamples above.
