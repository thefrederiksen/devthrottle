Mission report · issue 3029

A test that was guarding nothing

One test in the Gateway suite claimed to prove that the product correctly reports "I cannot find this session's transcript". It did not. On your machine it failed for a reason that had nothing to do with the product, and on a fresh machine it passed for a reason that had nothing to do with the product either. It now proves what it says, on any machine, whatever has been run on it before. Nothing in the product changed, because nothing in the product was wrong.

The value

What this buys you

The test guards a real failure you have already paid for. Issue 2561 records a session that sat silent for 48 minutes because this part of the product reported "I could not find the transcript" as "I read the transcript and it was empty". Voice narration heard "nothing to narrate", and nothing to narrate is never retried. The guard against that returning was this test.

The guard was not working. It built its session on the shared temporary folder and then asserted that no transcript could possibly be found for it. That is a claim about your machine, not about the product. Somebody had once run the Grok command line from the temporary folder, so a real conversation was sitting there; the product found it, correctly answered "ok", and the test went red. You saw that red every time you ran the suite.

The quieter half is worse. On a machine where nobody had ever done that, the same test went green - not because the product reports a missing transcript correctly, but because the folder happened to be empty. A test that can go green by accident is not guarding anything. That is what has been fixed: the test now builds its own folder, fresh for each run and deleted afterwards, which no transcript locator can resolve on any machine, for reasons that hold by construction rather than by luck.

The failure the test reported before the change was Expected: "no_transcript" Actual: "ok" - the product finding the stray Grok conversation, exactly as diagnosed.

The part that matters more than a green run

A test that has never been watched failing is decoration. So the product was deliberately broken underneath the fixed test, twice, by two different seats on two different agent families:

  • The builder removed the product's guard entirely, restoring the behaviour it had before issue 2561 was fixed. The test went red with Expected: "no_transcript" Actual: "ok" - byte for byte the old symptom, but now for the right reason: the product really was reporting a missing transcript as a successful read.
  • The reviewer, on a different agent family, did not trust that and broke the product itself. It watched the same three cases go red with the same message, then restored and watched them go green.

Under the old test that break could not have been caught on your machine at all, because the locator found a real transcript before the product ever reached the code being guarded. It can be caught now. That is the whole mission.

The review

The review was done by a session running a different agent family from the one that wrote the code, and it did not arrange its own review - I sent it. Its verdict was no findings, and it states what it read, what it ran and what it could not reach, so that an empty review and a review that never happened do not look the same. It read every transcript locator in the product rather than the comments describing them, and confirmed the new folder is unresolvable by construction for each one. It raised a single cosmetic observation and explicitly declined to file it as a finding.

Limits

What is NOT proven

One machine

Every run is SOREN_NORTH, Windows, Debug. The change removes the dependence on machine history by construction, and the argument is about how the locators match rather than about this machine - but it has not been executed on Linux or macOS.

The eight that remain

All eight are the same PostgreSQL fixture refusing to connect in HostedSchemaRefusesAnUnownedRowTests. They were out of scope by the mission document and were not touched, run or investigated. Your local suite is still red every time you run it.

Two agents are still uncovered

The Copilot and OpenCode readers key on a single machine-wide database rather than on the working folder, so this test deliberately does not assert them. It did not before either. A future locator built the same way would not be covered by this fix.

The stale baseline

The committed baseline this mission was written against said ten failures. I measured nine on the exact commit I was working from, because the tenth is a known intermittent that did not fire. I used my own before-run rather than the written number, which is why the drop reads as nine to eight and not ten to nine.

The real subject

The method's first run, and where it was awkward

This fix was small on purpose. The point was to find out whether the DevThrottle Method can actually be used. It can: a mission document, a delivery lead who never wrote a line, one builder, one reviewer on a different agent family, a check run by the seat doing the accepting rather than read off a report, and proof committed beside the code. The shape held all the way to merged. Five things rubbed.

Nobody is left to land the work

The workflow says only the Architect puts anything on main. The method has the Architect hand over and stop driving, and gives the delivery lead "drives the mission to done". Mine handed over and said plainly it was not looking over my shoulder, so there was no Architect to land it. I merged it myself, on the method and the mission document, which outrank the workflow. That contradiction should be settled in writing rather than by each run deciding for itself.

A seat can be opened and never start

The reviewer was first opened on Copilot. Its opening instruction sat unsent while the session loaded 69 skills, and it went quiet having done nothing at all. That looks exactly like a session thinking. Only reading its screen revealed it. I stopped it and reopened the reviewer on Pi, which started immediately. The method has no step that says confirm the seat actually started, and it needs one - or better, the product should not report a seat as open until it has taken its first instruction.

A baseline goes stale faster than a mission runs

The mission was written against a measured baseline from an earlier commit. By the time I ran, main had moved and the number was wrong. Measuring the before state myself on the exact commit cost four minutes and made every later claim safe. The method asks for a check; it should also ask the accepting seat to measure the before state rather than inherit it.

Every seat wants its own worktree, and there were four

Each seat gets its own checkout so that nobody edits the files underneath someone else's test run. The shared pool holds four and other missions had all four. I raised it to six. A three-seat mission needs three slots, so four is below the size of one ordinary mission plus anything else running.

Which agents are available is folklore, not product

Two agent families were at their usage limits, measured earlier the same day and written into my handover by hand. A session that hits a limit disappears shortly afterwards, so it reads as a broken start rather than as a limit. Without that handwritten note I would have spent an hour on it. The product knows this and could say it.

Yours to decide

Two decisions I did not make for you

The eight remaining failures

They are one cause - a PostgreSQL fixture that cannot connect - and they make your local Gateway suite red on every run, which is exactly the condition in which a real new failure hides. It is a small, well-understood piece of work and nobody is on it. Worth opening a mission for?

Who lands a mission's work

The contradiction above. My recommendation is that the delivery lead lands it, because the method already makes that seat responsible for the goal and for the record, and the architect is explicitly gone by then - but it is your method and your call.
