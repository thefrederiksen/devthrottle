## Verdict

**Accept, with two low findings that do not block the merge.** The five tables, the three stores and the validator
do what contract sections 2 and 3 say. Every table is tenant-scoped through `ApplyTenantScope`, every read I traced
is filtered to one account, every refusal in the store code returns before anything is added to the context, and a
rules version is written in the same `SaveChanges` as its change row. Both migrations carry the filtered unique index
over active channels, the unique (tenant, version) index on rules and the unique (tenant, channel, message key) index
on decisions, and both hold on a real PostgreSQL. No body column, no body field on the insert. Only
`email@devthrottle.com` and the reserved example domains appear in tests and examples. No attribution to any tool or its maker
anywhere in the diff or the commit message.

F1 is a test gap the contract's own rule ("nothing is recorded on any refusal") makes worth closing: a mutant that
records a change row on a refused mode passed all twenty channel tests. F2 is a provider divergence on the decision
insert that no SQLite test can see; whether it ever fires depends on which message key phase 3 chooses.

## Findings

### F1 (low). Three refusal paths are not tested for "nothing is recorded", and a mutant proves it

Contract section 4: "Nothing is recorded on any refusal." The store code honours it everywhere: `SetMode` refuses a
bad mode before taking the lock, and `Remove` and `SetMode` return `NoSuchChannel` before anything is added to the
context. The tests prove it for `Add` of an active address (`Assert.Equal(1, ...History(A).Total)`) and for an
invalid or stale rules save (`History(A).Total` is 0 or 1). They do not prove it for:

- `SetMode_AModeOutsideObserveAndLive_IsRefused` (checks the outcome, the sentence and that the mode is unchanged);
- `SetMode_ARemovedChannel_IsNoSuchChannel` and `Remove_AnAddressWithNoActiveChannel_IsNoSuchChannel` (check the
  outcome only).

What breaks: with mutant A applied (a `mode` change row written and then the refusal returned) all twenty channel
store tests passed. A later edit that moves the change row ahead of a refusal, in the store or in the route that
wraps it, reaches the branch green, and the owner's history then shows a mode change that never happened. The fix is
one assertion in each of the three tests: the history total before equals the history total after. It is a test
change only; the production code needs nothing.

### F2 (low, conditional). The decision insert enforces every column bound but the message key's, and the two providers disagree about it

`MailDeskDecisionStore.Require` refuses a sender longer than 320 characters, and `Insert` cuts the subject, the
reason and the outcome detail to their 1,000-character columns, so a row is kept the same way on both databases.
`MessageKey` (column `character varying(512)` on PostgreSQL) is checked only for blank, and `RouteFactory` and
`RouteSeat` (64) only for blank when the decision is a route.

What breaks: SQLite does not enforce a text length, so a key longer than 512 characters is kept locally and every
unit test passes. On the hosted PostgreSQL the same insert throws `DbUpdateException` from `SaveChanges`; the catch
asks `Kept` whether another writer holds the message, finds nothing, logs and rethrows. The decision is not recorded
and phase 3's check gets an exception instead of a row, for a message that was decided correctly. Nothing in the
suite can see this, because the only PostgreSQL test inserts a three-character key.

Whether it ever fires depends on the key phase 3 chooses: a Microsoft Graph message id is usually under 200
characters; an internet message id may run to 998 under the mail standards. The route factory and seat come from the
validated rules document, where `FactoryNames` already caps them at 64, so those two are safe today. The cheap fix
is one more line in `Require`, refusing a key over 512 with a sentence as the sender is refused, so that both
databases give the same answer and the bound is stated in code; alternatively the contract names the key and its
bound in phase 3 and this becomes moot. It does not block this merge.

## Observations that are not findings

- **Two open choices, both sound.** A stale save is a clear refusal with the newest version, not a retry; mutant B
  shows the index gives the same answer when the lock cannot. A seat must pass `FactoryNames.TrySeat`: every other
  seat the Gateway accepts (briefs, cron jobs) already goes through it, so a route can only name a seat that could
  exist, and `factory/seat` stays a usable key.
- **Cost as `CostMicros`.** The contract says "cost in US dollars (nullable)"; the model forbids a bare decimal, so
  millionths of a dollar as a `bigint` is the right translation. The route must show `costUsd`, as the description
  says.
- **Stores are not registered yet.** The routes pull request must register each store once per process (the lock is
  per instance). Two instances in one process would still be correct, because the unique indexes decide, as mutant B
  shows.
- **History ordering at an identical instant.** `History` orders by `AtUtc` then `VersionAfter` descending.
  Channel and mode rows carry a null `VersionAfter`; PostgreSQL sorts nulls first in a descending order and SQLite
  sorts them last, so a channel change and a rules change made at the same instant come back in a different order on
  the two databases. With real clocks it will not happen; with an injected clock in a test it could surprise.
- **The stale sentence when the caller is ahead.** A save made on version 7 when the newest is 3 is refused as
  "made on version 7 and the newest is now version 3". Nothing is written, which is what matters.
- **Public-repository rule.** Every address in the diff is `email@devthrottle.com` or on `example.com`,
  `example.org`, `example.net` or a `.example` domain. `*@devthrottle.com` appears once as a deliberately bad input
  to the address check; it is the allowed domain, not an owner's second address or a real sender. The only two
  tool names a word search finds in the diff are an existing agent-permission column of another table, repeated in
  every designer snapshot as every column is; they are not attribution.
- **A log line never carries a session's name.** Checked in all three stores: the lines log the kind and the id.
