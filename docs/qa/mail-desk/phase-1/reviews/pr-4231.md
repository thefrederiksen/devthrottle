# Mail Desk, phase 1: review of pull request 4231 (the Mail Desk routes on the Gateway)

Date: 18 October 2026. Mission: `docs/missions/mail-desk-2026-10-18/MISSION.md` (issue #4213), sections 5.6, 5.8
and 5.10. Binding contract: `docs/qa/mail-desk/phase-1/CONTRACT.md` on `origin/mail-desk-phase-1`, sections 4
and 5. The pull request merges `mail-desk-p1-routes` (head `1e492bd7e`) into `mail-desk-phase-1`, not main.

## Verdict

**Accept, with one low finding that does not block the merge.** The ten routes are the ten of contract section 5,
every one mapped into `MailDeskGate.Group`, and every one answers 404 with no body for an account that is off. The
session key guard admits exactly those ten shapes and nothing beside them. The caller decision moved into
`GatewayCaller` without changing what `FactoryDefinitionEndpoints` answers. Every refusal I traced returns before a
store is asked to write. Tenant isolation rests on the existing key-bound resolver and the stores' per-account
contexts, and the tests prove a second account sees and changes nothing. The fold decides `signedIn`, `lastCheck`
and `today` in one place, and the day boundary is right in a time zone that is not UTC, including the day the
clocks go back. The stale-save retry makes the one change again on the newest document and gives up with 409 after
three tries, recording only the rival's saves. Only `email@devthrottle.com` and reserved example domains appear;
no attribution to any tool or its maker anywhere in the diff, the commit or the pull request description.

F1: `GET /status` counts today's decisions only over channels that are still active, so on the day a channel is
removed its decisions drop out of the account's day total, and `/status` then disagrees with `/decisions`.

## What was looked at hardest

**1. The session key guard.** `IsMailDeskRoute` admits, under `/gateway/mail-desk`, exactly: GET of `status`,
`decisions`, `rules`, `channels` and `rules/history`; POST of `channels`, `channels/remove`, `channels/mode`, and
`rules/{anything}/add` or `/remove`. Segments are lower-cased before the match, so `/Gateway/Mail-Desk/...` is
matched the same way routing matches it. The `{anything}` in the rules path reaches only a route that answers 404
`no_such_list` for anything but the four lists. Called from the PUT block it always answers false, so no PUT is
opened. It cannot reach the admin route `/gateway/admin/mail-desk`, because the second segment there is `admin`. It
runs after the agent-input and smart-restart refusals, so it cannot widen either. It cannot reach another account:
the guard decides only the path, and the account is the one the key is bound to (`ResolveReadTenant` answers the
key's bound tenant or null, and null throws before any store is read). The tests check both directions: every
mapped route is admitted, and nine near-miss shapes are refused.

**2. `GatewayCaller` and `FactoryDefinitionEndpoints`.** Traced case by case against the code it replaced: a
person records `FleetManagerOwnerDevice.Caller(ctx)?.Actor` as before; a session the Gateway does not know is the
same 409 with the same body and the same log tag (`nameof(FactoryDefinitionEndpoints)`); a session in no factory
gets the same three-part caller; a factory's session compares the same trimmed factory name; the default is the
same `machine` kind with no identifier. `IsInAFactory ? Factory.Trim() : null` followed by `Factory is null` is the
old `!IsInAFactory` branch. The three other `KindOf` callers now call the shared one, which is the old body
unchanged. No behaviour change; the 1,253 tests above include every factory definition test.

**3. Every refusal records nothing.** In every change route the order is: account, author, body, why, then the
route's own checks, then the one store call. Every refusal returns before that call, and the stores' own refusals
(bad address, bad mode, already active, no such channel, invalid rules, stale) write nothing (review of 4222). The
tests compare a text of every Mail Desk row before and after each refusal, for the machine token, a session not yet
known, a factory's session on each channel change, a missing and a blank why on all eight kinds of change, every
bad channel body, a removal of something absent, an invalid rules change, an unknown list, and the switch off.

**4. Tenant isolation.** Covered under 1 for the account a key reaches. Inside the routes every store call passes
the resolved account, and `GET /decisions?channel=` resolves the address to channel ids through the same
per-account context, so it cannot match another account's channel of the same address. The isolation test adds the
same mailbox to a second account and proves each sees only its own, and that the second cannot remove the first's
channel or block entry.

**5. The fold.** `signedIn` is `unknown` with no Mail Desk start or no check yet, `failing` quoting the check's own
reason when the last outcome is `failed`, and `yes` for the four other outcomes, each of which means the check ran
and read the mailbox (`TriggerRunOutcome` has exactly five). `lastCheck` is null and null with the contract's
sentence when the factory is not published. `today` runs from local midnight to the next local midnight in the
account's zone, converted to UTC, counting by `DecidedUtc` in a half-open span; a zone whose midnight does not exist
starts at its first real minute. The tests pin 21:59 and 22:00 UTC as the two sides of midnight in Copenhagen, the
25-hour day the clocks go back, and a count that is 2 in Copenhagen and 1 in UTC for the same three decisions.

**6. The stale-save retry.** On `Stale` the route reads the newest document again and makes its change on that, at
most three times; on `Invalid` from the store it answers 400; any other outcome throws rather than guessing. The
tests put a rival writer between the read and the save: once (the change lands as version 2 on top of the rival's
version 1, and both entries are there) and every time (409 `rules_conflict`, three rival versions, and every change
row is the rival's).

**7. Tests that would fail if the code were wrong.** The ones above assert exact statuses, error words, recorded
rows and versions, not just "not 500". Each refusal test is paired with the same body succeeding with a why, so a
test cannot pass because the body was wrong for some other reason. The switch-off and guard tests enumerate the
mapped routes from the application itself and pin the count at 10, so a route added later without the gate or the
guard fails them.

**8. The public-repository rule and attribution.** Every address in the added lines is `email@devthrottle.com` (in
three spellings, to test case folding) or under `example.com`, `example.org`, `example.net` or a `.example` domain.
No tool or vendor name, trailer or footer in the diff, the commit message or the pull request description. A
session's name never reaches a log line: the logs carry the session id only.

## Findings

### F1 (low, does not block). `GET /status` drops a removed channel's decisions from today's account total

**Where:** `MailDeskEndpoints.Status`, `src/CcDirector.Gateway/Api/MailDeskEndpoints.cs:126`, which folds
`parts.Channels.List(tenant)`; `MailDeskChannelStore.List` defaults `includeRemoved` to false. The fold then sums
`today` over the rows it was given (`MailDeskChannelFold.cs:81`).

**What breaks.** The owner removes a channel at 12:00 after it decided 30 emails that morning, 4 of them junk.
Asked at 15:00, `GET /status` answers `today.total: 0` and `junk: 0`, while `GET /decisions?since=<local midnight>`
answers `total: 30` and `junk: 4`, and `GET /channels?all=true` shows the removed row with its 30. Two Gateway
answers to "how many emails were decided today" disagree, and the status view, the one `maildesk status` prints,
hides the junked mail the mission wants seen (section 5.8: "what went to Junk, every one, ... so a wrongly junked
email is seen"). Removal keeps a channel's decisions (section 5.8); the day's total should keep them too.

**Why it must change, and how small it is.** `today` in contract section 5 is the account's day, not the sum of the
rows shown. Count it over every channel of the account, removed ones included (or straight from
`CountsByChannel`, which already has every channel), while `channels` stays the active list. One test: decide on a
channel, remove it, and assert `/status` still counts the decision today.

## Observations, not findings

- `AddEntryAsync` and `RemoveEntryAsync` check the list name before the author, so the machine token naming an
  unknown list is answered 404 `no_such_list` rather than 403. Nothing is recorded either way; noted only so the
  order is known.
- `GET /rules` adds `savedByKind` beside the contract's `savedBy`. An extra field, harmless; the command line
  pull request can use it.
- With no Director ever reported for the account, a channel's machines are taken as given. Documented on `Parts`
  and deliberate; worth one sentence in the phase's record so phase 2 knows a misspelt machine can get in on a new
  account.

## Answers from the Developer

**F1: accepted.** Contract section 5 gives `GET /status` the account's day (`today: { date, timeZone, total,
byDecision }`), separate from each channel row's own `today`, and mission section 5.8 says removing a channel keeps
its decisions. Summing only the rows shown let a channel removed at noon take its morning's decisions out of the day,
including the junked mail the 08:00 email and `maildesk status` exist to make visible. The account's day must agree
with `GET /decisions` for the same span.

**What changed:**

- `src/CcDirector.Gateway/MailDesk/MailDeskChannelFold.cs`, `Fold`: the day's total is now summed from
  `MailDeskDecisionStore.CountsByChannel`, which reads every channel of the account through the account's own
  context, removed ones included, instead of from the rows folded. The `channels` list on `/status` is unchanged and
  stays the active list; each row's own `today` is unchanged. The class comment, the `Fold` summary and the
  `MailDeskDay` summary now say the day is the whole account's.
- `src/CcDirector.Gateway.UnitTests/MailDesk/MailDeskEndpointTests.cs`, new test
  `Status_AChannelRemovedToday_StillCountsItsDecisionsInTheDayAndAgreesWithDecisions`: one channel junks one email
  and archives one, a second channel archives one, the first is removed; `/status` lists only the second channel,
  counts 3 today (1 junk, 2 archive), and matches `GET /decisions?since=<midnight>` on the total and the junk count.
  Run against the fold as it was at `1e492bd7e`, the test fails (expected 3, actual 1); with the change it passes.

**Tests run** (devlinux, this branch, with the change):
`dotnet test src/CcDirector.Gateway.UnitTests -p:EnableWindowsTargeting=true --filter
"FullyQualifiedName~MailDesk|FullyQualifiedName~FactoryDefinition|FullyQualifiedName~SessionKeyGuard"`:
**1,254 passed, 0 failed, 0 skipped** (the review's 1,253 plus the new test).

**The third observation, for phase 2:** while an account has never had a Director report in, `POST /channels` takes
the machines it is given as they are, so a misspelt machine name can be saved on a new account and its check will
then never run on any real machine; phase 2 should check a channel's machines again once the account's first
Director reports, or show the mismatch on the channel row.
