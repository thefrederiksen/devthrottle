- Every filter of `decisions`, `rules history`, `rules show` and `channel list` is sent to the Gateway as a query

## Findings

### F1. `channel remove` and `mode` report success from the wrong field, so an unchanged row is announced as a change

`_channel_changed` (`maildesk_ops.py` lines 420 to 427) confirms all three channel changes with
`axi_cli.confirmed(answer, ["address"], ...)`. For `channel add` that is the right proof: a 201 with a row that
carries the address. For the other two it is not. A removal is proved by `removedUtc` being set; a mode change is
proved by `mode` being the mode that was asked for. The address is present on every channel row, changed or not.

I ran both commands against a Gateway that answers 200 with the channel row unchanged (`mode` still `observe`,
`removedUtc` null). The command printed, with exit 0:

```
Mode change of channel email@devthrottle.com recorded.
channel[1]{address,mode,mode-label,signed-in,last-check,today,machines,provider}:
  email@devthrottle.com,observe,"Observe - decides and records, changes nothing",x,y,0,devlinux,outlook

Removal of channel email@devthrottle.com recorded.
channel[1]{address,mode,mode-label,signed-in,last-check,today,machines,provider,removed}:
  email@devthrottle.com,observe,"Observe - decides and records, changes nothing",x,y,0,devlinux,outlook,
```

The first line of each is the command's own verdict, and it contradicts the row under it. An agent reads the
first line. The `confirmed` helper exists exactly so that "a change is reported from what the Gateway ANSWERED,
never from what was asked", and the repository's own precedent uses its `accept` argument for this: the session
rename compares the answered name with the requested one, hold and raise accept only the expected boolean
(`session_ops.py` lines 643, 667, 785, 855). This matters more here than for a rename: `mode live` is the one
command that turns the Mail Desk from recording to acting on a mailbox (mission 5.8, contract section 4, "person
only"), so "Mode change recorded" must be true when it is printed.

No test would catch this: `test_mode_PostsAddressModeAndWhy` and `test_channel_remove_PostsAddressAndWhy` have the
fake answer the changed row, and `test_change_AnswerWithoutVersion_IsNotReportedAsSaved` covers only the rules
path. A test that answers the unchanged row passes on the current code.

What must change: confirm the removal on `removedUtc` (present and not null) and the mode change on `mode` with
`accept=lambda v: v == new_mode`, and add the two tests that answer an unchanged row and expect exit 1 with no
"recorded" sentence.

### F2. No test proves the session key is sent, where the sibling command groups' tests do

The fake Gateway in `test_maildesk_ops.py` discards the `headers` argument, so no test asserts the
`Authorization: Bearer <session key>` header. The factory command tests record it and assert it
(`test_factory_ops.py` line 107, and the definition, record, brief and memory tests likewise). If a change to
`MailDeskClient._request` dropped or misnamed the header, every maildesk test would stay green and every real
call would fail with the Gateway's 401. There is no tenant leak in that failure, which is why this is minor; it
is a gap against the repository's own test convention for a client that carries the one credential tenant
scoping rests on. What must change: record `headers` in the fake and assert the bearer value in one request test.

## Observations, not findings

- `decisions` prints its `by-decision:` line without the `_line` escape that `status` applies to the same text.
  The keys are the Gateway's fixed vocabulary and ASCII today, so nothing breaks; it is only the one unescaped
  line in the module.
- A Gateway built before these routes exist answers a POST to an unknown path with a bodyless 404 the same way
  the switch does, so until the routes pull request is deployed `channel add` would say "Mail Desk is not switched
  on for this account". That is the contract's own reading of a bodyless 404 and the practical meaning is the
  same (nothing happened); noted so the deploy order is known.
