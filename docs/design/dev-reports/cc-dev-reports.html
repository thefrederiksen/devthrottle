cc-dev-reports: answer the agent inside the report

16 September 2026 Tracking issue: #2936 Decided - ready to build Nothing built yet

How to read this: the summary and the questions section are all you need. Stop there. Everything after is detail for whoever builds it.

Executive summary

  • Whatcc-dev-reports: every report an agent writes for its owner is one HTML file. The owner reads it in the Director, the Cockpit or the phone, and answers inside the page. Notes and answers go straight into the session that wrote it.
  • WhyToday a report is answered by typing in chat ("the third row of the second table is wrong"). Here the owner clicks the row and types. Decisions become buttons.
  • ShapeEvery report has the same top: summary first, questions second, detail after. A simple report is finished in the first screen.
  • CreditThe idea comes from lavish-axi by Kun Chen (MIT licence), which we tried on Windows 11. We take its in-page notes, the reply shown in the page, notes that are never lost, and its report-writing guides. We leave its local web server, its endless waiting command and its network defaults.
  • HowOne shared script inside the page does the note-taking. The Gateway keeps each report and its conversation. The three apps only display it. One tool (cc-dev-reports) and one skill (dev-reports) teach every agent in every repo to use it.
  • BuildFive phases, each usable on its own. Cockpit and phone come first; phase 3 is the first point where the owner answers from the phone.

1The loop

The whole feature is one circle. The agent never waits for the owner: answers arrive in the session like any other prompt. If the agent is in the middle of a turn, the notes are held and delivered when the turn ends, and the report shows "delivered when the agent finishes".

What a note carries, as seen in the lavish-axi trial: the text typed, the exact place in the page, the quoted text, and for a table the row and column names. The agent never has to guess what "this" means. Answers to questions carry the question and the chosen option.

2The report shape

Every dev report follows one order. The skill teaches it and cc-dev-reports open checks it.

The rules

  • Summary, then questions, always at the top. Nothing goes above them.
  • If there are no questions, the section still appears and says "No questions - nothing needed from you."
  • Every question names the decision, the options with their cost, and one recommendation, preselected.
  • Once answered, the agent removes the question and writes the decision into the body. Old questions never pile up.
  • The status line says what the report is waiting for: Waiting on you Agent working Done.
  • Pictures instead of paragraphs where a picture is clearer: hand-drawn SVG with a label on every part, so the owner can click the exact box they mean.
  • The last section says plainly what is not proven.

3One mechanism, three apps

Only the note-taking script is written once. Each app shows the report in a locked-down frame, adds the script, and passes notes to the Gateway. Session content already travels this way: the phone's Terminal and Chat tabs show sessions that run on a Director. In version one only the owner of the session can open or answer its reports.

4The tool and the skill

CommandWhat it does
cc-dev-reportsWith nothing else: this session's open reports and how many notes are waiting.
cc-dev-reports open <file>Checks the shape (summary and questions at the top), publishes the report for this session, prints where to view it. Run again after every edit.
cc-dev-reports reply "<text>"Shows the agent's answer in the report's conversation.
cc-dev-reports notes <file>Shows notes already delivered, if the agent needs them again.
cc-dev-reports guide [kind]Writing guidance: plan, comparison, table, diagram, decision.

The tool follows our AXI standard: compact output, a next_step line on every answer, and errors with a code and a fix. An unknown flag is an error, and no command ever waits forever.

The skill dev-reports says: any page written for the owner to read or answer is a dev report; run cc-dev-reports guide before writing one; summary and questions go at the top; open it with cc-dev-reports open. An agent never uses its own built-in way of publishing pages to a vendor's website for a dev report. That rule also goes into the owner's global agent instructions, because a skill alone does not reliably override an agent's built-in behaviour.

5What we take from lavish-axi, and what we leave

Take

  • Notes pinned to an element, text or table cell, with human labels
  • Questions answered with buttons; one Queue per question, nothing sent until the owner says so
  • "Queued" shown separately from "sent"
  • The agent's reply shown in the page
  • Reload after an edit keeps the reader's place and any half-typed note
  • Notes kept until delivered
  • A locked-down frame around agent-written HTML
  • Report-writing guides, rewritten for our reports

Leave

  • A web server on each PC. The Gateway and our apps replace it
  • A command that waits for feedback with no end
  • Phone access by opening the review server to a private network without sign-in
  • Usage analytics
  • Publishing to a third-party host
  • Editable diagram whiteboards. Maybe later; not needed for reports

6Build order

  1. The note-taking script and the report shape. Works on a plain file in a browser. Includes the shape check.
  2. The Gateway report record and delivery into the session. Publish, store, hold notes until the turn ends, deliver as a prompt, reply. Owner-only access.
  3. Cockpit and phone viewer. First point where the owner answers from the phone.
  4. Director pane, built on the existing HTML viewer.
  5. The tool, the skill and the global instruction rule rolled out to every repo. The tool exists from phase 2; this is when it becomes the default everywhere.

8Evidence, and what is not proven

Proven

  • lavish-axi 0.1.69 was run on Windows 11 against one of our HTML QA reports: a note on a table cell and a chat message reached the agent with the row and column names, and the agent's reply appeared in the page.
  • The Director uses WebView2 and has HtmlViewerControl, which opens a local HTML file (src/CcDirector.Avalonia/Controls/HtmlViewerControl.axaml.cs).
  • The report-writing rules here draw on the lavish-axi plan, input, comparison and diagram guides.

Not proven

  • How the Gateway stores and forwards report files. Not designed yet; phase 2.
  • That the Director's viewer can host a locked-down frame and pass messages out. WebView2 can; our code does not do it yet.
  • Whether the Cockpit or phone already has anything like a report view. Not checked.
