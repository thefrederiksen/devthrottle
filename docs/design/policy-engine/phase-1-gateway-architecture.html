Policy enforcement, phase one: everything the Gateway can do on its own

2026-09-19  |  Policy Engine mission  |  Phase one is Gateway-only and needs no change to any agent. Phase two adds the per-agent hooks. Every claim about our own code below was read from the main branch, and section 7 says what I did not prove.

Executive summary

Almost all of it can be done on the Gateway, and one piece of it is stronger than I expected. I checked your premise in the code first. One half of it needs correcting and the correction works in our favour.

The correction. The Director does not send the terminal to the Gateway all the time. The live byte stream only exists while somebody is watching a terminal, and it is paced by that viewer. What the Gateway gets continuously is session state. But the Gateway can pull any session's screen or terminal buffer at any moment over the tunnel, mid-turn, with no Director change at all - and it already does, in three different places. So you get the capability you wanted; it is a read we choose to make rather than a feed we receive, which means sampling cadence is a cost we design, not a free gift.

The stronger piece. Session creation goes through the Gateway carrying a BypassPermissions flag and the agent's launch arguments. A policy that refuses a bypassed launch forces every agent in the fleet to keep its own permission prompt. That prompt shows the proposed action before it runs, on a screen we already know how to read, in a state we are already told about. That is a real preventive gate, mid-turn, on every agent, with no hooks. It is the single best thing in phase one and I did not see it until I read the create path.

So phase one has six gates, four of which genuinely prevent. It reuses the supervisor's engine shape, the rules engine's dry-run promotion and recorded firings, the Wingman's model, and the governance audit log. Phase two replaces one gate's implementation with a per-agent hook; it is not a new architecture.

The one thing phase one cannot do is stop a tool that a bypassed or auto-approving session launches. There it detects and stops what comes next, and it says so in those words rather than pretending otherwise.

What I need from you

1. Should a policy be able to refuse a session launched with permissions bypassed?

This is what turns the agent's own permission prompt into our gate on every agent, with no hook work. The cost is that a team with a strict policy loses the unattended speed of a bypassed run, so the policy has to be theirs to set rather than ours to impose.

2. Should phase one watch mid-turn, or only at turn end?

Mid-turn sampling is the only thing that catches a bypassed or auto-approving session before the turn finishes, and it is what lets us interrupt. It costs one tunnel read per sample per working session, and a cheap model call only on samples the pattern pass cannot settle. Turn-end only is free but always late.

3. Should the small model judge every incoming prompt?

This is the open question from earlier today. Patterns catch what has a shape - keys, card numbers, identifiers. A password typed as prose has no shape, so if the model only runs after a pattern hits, it never sees the case it exists for.

2. What I checked, and where your premise needed correcting

You said the Gateway is sent the terminal all the time. Half right, and the half that is wrong matters for cost, so here it is precisely.

What I expected to findWhat the code actually says

The consequence. You get what you wanted - the Gateway can look at any session's terminal at any moment, including mid-turn. It is a read we choose to make, not a feed we are given, so how often we look is a cost we design. That is a better position than an always-on feed anyway: an always-on feed would put every customer's terminal bytes through our server whether any policy needed them or not.

Why G1 and G2 together are the interesting part

On their own, each looks minor. Together they are the whole phase.

Every agent we drive has its own permission prompt. That prompt is a moment where the agent has decided to do something and has not yet done it, and it puts the proposed action on the screen. We are already told when a session enters that state, and we already know how to read that screen without a model.

The only thing that removes that moment is launching the agent with its prompting turned off - and that is a flag on the create request we already see. So:

A policy that says "never launch with permissions bypassed" converts every agent's own prompt into our enforcement point. We do not have to build an interception. We have to refuse to throw away the one the agent already gives us. That is phase one's answer to "how do we stop the agent mid-turn", and it needs nothing from any agent vendor.

It is not free: a bypassed run is faster and quieter, and some unattended work wants exactly that. Which is why it must be a policy a team sets, visible on the tab, and not a rule we impose - that is question 1.

What G4 honestly is

G4 is the gate that catches what the others miss: a session a team deliberately allowed to run bypassed, a tool the agent auto-approved, personal data appearing in output nobody proposed. It reads new bytes since a cursor, so each sample carries only what is new.

It is detect-then-stop, not prevent. By the time a command's output is in the buffer, the command ran. What G4 can do is stop the next thing - and that is worth more than it sounds, because the damage pattern we actually care about is rarely one command. It is a session that has started doing the wrong thing and will keep doing it for twenty minutes. And for a data rule it is close to fully preventive anyway, because the leak only matters when it is stored or sent, and G6 stands in front of both.

4. One engine, six entry points

All six gates call the same five-step path. Only step four differs between them.

  1. Resolve the policy set for this company, team, agent and session, tightening only.
  2. Detect: patterns first, because they are free, instant and answerable; the small model second, and only for what patterns cannot describe. The model call is spotlit against injection, structured, and fails closed.
  3. Compose: declaration order, a refusal short-circuits, an ask is remembered and can still be overtaken by a later refusal.
  4. Enforce with the strongest action this gate actually has. A policy states what it wants; the gate states what it can do; the engine resolves the two and the answer is part of the verdict.
  5. Record, always, including allow - the gate, the detector that answered, the level the policy came from, and the person answerable for it.
The structural idea worth keeping. A policy does not say "block". It says what it wants, and each gate reports what it could do about it. So one rule resolves to blocked at G1, G3 and G6, asked at G2, warn-only at G4 and G5 - and the Governance tab shows exactly that. The honesty about stopping some things and only warning about others stops being a caveat in a sales conversation and becomes a computed property on a screen. It is also the table that later shows what phase two would upgrade.

The genuinely new parts are small: the policy store and its four levels, the composition, the per-gate capability resolution, the sampling loop behind G4, and the tab.

6. Phase two, so the seam is designed now

Phase two adds the agent's own pre-tool hook, answered by the Gateway - which is exactly what the competitor does for wrapped command-line agents, using the agent vendor's published contract rather than anything exotic. It changes one gate's implementation: G4 stops being detect-then-stop for tool calls and becomes prevent, per agent.

So G4 should be built with two implementations behind one gate from the start - the sampler now, the hook later - and the tab should display which one a given agent is getting. Phase two then ships per agent, visibly, and a manager watches the coverage improve instead of being told it did.

7. What I have not proven

  • Sampling cost at fleet scale. I have not measured what a terminal buffer read costs per session per sample, nor what a realistic cadence does to a busy Director. The design assumes it is cheap because the read is incremental from a cursor and the pattern pass is free. That assumption needs a measurement before G4's cadence is chosen, and it is the number most likely to change the shape.
  • That every agent we drive actually has a permission prompt we can read. I checked the mechanism and the state exist and that three parts of the product already read screens this way. I have not gone agent by agent and confirmed the prompt is recognisable on each of the nine. That is a short, concrete piece of work and it decides how much of the fleet G2 really covers.
  • Latency on the prompt gate. A model call in front of every prompt is one call before a turn that costs far more - but I have not measured the added wait as a person experiences it when dictating.
  • Nothing here has been built or tested. Every claim about our own code is a read of the main branch, not a running system.
