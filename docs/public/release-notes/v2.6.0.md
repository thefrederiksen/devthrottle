# DevThrottle v2.6.0

A message from one session no longer interrupts the session it is sent to. It waits in an inbox, and the
session is told about it only after it has finished what it was doing and has nothing half-typed on screen.

## A message is a record, not an interruption

`cc-devthrottle message send` places the message in the other session's inbox and answers `queued`. Nothing is
typed into that session at the moment you send. The session reads its messages in full with
`cc-devthrottle message inbox`, which marks them read.

- A session may message only the session that started it and the sessions it started. Anyone else is refused,
  with the reason said out loud.
- Six messages an hour per sender, one per recipient every ten minutes, and an exact duplicate that is still
  unread is dropped instead of queued.
- No session can type into another session by any other route either. Prompts, interrupts, Escape, fan-out,
  compaction follow-ups and verdict answers are all refused to a session that asks on another session's behalf.

## The doorbell

When a session has finished its turn and its composer is genuinely empty, the Director types one fixed line and
presses Enter once:

```
[DevThrottle doorbell] 3 fleet messages are waiting for you. To read, run: cc-devthrottle message inbox
```

- The composer is read off the screen, with a last look immediately before the first keystroke. If anything you
  typed is sitting there - even three spaces - the doorbell does not ring and waits for the next opportunity.
  It also waits while you are dictating.
- Nothing the product typed is ever erased. If the Director cannot verify that the line went in cleanly, it
  leaves it alone, tells the sender the message is parked, and you clear it yourself.
- A message nobody has read is rung again after five minutes, and after three unanswered rings it is marked
  stuck and the sender is told.

## Ask for a reply without waiting for one

`cc-devthrottle message send --reply-wanted` asks for an answer, and `--reply-by` sets a deadline. The other
session answers with `cc-devthrottle message reply`, and the answer turns up in your inbox. If the deadline
passes with no answer, you are told once. Nothing blocks while it waits.

## Every screen says what is waiting

Each session row now carries a line about its inbox - "2 messages waiting", or "1 message stuck, unread for 20
minutes". The Gateway works out the words once, and the Director's session list, the Cockpit and the phone all
show the same sentence.

## A message never wakes a session you parked

If you have snoozed a session, a doorbell - or anything else the product sends - leaves that snooze armed. Your
own typing still ends it. A snooze is your wish to be left alone, and another session ringing must not undo it.

## Restoring a Director's sessions is now the Director's own act

Because a session may no longer start a session owned by somebody else, the restore step of a Director restart
moved to the Director itself. The new `cc-devthrottle director restore` asks the Director to bring the drained
seats back, and the Director does the starting:

- Who owns each restored session comes only from what was captured when the Director was drained, so nobody can
  change it on the way through.
- Only seats that were actually drained come back, each one starts at most once, and a seat whose owner is not
  running is reported as failed rather than started under a dead owner.
- One Director holds a workspace at a time, and only that Director can write what happened to it.

The `director-restart` skill has been reworded to match.

## `cc-devthrottle message ask` has been removed

It blocked the asking session for up to two minutes waiting for the other side. Ask with
`message send --reply-wanted` and read the answer in your inbox instead.

## What this does not do yet

- The doorbell is typed only into the two agents whose screens the Director can read. Messages to any other
  agent wait in the inbox until that session reads them, are never marked stuck, and show on the session row as
  waiting.
- There is a gap of milliseconds between the Director's last look at the screen and its first keystroke, in
  which the session could start a turn on its own. The worst case is that one short fixed line queues behind the
  work already running. No text of yours is lost.
- A message is marked read just before its text is sent back. If the connection drops in between,
  `cc-devthrottle message inbox --all` brings it back for 24 hours, but you have to ask for it.
- Not exercised yet: a hosted Gateway serving more than one account at once, and a live Director restart using
  the new restore.

## Passwords your sessions use but never see

cc-secrets is a tool in the shipped toolbelt. You add a secret by hand on each machine, and a session can then
use it without the secret ever reaching the model:

- `cc-secrets run` starts a command with the secret supplied on its input, in an environment variable, or to a
  password prompt, and removes every recognisable form of the secret from what comes back.
- `cc-secrets login` fills a login form in a browser profile the Director owns, after checking the page is on
  the site the secret belongs to.
- `cc-secrets import` moves a whole credentials file into the store, one entry per line, without printing any
  value. `run --with` hands several entries to one command at once.
- Values that are not secret, such as a host or an email address, can be stored as settings beside the secrets
  (`add --setting`, `import --settings`). `cc-secrets get` prints a setting; a secret is never printed.
- `cc-secrets edit` changes an entry's user name, allowed site addresses, uses or agent access without
  re-entering its secret.
- Adding, editing, removing and importing are for you only and are refused inside a session.
- The store is one file per user per machine, readable by that user alone. Every use checks this, and on macOS
  it also checks access control lists and refuses drives that ignore file ownership.
- Every use is written to an audit log, which never contains the secret.

It runs on Windows, macOS and Linux.

## Linux: an app menu entry, and updates that work

- Installing on Linux now adds DevThrottle to the app menu, with its icon, so there is something to click. The
  command-line install finishes cleanly instead of failing at the last step, and uninstall removes the entry.
- A Linux Director now checks for updates, downloads its own build, and can install it. Before this release the
  check stopped before asking GitHub and reported "up to date" every time.

## Also in this release

- The Cockpit has a Wingman tab on each session: every stop the Wingman judged, with the outcome, the colour it
  produced at the time, and why.
- A session with work still running underneath it is no longer turned red for being quiet, and a red the Wingman
  wrote for that reason is taken back.
- The Wingman no longer invents a menu that is not on screen, so it never tells you to press a button that does
  not exist.
- The `cc-devthrottle` command line is easier for agents to use: lists show full identifiers, names and paths
  instead of cutting them short, filters work the same with `--json`, empty results say `count: 0`, running it
  with no arguments shows the live state, and a wrong flag fails with the valid choices listed.
- Dictation: the ready sound no longer ends up in the transcribed audio, the recorder keeps listening for a
  quarter of a second after you press Send or Pause so your last word is not cut off, and the time the
  microphone took to start is logged and shown.
- The stored raw transcript is the speech model's full output on every path, as the transcription rules require.
- The Fleet Map draws the same ownership tree as the Sessions list, across machines, so a session started from
  another machine shows under the session that owns it.
- The Fleet Map keeps a colour legend on screen, and hovering a session dot now gives the same words as its
  colour. The Missions board no longer says "needs you" under a session that does not need you.
- Voice narration is no longer silenced when a verdict check fails, and the Wingman now narrates every stop of a
  session that answers to you, not only in voice mode. The narration is saved with the verdict and shown in the
  Wingman panel. An account without a Pro plan is told that a full narration needs one, instead of waiting for a
  narration that cannot be written.
- The Wingman now judges sessions owned by a Fleet Manager session, so the Fleet Manager can act on its
  verdicts. Those sessions are still never read aloud to you.
- Each session has a Reports tab in the Cockpit and on the phone. When a session files a report about its own
  work, you can read it there and write back, and what you write is delivered into that session word for word.
- On Windows, the Director prepares a spare Director slot in the background the first time it starts after
  updating. No reinstall is needed.
