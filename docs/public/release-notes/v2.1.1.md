# DevThrottle v2.1.1

A release about what the Director does when the machine it is running on runs short of memory. Until
now it did three unhelpful things at once, and the worst of them quietly deleted what you had typed.

## Your typed words are no longer deleted because the machine was slow

When the Director sends a prompt to a session, it types the text and then waits for the agent's
terminal to echo it back before pressing Enter. That check exists for a good reason: without it, an
Enter pressed mid-repaint gets swallowed and your prompt sits in the composer unsent.

The wait was four seconds, fixed. On a machine that is short of memory and paging, a terminal can
genuinely take longer than that to repaint - so the Director concluded the terminal was broken,
pressed Escape **over the text you had just typed**, retyped it, waited again, and then gave up and
threw the prompt away. On one machine running eighteen sessions this destroyed thirty prompts in a
single run.

Three things change, and all three only take effect when the machine is **measurably** short of
memory:

- **The Director now reads how much memory the machine actually has.** Nothing in it ever did before,
  so none of its deadlines could tell "the other end is broken" from "this machine did not get a
  turn to run".
- **The wait gets longer when memory is short**, instead of the terminal being declared broken.
- **The composer is never cleared on a guess.** Clearing now needs positive evidence that your text
  is genuinely not there. If the Director cannot see the screen, or the machine is paging and the
  screen may simply be frozen, it keeps your words and tells you so - they stay visible on screen
  where you can press Enter yourself.

If a send does give up without clearing, the next send to that session clears the composer first, so
two prompts can never run together as one instruction you never gave.

**On a machine with memory to spare, none of this changes anything.** The behaviour is exactly what
it was, deliberately so.

## Sessions on a busy machine are less likely to go unreachable

Every session permanently occupies two of the Director's background worker threads for its whole life
- one reading its terminal, one waiting for it to exit. With a dozen or more sessions open, those
threads are all taken, and the regular signal that tells the Gateway "this Director is still here"
had to queue behind them. Miss enough of those and the Gateway concludes the Director is gone: the
sessions are still running perfectly well on your machine, but you cannot reach them from the Cockpit
or your phone.

The Director now reserves enough worker capacity at startup for the sessions it is carrying, so that
signal is not stuck in a queue behind them.

**This makes the failure less likely; it does not make it impossible.** If a machine is short enough
of memory that the operating system is swapping the Director itself out, no amount of thread
budgeting will get a signal out on time. The honest summary is that this removes one cause, not the
whole problem. If your machine is genuinely out of memory, the fix is fewer sessions on it - or more
memory.

## When something does go wrong, the log says what was actually measured

The Director's log lines about late or skipped updates now carry the machine's memory reading at the
time, and a late update reports how late it was against its schedule rather than only how long its
own work took - a report that could previously look perfectly healthy while sessions were
unreachable.

These lines deliberately stop short of blaming memory for a stall, and stop short of claiming your
sessions were unreachable, because the Director cannot see enough from its side to know either for
certain. They report what was measured and say plainly what cannot be concluded from it.

## Also in this release

- A small memory leak on macOS, in the new memory reading itself, found in review before it shipped.
- On a machine whose memory cannot be read at all, every deadline stays exactly where it was. An
  unknown reading is never treated as either good news or bad.
