# DevThrottle v2.7.2

Two fixes to the cc-* command line tools. The Tools board stops reporting a working tool as broken, and
every Director on a machine now uses the one installed copy of the tools instead of whichever copy
happened to be first on the path.

## The Tools board no longer reports cc-secrets as broken

The Director's home screen showed "NEEDS ATTENTION - DevThrottle tools - 9 pass, 1 fail - failing:
cc-secrets (version check: exit 2)". Nothing was wrong with cc-secrets. It stored secrets, ran commands
with them, and signed in to websites exactly as it always had.

The Tools page asks every tool it lists the same two questions: is the program where it should be, and
does `--version` answer. cc-secrets could answer the question only as a command, `cc-secrets version`,
and had never been given the `--version` flag that every other tool has. So the board asked, the tool
refused an option it had never heard of, and a healthy machine was told to go and fix something that was
not wrong. That is worse than a silent failure: it spends your attention on nothing, and it teaches you
to ignore the one banner that is supposed to mean something.

`cc-secrets --version` now answers and exits cleanly. The `version` command prints the same line from the
same place, so the two can never drift apart and give different answers to the same question. The flag
belongs to the tool rather than to its commands, so `cc-secrets list --version` remains the mistake it
always was.

If your board is showing this, it clears once this release has installed the tools and the Tools page has
looked again.

## One tools folder per machine

A machine is meant to have one installed copy of the cc-* tools, at the machine root, and every Director
on that machine is meant to use it. The repair that was supposed to keep it that way had the world the
wrong way round: it treated the machine's own copy as the outdated one, treated a copy inside a single
Director's folder as the right one, left every other Director's copy sitting on the path, and it only
ever ran when somebody pressed a button on the Tools page. A rule that is wrong and that nobody runs
repairs nothing.

It is now the right way round, and it runs at every Director start rather than waiting for a button. The
machine's copy is the one that answers. A copy inside a Director's own folder comes off the path,
including one whose folder has already been deleted and left an entry behind. A Director serving a
throwaway root of its own keeps its own tools, because that separation is what makes a test rig safe to
run. The installer follows the same rule, so putting the files at the machine root actually changes which
copy answers.

Nothing on your disk is deleted. A copy that has come off the path is still there; it simply no longer
answers a command.
