# DevThrottle v2.8.1

The superseded copies of the tools inside each Director's folder are now removed, not just taken off
the path - and the rules that decide what goes are written to keep anything they cannot prove is a
copy.

## The old tool copies are actually removed now

v2.8.0 stopped the extra copies answering your commands. It said, in as many words, "nothing on your
disk is deleted. A copy that has come off the path is still there; it simply no longer answers a
command." That was true, and it was half the job: the copies stayed, taking gigabytes, and the next
person to look at the folder had no way to tell a live install from a dead one.

This release finishes it. At every Director start, a copy that has been superseded is removed, and
the Tools page shows what went, what stayed, and the reason for each.

## What it will and will not remove

This deletes folders on your machine, so the rule it follows is worth stating exactly. **A folder is
removed only when every one of five things is positively true about it.** Not "when nothing looks
wrong" - each condition is a presence that has to be established, and anything that cannot be
established keeps the folder.

- It is directly inside a Director's own folder, or the machine root.
- Its name is one the product itself creates - the tools folder, the shared environment, the
  interpreter, or an interpreter left behind by a previous update.
- The machine's own installed copy is present and healthy. If the master copy is not there, nothing
  is swept anywhere, because then the copy in front of you might be the only one you have.
- No Director is running out of that folder. A folder whose state cannot be read, or that more than
  one live process claims, is left alone - not knowing is never permission.
- It is a real directory and not a link. A junction or a symbolic link is left exactly where it is,
  and what it points at is never looked at, never counted and never removed.

That last one is worth dwelling on, because it is the one that could have cost somebody real data. A
link is transparent to the file system calls a sweep like this uses: list a junction and you get the
contents of whatever is at the far end; delete through it and you destroy the real file, not the
link. So somebody short of disk space who had pointed a Director's tools folder at the machine's own
copy - exactly the thing a person does on a machine carrying several copies - would have had the
master destroyed seconds after the sweep confirmed it was healthy. Links are now refused at every
level: as a candidate, while walking into a folder, and while removing one.

Nothing is removed from a Director that is serving a throwaway root of its own, so a test rig is
still safe to run.

## Retired commands stop leaving broken launchers behind

Commands the product no longer ships used to leave a launcher behind in the tools folder. The
launcher pointed at a program that was not there any more, so running the command printed a message
saying the tools were not fully installed - on a machine where they were fully installed and working.

Those leftovers are now removed, and the list of names covers every command the product has retired
rather than the handful it happened to list before. A launcher is only removed when its contents are
the product's own, written in the product's own form. One you wrote yourself, pointing wherever you
chose, is left alone even when it carries the same name.

## Also in this release: the disk tool now recommends what to remove

`cc-cleanup-storage` arrived in v2.8.0 able only to look. It can now recommend, with a `recommend`
command beside `scan` and `report`. It still removes nothing itself.

A rule may offer something for removal only when it holds one of exactly three proofs: a record the
system itself keeps says nothing needs it any more, or the tool that created the data has its own
command for clearing it, or we made it, under a name we know exactly, and it is old and finished
with. There is no fourth kind of reason, and a pattern borrowed from somebody else's cleanup product
is not one.

Anything no rule matched is reported as unclassified and is never offered. On the machine this was
built on that is 596 gigabytes left untouched, which is the intended outcome rather than a gap to be
closed by relaxing a rule.

A rule that cannot do its job says so instead of reporting a clean disk. A rule comparing against a
system record that failed to load would otherwise find nothing every time and look exactly like
having nothing to find - and for installer packages in particular it would mark the entire Windows
package cache as orphaned, which would leave the machine unable to repair or uninstall anything.
Six rules ship for Windows; the largest finding on the machine it was built on was 26.6 gigabytes of
orphaned installer packages.
