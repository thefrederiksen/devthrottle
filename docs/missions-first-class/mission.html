4. Decisions

  • A Mission is not forced. No Mission means a yellow warning, never a refusal. (Your words: "We don't want to force a mission.")
  • The mission document is a dev report stored on the Gateway. (Your words: "Mission is a dev report that's stored on the gateway.")
  • The goal is the one the mission document already describes, not a new idea. (Your words: "the goal is already described in our reports.")
  • With a Mission the colour is calm, not the Cockpit green, not orange.
  • Answered 6 November 2026, all as recommended. Go given the same day.
  • The document link: the Mission record holds its document's report id, set by publishing with cc-dev-reports open mission.html --mission-document. Republishing updates the same link. One document per Mission, and the link outlives the Architect's session.
  • The goal: read from the document itself. A mission document marks its why and goal sections (data-dev-report="why", data-dev-report="goal"). On publish, the Gateway reads them and stamps them on the Mission.
  • The colour: indigo, #4338CA. No mission: yellow.
  • The corner button: shows the selected session's Mission, beside the toolbar Cockpit button. It shows the Mission name and opens its document, or yellow "No mission". The session tab bar gets the plain Mission button beside its own Cockpit button.
  • The 18 sessions with no Mission: left to session 103. This mission builds the buttons; it does not audit sessions.

The pieces, as decided:

  • Gateway - the Mission record gains the id of its mission document, plus its goal, read from the document. The why it already has is filled the same way. The Gateway works out the button's verdict once, from the session's state: "has a Mission with a document", "has a Mission but no document yet", or "no Mission". It also works out the button's label, colour key and tooltip. Clients render that verdict and decide nothing, as the client-is-dumb rule requires.
  • Gateway - dev reports learn the two new section markers, why and goal. They are optional for an ordinary report and expected in a mission document. Publishing with --mission-document links the report to the publishing session's Mission.
  • The command line: cc-dev-reports open --mission-document. cc-devthrottle mission list shows whether each Mission has a document.
  • Director: the Mission button beside TabBarCockpitButton, and the corner button beside BtnCockpit. Both open the report's /r/<id> address.
  • Skills: the dev-reports skill and the method's Architect section learn to publish the mission document with --mission-document, so every new Mission gets its link from the start. Both are built-in skills, so this ships with a Gateway deploy.

Out of scope: forcing a Mission on spawn. Changes to the Cockpit's missions board beyond showing whether a Mission has a document. Rewriting the documents of old Missions.

A question for a later phase, not now: the third verdict, "has a Mission but no document yet", probably wants its own look. I plan to draw it as the Mission colour with an outline only, and will show it in the phase 2 screenshot.
