Director and Gateway

One outbound stream · no ports · the read model · workspaces — how a machine and the Gateway talk

A Director opens exactly one connection - outbound - to the Gateway, and keeps it open. Everything flows over it. The Director exposes no network ports at all. The Gateway is the only reachable host in the system.

1. The one idea, and the invariants

The Director dials out and keeps one connection open. Raw state pushes up; commands and requests flow down; requests work in both directions; terminal bytes ride outbound byte streams the Director dials on demand.

Because the Director dials out, it needs no inbound firewall port, no port-forward and no per-machine network address. It works behind any NAT or firewall that allows outbound HTTPS - home, corporate, cellular, anywhere.

The invariants. These are the musts.

  1. The Director dials the Gateway. The Gateway never dials the Director. This is the whole point; it is what makes the Director portless.
  2. No Director ever talks to another Director. All cross-session messaging, fleet comms and remote viewing are relayed by the Gateway. If any Director-to-Director path survived, something would still have to be reachable and the benefit collapses.
  3. All remote access goes through the Gateway. A phone or another machine can only reach a Director by way of the Gateway.
  4. The Director has NO listener at all - not even loopback. See below; this is the one that changed.
  5. Who-initiates is not who-can-ask. One Director-initiated connection carries requests in both directions. The Gateway can ask the Director for history over the open stream. Portless forbids a new inbound connection, not the request-and-reply pattern.

Invariant 4 went further than the proposal - there is no loopback API either

The candidate document proposed keeping a loopback-only API on 127.0.0.1 for the local agent and the command-line tools, reasoning that it exposes no network port and so does not violate portless, and that local work would never depend on the Gateway being up.

That is not what shipped. The Remove-the-network-port mission deleted the Director's HTTP Control API outright - the web host, the loopback routes, and the port allocator that picked from the range 7879 to 7898. In the words of the class that used to host it:

THERE IS NO LISTENER HERE, AND THERE MUST NOT BE. [...] Everything an agent or another machine does to this Director arrives over the Gateway, down the tunnel this host dials OUT. Process lifecycle (stop, update check) is a named signal, not a route. If a change here needs a caller to reach this process directly, the answer is a tunnel verb or a file, never a socket.

The consequence the candidate wanted to avoid was accepted deliberately: local work now does depend on the Gateway. A command-line tool talking to a session on its own machine goes out to the Gateway and back. The trade was made because a second door is a second door even when it is only open to the local machine - and because "it is only loopback" is exactly the argument that keeps a port alive forever.

The class name ControlApiHost survives the listener it was named for, because it is referenced throughout the desktop, the tests and the documentation. What it hosts today is the Director's service plane. That is a naming debt, recorded here so the next reader does not go looking for an API.

2. What collapsed into the stream

Everything that used to be a separate Director-to-Gateway mechanism is now one channel.

BeforeNow
Register on start, over HTTPStream connect, with authentication in the handshake
Heartbeat every 15 seconds, pushed over HTTPStream keepalive plus a periodic full-snapshot reseed
Doorbell on change, best-effort HTTP pushA delta pushed up the stream
Gateway fans out and PULLS each Director on every client pollThe Gateway serves its own in-memory model. No fan-out.
Assessed state pushed down into the Director over HTTPA message down the stream
Commands: Gateway to Director over HTTP - needs an inbound portA message down the stream. No inbound port.
Terminal bytes: browser to Director directlyAn outbound byte stream the Director dials, relayed by the Gateway
History: the Gateway pulls the Director on demand - needs an inbound portA request down the stream; the Director answers up it

The transitional flag is GONE, and that matters more than it sounds. The stream shipped behind a gateway.streamMode gate with the whole HTTP path preserved beside it, so a Director behaved identically with the flag off. That dual-mode period is over: the Gateway Cleanup mission removed the gate, and a configured Gateway means the tunnel. There is one path now, not a preferred path with a fallback. A fallback that still exists is a fallback that will be taken, and the second path could only ever be taken in the situation nobody was testing.

3. Commands: one envelope, one executor

When commands moved onto the stream there was a choice: write a stream handler per verb beside each existing REST handler, or build one envelope both paths execute through. The second was chosen, and the reason is the reason this whole repository keeps re-learning: two implementations of one rule drift, and the drift is invisible until somebody hits the path nobody exercised.

So a command is a generic envelope - a verb, a session id, and a serialized payload - and a single shared executor runs it. The stream path and any other caller reach the same method, with the same guards, and cannot disagree.

DirectorCommand   { CommandId, Verb, SessionId, PayloadJson }
DirectorCommandResult { CommandId, Status, BodyJson, Error }

Status: Ok | BadRequest | NotFound | Conflict | Error

The result carries the outcome rather than an HTTP status, because the stream has no status codes. The common guards - parse the session id, find the session - live once in the executor rather than once per verb.

A command to a disconnected Director is REJECTED immediately, never queued. The Gateway resolves the Director's live connection; if there is none, the answer is "unreachable" now. A mutating command held in a queue would fire against a machine whose state has moved on, at a moment nobody is watching.

4. Recovery: reconnect is the same path as first connect

The Director is the source of truth. The Gateway is a disposable derived cache.

So the Gateway never "reacquires" - the Director re-asserts. Every attach, whether the first or the thousandth, begins by sending a full snapshot of every session's current facts; then deltas flow. No diffing, no gap replay. Nothing is lost because the durable truth - the terminal buffer, the transcript files, the raw facts - never left the Director.

A connection generation, not an integer epoch

A dying connection can deliver a message after its replacement has already attached, and that message would overwrite fresher state with staler state. Each attach therefore takes a monotonic generation, and the Gateway drops any message from an older one.

The first design was a simple integer epoch on the Director. It was replaced by a generation assigned per CONNECTION at the Gateway, because the Director is the one component that might have restarted - a counter that resets to zero on the very event the mechanism exists to survive is not a mechanism. Duplicate-connection ownership follows from the same fact: the newest generation owns the Director's entry, and an older connection still talking is ignored rather than fought with.

Removals travel as tombstones

A delta that only ever adds and updates cannot say "this session is gone", so a killed session would live forever in the Gateway's model until a full reseed happened to drop it. Removal is an explicit tombstone in the delta - the absence of a session is a fact that has to be SENT, not inferred from a list that no longer mentions it.

5. The Gateway read model

The roster serves last-known state, unconditionally. Age decides what the roster SAYS about a machine; it no longer decides whether the machine is on it.

The defect this replaced, because the shape recurs

The Gateway refused to serve any machine whose last push was older than twenty seconds. A Director re-pushes every ten seconds, so two missed ticks blanked a machine - every session, every colour - and with the tunnel dropping dozens of times a day the roster emptied several times an hour, while the Gateway sat holding the very data it had just refused to show.

There were three staleness authorities stacked in one path, which is the part worth remembering:

  1. The pushed store was read through a freshness check that returns nothing past its window, and that nothing was rendered as "unreachable, no sessions".
  2. The result was then handed to a roster cache that granted three poll cycles of grace and then declared the machine offline and dropped its sessions for good.
  3. Further out again, the registry swept a Director's entry sixty seconds after its last heartbeat, taking its cached sessions, its snooze rows and its session numbers with it.

The third one is why a partial fix would have looked like a whole one: restoring the read alone would have bought about a minute against a requirement of five.

Two methods, deliberately - and this is not a relaxation

ReadServesUsed by
GetLastKnown Whatever was last pushed, with its age reported alongside. The roster - reads that only DISPLAY. A stale row that says it is stale is better than a blank screen.
TryGetFresh Nothing at all once past the staleness window. Reads that ACT - session location for command routing, and every gate. Untouched, and it kept every one of its callers.

A read that ACTS must still refuse a stale answer, because acting on one could route a command at a machine that is no longer there. Displaying one merely needs to be honest about its age. Collapsing the two into a single "is it fresh?" question is what caused the defect.

Link state comes from the tunnel, not a countdown

onlineTunnel up and a current push.Yes
wobblyTunnel up, nothing recent.Yes
offlineTunnel down.Yes - this is the change

The roster cache was DELETED rather than bypassed. Its only production consumer was this one handler, and a second authority that can still be wired back in is a defect waiting to be re-introduced.

Session location reads the cache, because a pull is impossible

Finding which Director hosts a session used to be an HTTP pull against each Director. Under portless there is nothing to pull - so location reads the pushed cache instead. This is not an optimisation: the old path cannot run at all on a portless Director, and a location that silently failed would make a session unreachable rather than visibly absent. The push cache is therefore kept fresh specifically so location never needs a fallback that does not exist.

6. Workspaces live on the Gateway

A workspace is a named set of SEATS. A seat is a repository plus the agent, model, seat, mission, owner and opening prompt that make one session.

There are two ways to get one - authored by hand ("my morning fleet"), or captured from a running Director, which is exactly what a drain produces. And two ways to use one - started cold, which is the ordinary set-of-sessions case, or started with each seat seeded by its own handover, which is the restart case.

Those are the same object. The restart index written by hand during the first real drain, on 6 September 2026, already was a workspace with extra fields on it; a workspace is a restart index with the drain's judgments left blank. So one thing is stored, not two.

Why on the Gateway

The one moment a workspace is worth having is the moment the machine it describes has been restarted out from under its fleet. So it has to be readable when that machine is down, and editable from another computer. That is the whole reason it REPLACES the Director-local workspace files rather than sitting beside them: those were readable only while that machine was up and editable only at that keyboard.

Nothing on disk was lost in the move. The first time either dialog is opened, every legacy workspace file on the machine is pushed up and renamed aside. A file whose id is already on the Gateway leaves the Gateway's copy alone - that is the one people have been editing since - and a file that cannot be parsed keeps its own name so the bytes stay findable. With no Gateway configured the dialogs SAY so, rather than showing an empty list, which would read as the upgrade having deleted the user's saved work.

What happened to the Director and what happened to the seats are TWO facts

The hand-written index had one coarse word for both, and two of its values welded the pair into a single token: restored meant the Director was restarted AND the seats came back. So the first combination nobody happened to weld had no word at all - and that combination is not exotic. A drain that BLOCKS has already closed, leaf-first, every seat that handed over cleanly, so the expected result of never forcing is a half-gone fleet, with no restart, whose seats must then be brought back without one.

Three fixes were tried, and the first two each looked finished:

  1. A fifth value. It hid the same defect one case further out - the next case (restarted, restore only half complete) needs a sixth.
  2. Deriving the word from the pair. That stopped it CONTRADICTING them but still welded them: a refused restart and a session that would not stop both derive "blocked", which are the two most confusable results a run can have. The fix for that was a warning telling every future reader never to read the field alone - and a rule that must be obeyed forever by people who were not in the conversation is the weakest kind of fix there is.
  3. Deleting it, which is what shipped.
FieldValues
directorOutcomenot-restarted, restarted, restart-refused
seatOutcomerestoredCount, notRestoredCount, notRestoredWhy, and a scope DERIVED from the two counts: nothing-to-restore, none, some, all

scope has four values and not three for the same reason the pair exists at all: "nothing was owed" and "everything owed is missing" are a success and a total failure, and one word for both is the absence-shaped hazard in miniature - an empty restore list reading as success is how a run that restored nothing certifies itself. notRestoredWhy is REQUIRED whenever anything was not restored, because a missing seat with no reason beside it is indistinguishable from one nobody noticed.

The surface

GET    /gateway/workspaces        every workspace, newest first (summaries)
GET    /gateway/workspaces/{id}   the whole document
POST   /gateway/workspaces        CAPTURE: fold a Director's live sessions into a new one
PUT    /gateway/workspaces/{id}   store one (authored, or a captured one with judgments written on)
DELETE /gateway/workspaces/{id}   remove one

The document is stored as JSON in one column, with a few head columns projected from it for the list. That is deliberate: a workspace is a RECORD, its shape grew three whole blocks during the first real run, and it will grow again. Columns would make each of those a migration. A document written elsewhere that still carries a retired field keeps it verbatim in the unknown-field bag - not modelled, not obeyed, and not lost.

Capture is a verb rather than something the caller assembles, because the facts on a seat - the agent, the resolved seat, the owner, the model, the transcript path - are ones the Gateway holds firsthand, and this document is read after those sessions are gone, when nobody can check. It CREATES and never replaces: overwriting would destroy a drain somebody is halfway through, silently. And the capture makes no judgments - drain state, handover path, restore decision and the restore list are all left at their honest empty values, so a document nobody has judged yet cannot be mistaken for one that has been.

A session key may call all five. A session drives a drain, so a guard that let a session read workspaces but never write one would leave the record to a human at the keyboard of the machine being restarted - the one person the exercise exists to spare. Restarting the Director itself stays refused; that is the admission surface.

7. Consequences accepted, eyes open

Each of these was named before the model was built and is still true.

  • The Gateway is a single point of failure for REMOTE access. With no direct path, a Gateway that is down means no phone and no other machine can reach a Director at all.
  • The Gateway is in the byte data path. Bytes go Director, Gateway, browser rather than browser-direct. Measured load is small - single-digit kilobytes per second per watched session - but the Gateway now relays bytes, not just metadata.
  • Local work depends on the Gateway. Session-to-session messaging on ONE machine routes out to the Gateway and back. The candidate document expected loopback to spare us this; the loopback API was then removed, so this consequence is larger than it was written to be.

The connection indicator in the Director window is load-bearing under this model, and is the one signal for "is remote access working right now": healthy, reconnecting, or down. When the stream is down the desktop keeps rendering the one fact it owns firsthand - is this agent producing output - as blue or red, and nothing else. That floor is described in sessions.html, which owns every rule about colour.
