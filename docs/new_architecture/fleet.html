1. The Mission

A Mission is the named unit of work a group of sessions is collectively chartered to accomplish. Sessions ATTACH to a Mission, and that attachment - not the spawn tree - is what ties them together.

Why an object, and not just the spawn tree

The only relationship the fleet used to model was the spawn tree: X started Y. A tree can express strict hierarchy and nothing else. It cannot express "the Architect and the Manager are equals pointed at the same goal".

The Mission supplies the missing horizontal binding. An Architect, a Manager and Workers all attach to one Mission; the Architect and the Manager are peers BECAUSE they share a Mission, not because one started the other. That is what lets you rework a design with the Architect without stalling the running Manager - neither controls the other. Without a Mission object, "Architect beside Manager" has nothing to hang on and collapses back into a chain.

Role cardinality - one Architect, one Manager, N Workers

This is the shape the Mission object exists to make expressible. A spawn tree can only say "X started Y"; it cannot say the Architect and the Manager are equals pointed at one goal. They are peers BECAUSE they share a Mission, not because one started the other — which is what lets you rework a design with the Architect without stalling the running Manager.

SeatHow manyMandate
Architect Exactly one, optional The DESIGN authority. It recommends to the Manager and maintains the architecture documents. It does not drive implementation. Co-equal with the Manager on design; the Manager alone owns execution. A simple Mission can run with no Architect.
Manager Exactly one, required once work is delegated The coordinator. Owns the decomposition of the Mission into Tasks and the supervision of the Workers. How a Manager learns what its Workers are doing is a seat rule, defined in sessions.html section 4.
Worker N Does one Task. A Worker's job type - developer, quality assurance, and so on - is decided by the agent skill at runtime and is deliberately NOT encoded in the seat.

Never two Architects and never two Managers on one Mission - single design authority, single coordinator. This matches every serious system surveyed: Magentic-One's one Orchestrator, Anthropic's one lead agent, CrewAI's one manager in the hierarchical process.

The Architect is human-facing; what that means is defined in sessions.html section 4. The July text had been superseded for over a week and still read as current, so carrying it here unchanged would have re-taught a rule the owner had already thrown out.

What sizes a Mission: the goal, not the labor

A Mission is defined by its GOAL, not by how much work it takes or how many sessions do it (owner, 9 July 2026). A large goal does not become several Missions - it becomes ONE Mission with more Tasks and more Workers under the single Manager. A Manager scales by adding Workers, never by spawning peer Managers.

Labor size, or the fact that work spans several sessions, is NOT a reason to declare two Missions. That is a division of LABOR, which is what Tasks are for, not a division of MISSION.

Worked example from this project: "fix the session lifecycle" is ONE Mission. The plumbing - the role data, the schema, auto-naming - and the visible features - the role badge, the spawn command, attaching a session to a Mission - are TASKS inside it, even though different sessions built them.

Missions are FLAT - nesting was removed on 7 August 2026

Nesting was specified, built (Mission.ParentMissionId, a parent argument on create, parent validation on the route, and a tenant-scoping test for it) and then never used once. Every Mission the fleet ever created had a null parent. The owner dropped it on 7 August 2026.

Why remove it rather than leave it lying there. An unused field is not free. It has to be understood by everyone who reads the type, kept correct in every store and route that touches it, carried through every migration, and reasoned about by every feature built afterwards - and mission state, rename and numbering were all about to be built on top of it. It also widened the create route's attack surface for nothing: a parent is a caller-supplied reference INTO the mission set, so it needed its own tenant guard and its own test to prove another account's mission could not be named as one. Deleting the field deleted that whole class of question.

Two related missions today are simply two missions. If a real case for sub-Missions ever turns up, the reasoning above is the thing to restart from - and the tenant-scoping test comes back with it.

Mission state

A Mission is its OWN persisted record, not merely an attachment field on a session, so it survives a Manager restart. MissionStates: active, complete, removed. A record written before state existed reads as active. The command line carries mission create / list / rename / complete / remove / reopen.

Scope, and work that belongs to nobody

Surfaced from live use on 9 July 2026: work kept being routed to a Mission because its NAME sounded close, not because it was in scope. Two rules came out of it.

  1. A Mission has an explicit SCOPE - the written boundary of what it owns. Work is routed by SCOPE, never by name similarity. A Manager declining out-of-scope work is CORRECT behavior, not obstruction. The scope must be written down precisely so that routing is a reading rather than a guess at the name.
  2. Homeless work is ASSIGNED, never DEFAULTED. Cross-cutting work that no existing Mission owns - release, installer, self-update, deploy infrastructure - must be explicitly assigned its own Mission or a named owner, and must NEVER default onto the nearest-sounding Mission. A Manager that meets homeless work DECLINES and escalates the assignment question; it does not absorb it.

2. Attaching, moving and detaching

A Mission could originally only be joined in the instant a session was spawned. That made the feature miss the case it exists for: a mission's shape is DISCOVERED as it runs - that is what makes it a mission rather than a task - so attach-at-birth grouped only the work somebody had already planned, which is the work that least needs grouping.

The case that found it: a release push that began as one coordinating seat and grew over a day into about a dozen - an architect and a manager, three review seats, three more for a different question, an investigation seat, four independent gate reviewers commissioned one pull request at a time, and a session fixing a defect one of them found. All one body of work. None of it foreseeable at spawn. None of it representable.

cc-devthrottle mission attach <session> <mission>
cc-devthrottle mission detach <session>

The six rules, each decided rather than implied

Somebody hits every one of these, and an implied answer gets re-litigated at the worst moment.

  1. Attaching is a MOVE, not a one-way door. A session that already carries a mission is re-pointed by the same command. The first classification of a session is always a guess about work still taking shape, so a one-way attach would make every wrong guess permanent until the session was killed.
  2. The move is REPORTED. The command names the mission the session LEFT. A move that reports only its destination hides that anything was displaced, which is how a session goes missing from the pod somebody is looking at.
  3. Detaching is supported. No mission is the ORDINARY state of a session, so returning to it must not require inventing a mission to park the session in. A session that had no mission is told exactly that, rather than being told it was detached from nothing.
  4. A refused attach changes nothing. A mistyped mission id leaves an existing attachment intact - otherwise the failure looks like nothing happened until somebody goes looking for the pod.
  5. Attaching a controlling session does NOT bring its children by default; --with-children does. A supervisor routinely commissions work that is not part of its own mission, and a silent bulk re-parent cannot be undone in one step. With the flag the walk is TRANSITIVE - children, their children, and so on - because stopping at the first level would attach the Manager and leave the Workers behind, which reads as success while producing exactly the split view this feature exists to end. Every session it moves is NAMED, not counted.
  6. A spawned session INHERITS its supervisor's mission by default. The fleet already records the relationship, so this costs nothing and would have grouped the release push above for free. An explicit --mission wins (stated intent beats a default), --mission none is the opt-out, and the inheritance is never silent: the spawn names the mission, names the session it came from, and says how to undo it.

The workflow seat moves with the mission

A Mission is not only a record. It is also a RUN of the built-in mission workflow, and a mission-scoped spawn seats the session on that run. The seat - the run id plus the workflow id and its PINNED version - is what decides the conduct the agent was told to follow.

So the mission link and the seat are two halves of one fact. An attach that moved only the link would leave a session displayed under one mission while governed by the one it left, taking its conduct from a mission it is no longer in and still counted in that mission's participant ledger. That is worse than an inconsistent label, and it would happen in exactly the case this feature was built for. (Found by independent review of the first cut, which moved only the link.)

  • A seat that is a run of the mission being left follows it: on a move it becomes the destination mission's run; on a detach it is cleared.
  • A seat the caller chose independently - an explicit --workflow-run that is not this mission's run - is preserved untouched. It was never the mission's to take.
  • A session with no seat simply gains the destination mission's seat.
  • A destination mission with no run of its own seats nobody, so the session moves unseated rather than keeping the old seat. A move must not smuggle a seat past a switch the owner deliberately turned off.

Detach clears the seat rather than refusing. Refusing to detach while a seat exists was considered and rejected: every mission-spawned session is seated, so refusal would make detach impossible for precisely the sessions that most need it. Refusal is the right answer only where no coherent action exists, and here one does - leave the run.

Leaving is recorded, not erased. The ledger marks the participant as having left. That the session was in that run is true and stays true.

The limit, stated because it is real. Moving the seat corrects the RECORD - what the fleet shows, what governs the session, who the run lists. It cannot reach into a running agent's context and replace the conduct text injected at birth. Only telling the session to fetch its conduct again does that, and the command line says so every time a seat moves.

The tenant boundary, which is the constraint that governs the design

Missions are TENANT-SCOPED, and that was hard won: a live leak once served every account's mission list to every account, and a mission NAME is free text a person typed - customer names, project names, people's names. Attach is the first WRITE that takes a mission id from a caller and applies it, so it is exactly the shape that would put the leak back.

The attach route therefore follows the mission-read route line for line: resolve the CALLER's own tenant server-side from the authenticated device key, REFUSE when no tenant is bound (never fall back to a shared partition), and resolve the mission INSIDE that tenant. The mission is resolved BEFORE the session is located, so a refusal is a property of the tenant gate alone and cannot be confused with a Director being offline.

A refusal must not reveal WHICH refusal it is, and that is a security property of the route rather than a nicety of its error text. "No mission has that id" and "that mission belongs to someone else" answer identically - same status, same sentence, only the echoed id differing.

If they diverged, attaching a session to guessed identifiers would enumerate which missions exist in other accounts, one request at a time, without ever reading one. The test that holds this compares the two answers TO EACH OTHER rather than to a fixed string, so a later edit cannot reword one and leave the other behind.

The Gateway sends the RESOLVED NAME down with the id and the Director stamps it directly. A Director must not re-validate against its own mission store: that is a different, single-tenant, per-machine set, so a mission that is real and owned would be rejected for being absent from the wrong store. This is also why a Director's own mission route relays through the Gateway even for a session it hosts itself - a second implementation of this rule would drift, and the drift would be invisible until somebody found a session governed by a mission it had left.

3. Mission and Task - the vocabulary, and why

  • The shared root a pod attacks is a Mission.
  • The single piece a Manager hands to one Worker is a Task.

Chosen after a prior-art survey of multi-agent frameworks and mature work-management tools. Task is the universal, baggage-free unit-of-work primitive - CrewAI, Magentic-One, MetaGPT, LangGraph, Jira, Azure DevOps and Asana all use it for exactly this. Mission is the one root name that inherently means "a crew is collectively dispatched to accomplish one objective", has a real decompose-into-tasks precedent, collides with no mainstream work-management hierarchy level, and reinforces the Mission Control brand.

RejectedWhy
Work itemThe industry umbrella term for ALL work types - Azure DevOps and Jira define a Task AND an Epic as both being "work items" - so it blurs the root and the piece into one word. The most confusing option, not a neutral one.
ObjectiveCollides with Anthropic's use of "objective" for the delegated piece, and carries objectives-and-key-results baggage.
Epic / StoryLocks the vocabulary into agile ceremony.

4. Naming and addressing

Two rules make a fleet legible: NAME every session, and ADDRESS it by something a person can say out loud.

Every session has a number

A short number is allocated at creation, in the range 100 to 999 (SessionNumberAllocator). The Director always allocates, so a session has a number even with no Gateway.

The July open question about fleet-unique numbers is SETTLED and built. The Gateway is the authority and hands out from the LOW end, 100 upward. When a Director cannot reach the Gateway at creation it picks a random free number from a high OFFLINE BAND, which makes a clash between a coordinated number and an offline guess very unlikely. The source document listed this as an open decision for the owner between two designs; the shipped answer is neither of them exactly, and is better than both.

Address by name or number, never by an internal id

People do not parse GUIDs, and neither the wingman nor inter-agent text should make them try.

  • The canonical address in any human-facing or agent-facing text is the NAME if present, else the NUMBER. A raw GUID never appears in human- or agent-facing output.
  • The wingman says "111 wants you", never a GUID.
  • The command line accepts a number, a name, or a short id prefix as an address.
  • The rail shows the number prominently, so a person maps talk-to-row instantly.

For the Architect and Manager seats, the name IS the role-of-mission

Because a Mission has exactly ONE Architect and ONE Manager, "the {role} of {mission}" is a unique, unambiguous address for those two seats - a direct payoff of the cardinality rule. Say "the Manager of the Lifecycle mission", never "f33d" or "111". Workers are N per Mission, so a Worker is addressed by its TASK - which is exactly why a Worker is named from its task.

The display-name convention (ratified by the owner, 11 July 2026)

Mission first, role second, joined with " - ":

Gateway Connection - Architect
Gateway Connection - Manager
Gateway Connection - Worker - connect panel
  1. Mission name FIRST, so sorting the session list by name groups every session of one Mission together, Architect and Manager adjacent, Workers under them.
  2. The repository is NEVER part of the name - the session list shows the repository in its own column, so repeating it is noise that pushes the meaningful part off-screen.
  3. Session ids and numbers are NEVER part of the name. They are machine addressing.
  4. A solo session with no Mission is named for its work - "Clean up stale branches" - again without the repository.

Auto-naming, and what is actually built

A session left on its default name is illegible: the roster reads like a list of hashes. What exists today is the birth half - a name is composed when the session is created, and IsAutoNamed records that it was auto-composed so that a later rename by a person or by the session itself always wins and is never overwritten.

NOT BUILT, and the source document read as though it were: the rename-the-stragglers policy - a generic-name test, a trigger after N turns or M minutes, the Gateway reading a session's first prompt to propose a better name, and help-then-enforce. There is no auto-namer in the Gateway. The thresholds in the source document (3 turns, 2 minutes) were a proposal awaiting the owner's decision and were never settled. Treat this as an idea, not a rule.

The wingman speaks the model, in plain engineering English

The wingman must understand the Mission and seat model so it can talk about sessions correctly, and it must use plain engineering English: "the Manager of Lifecycle needs you".

5. Starting and stopping a session

CORRECTED against the source document, and this one matters most. The lifecycle recipe told every agent to start a session by posting directly to its own Director on a loopback address - "You reach only your OWN Director... No Gateway address, no token."

That is no longer how it works. The remove-the-network-port mission took the loopback port away. EVERY spawn now goes through the Gateway, including one on the very machine you are sitting on. An agent following the source document would be calling a door that no longer exists.

The path a spawn actually takes

TargetRouteWhat it means
HerePOST directors/{my director}/sessionsThis session's own Director, named from what the session was told at launch - no roster lookup and no hostname read off the operating system, which is a different string on a different day.
A machinePOST machines/{machine}/sessionsSome Director on that computer, auto-launching one if none is running.
One named DirectorPOST directors/{id}/sessionsA machine can run several named Directors, so this names ONE - by id or display name. A name that matches two Directors is an error listing both; it never falls back and never auto-launches.

There is no local path to fall back to, and that is the point of the mission that built it: a spawn that quietly landed somewhere else would be the second door in its worst form.

Who owns the new session must be DECLARED

A spawn from inside a session is refused until it says who will own the result. That rule, the three answers, and why --standalone exists are defined in sessions.html section 2 and are deliberately not restated here.

Starting on another computer

Starting and stopping sessions across computers is a first-class capability (owner, 9 July 2026).

  • "Which computer" is optional and defaults to LOCAL - the machine the requesting agent is on. To target another, you NAME it.
  • Address the target by MACHINE NAME, consistent with the addressing policy: names, not GUIDs.
  • No Director on the target? The Gateway auto-launches one through the launcher, then spawns.
  • STOP takes no computer parameter. A session's machine is part of its identity, so stop addresses the SESSION and routes to its home machine automatically. Machine-targeting is START-only.
  • Cross-machine pods work. A Manager on machine A may own a Worker on machine B; the attention model is fleet-wide.

An offline or unreachable target FAILS FAST and FAILS LOUD (owner, 9 July 2026). We cannot power on machines, so the start fails immediately with a clear error naming the computer. No queue-until-wake, no silent fallback to local. That is the no-fallback law, applied: queue-until-wake was considered and explicitly rejected.

The launcher is what makes this possible, and it is built. The launcher is the small tray application that starts on boot and is always running, unlike a Director. It holds the same persistent connection to the Gateway that a Director does, so the Gateway can command a machine to start a Director when none is running: Gateway, to always-connected launcher, to a new Director, to the session. EVERY machine runs one, including the machine hosting the Gateway - that uniformity is the point, and it means the flow can be tested on one machine.

Stopping

A session is stopped with cc-devthrottle session stop <target> --reason "<why>". The reason is not decoration: it is one confirmation rather than an interrogation, and the stop reports what it did. To stop a whole test Director, raise its shutdown signal, named for that Director's own identifier. Graceful: it kills its own sessions and deletes its crash journal, avoiding a phantom "interrupted" fleet entry. There is deliberately no shutdown endpoint - the remove-the-network-port mission took lifecycle off the socket, because stopping a Director has to work when nothing is listening.

Manager discipline when spawning a Worker

From the 9 July 2026 harness survey, and still true:

  • Every Worker's opening prompt MUST carry an explicit objective, the expected output format, and hard task boundaries. The documented multi-agent failure is two Workers duplicating the same investigation because the boundaries were vague.
  • Only spawn Workers for high-value tasks. Multi-agent runs cost roughly fifteen times the tokens of a single chat. Do not spawn a fleet for something one session can do.
  • Name the model you intend. Arguments are passed literally and no default model is applied, so omitting the model runs the session on something other than what you meant.
  • Permission posture is the user's choice, per session (owner, 9 July 2026). The framework does not force, gate or police it. We are not a seatbelt chime.

What the survey of other systems actually taught us

A 9 July 2026 survey of CrewAI, AutoGen, LangGraph, OpenAI Swarm, MetaGPT, Anthropic's orchestrator-worker pattern, claude-flow and cmux. The findings that shaped this design:

  • Enforce in the TRANSPORT, not the prompt. The only system that reliably keeps workers from interrupting the human does it by DENYING the tool, not by instructing. So our suppression is structural - in the fold - and is never a prompt request.
  • Report UP, never hand OFF. A Worker is an agent-as-tool: it returns a result to whoever asked and never inherits the human conversation.
  • Prefer the supervisor PULLING over the worker PUSHING. Routing everything through a manager as broadcast is quadratic chatter at scale.
  • Give workers a status, not a raw dump.
  • Make the seat VISIBLE and route worker attention to its supervisor, not the human roster. cmux, which has no seat model, proves the failure: N panes all shouting at one person.

6. Proposed and never built

Kept because the ideas are the owner's and may still be wanted - and marked, at length, because the source document read exactly like design that had landed. Neither of these exists in the code. Both were checked on 14 September 2026.

The Hub Manager

Proposed 9 July 2026: the fleet gets a top-level Manager that runs as a real session at the Gateway box rather than as an implicit background brain - the fleet's Queen. It would supervise workers, be a seat that surfaces to the owner, and have a large-language-model assistant it can call on demand for judgment: summarize a worker, decide, brief the human. The argument for making it a real session is that it is then a first-class Manager like any other - it can own workers, appears on the roster, and is addressable by number or name.

Status: not built. There is no hub manager anywhere in the code. The design also never answered its own three open questions - one per fleet or one per machine; whether its terminal runs an agent that separately calls the assistant or the assistant IS its agent; and how a person talks to it.

Per-role model configuration

Proposed the same day: name the CONSUMER rather than just the tier. Today a model is resolved from two generic tiers, thinking and fast, stored as brain_model. The proposal was to add per-role keys - a wingman model, a hub-manager model - resolving as "the role's model if set, else the generic tier, else the provider default", with one dropdown per named role in settings.

Status: not built. The generic tiers are all that exists. This one is also partly blocked on the item above: half its purpose was a model binding for a seat that does not exist.
