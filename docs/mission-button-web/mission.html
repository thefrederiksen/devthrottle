The why

You run the fleet from the Cockpit and from your phone as much as from the desktop. A session's Mission and goal that only the desktop shows is invisible exactly where you are when a session asks you for something. The Gateway already decides the button; the two web surfaces just have to show it.

The goal

On the live Cockpit and the live mobile app, both opened in a browser on the computer, each session shows its Mission button, and a QA report proves it with screenshots:

  • A session attached to a Mission with a document shows an indigo button with the Mission's name; its tooltip or long-press shows the name and goal; clicking it opens the mission document.
  • A session with no Mission shows yellow "No mission". Nothing stops it working.
  • Both surfaces render one shared component, so they cannot drift.
  • Merged to origin/main, reviewed by a separate review session, deployed with the deploy workflow.

1. What gets built

  • One shared component in packages/client-core, a Mission button that renders the session's missionButton verdict verbatim: the label, the colour from the colour key (mission indigo, mission-outline indigo outline, warning yellow), the tooltip, and a link to the document address. An unknown colour key shows a visible problem, never a guessed colour.
  • Placement: on each session's own screen - the Cockpit session detail header beside its actions, and the mobile session app bar. The session roster rows are left as they are.
  • No Gateway change. The client decides only layout, never what a state means.

2. The proof

After the deploy, in a signed-in browser on the computer: the live Cockpit and the live mobile app (the mobile app in a phone-sized window), each showing a session in this Mission (indigo, its tooltip, the click opening this document) and a session with no Mission (yellow). Published as a QA report linked from section 3.
