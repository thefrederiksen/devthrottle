# Track C, developer C3 - a usable approver form (pull request 1 of 2)

17 October 2026, branch `license-c3-approver-form`, cut from `origin/main` at `08dec1140`.

## What the owner saw, and what is there now

On 16 October, Licenses > Sign-ins > "Set an approver" was four free-text boxes, the account box filled with the
wrong account, the operating system user and the browser profile empty, and Save greyed out with no reason.

Now the form is four pick lists and nothing is typed:

- **Claude account** - the accounts on the Licenses page. Nothing is chosen, unless the form was opened from that
  account's own card: every card now has a **Set the approver** button beside the approver sentence, which opens the
  form with that account chosen and puts the cursor in it. Change on an approver row keeps that approver's account,
  as before.
- **Approving machine** - the machines that have reported.
- **Operating system user on that machine** - the users that machine has reported. With one user, it is chosen for
  you.
- **Browser profile on that machine** - read from `GET /directors/{id}/browsers` of the Director that reports that
  machine and user. While it is read: "Loading the browser profiles on machine-a...". When that Director is not
  connected: the Gateway's sentence, "machine-a's Director is not connected, so its browser profiles cannot be
  listed.", and no profile is listed and the Director is not asked. When it has none: "machine-a's Director has no
  browser profiles." When the read itself fails: the Gateway's own sentence.

Changing the machine clears the user and the profile; changing the user clears the profile.

**Save is never shut while the form is idle.** Pressed with a choice missing, it sends nothing and lists exactly what
is missing, one line each ("Choose the browser profile on machine-a."). Each line goes away as its choice is made. A
refusal from the Gateway is shown in the Gateway's own words and the form keeps what was chosen.

The profile is sent by its **identifier**, not its display name, so renaming a profile does not break the approver.
The approving Director's `license approve --browser` accepts a name or an identifier (`director_browser` in
`tools/cc-devthrottle/src/license_signin.py`), and the Gateway's profile check (letters, digits, spaces, dots,
underscores, hyphens, at most 64) accepts the identifier slugs. A stored approver whose profile was saved by name is
shown chosen by matching the name when the form opens on it.

## One Gateway change, and why (repository rule 7)

The brief names the Cockpit files only, but the page cannot know which Director reports a machine: a machine name and
user can have several Directors over time (development slots run side by side), and only the Gateway's read model
records **the Director that sent the machine's last accepted report** - the same record the approval relay uses to
find the approver. So the Gateway now puts three fields on each machine of `GET /gateway/licenses`, folded in
`LicenseSignInFold.Apply` beside `canAddSpare` / `addSpareText` and in the same pattern:

| Field | What it is |
|---|---|
| `directorId` | The Director that sent the machine's last accepted report. |
| `canListBrowserProfiles` | That Director is connected. |
| `browserProfilesText` | "The browser profiles of machine-a's Director.", or "machine-a's Director is not connected, so its browser profiles cannot be listed." |

So the not-connected sentence is the Gateway's, and the page does not decide connectedness. The words the page says
itself are the loading line, the "has no browser profiles" line and the missing-choice lines: each describes the form's
own state (a read in flight, an empty list, a choice not made), not a verdict about the fleet.

`missions/license-switching/cockpit-api.md` (section 2 example, section 7.6 table) and the Cockpit fixtures were
regenerated by the existing tools (`produce_overview_example.py`, then `copy_fixtures.py`); the producer reported
"0 differences, 6 fields added".

## Does `GET /directors/{id}/browsers` answer the owner's Cockpit sign-in? Yes.

Read on `origin/main`:

- The route (`GatewayEndpoints.cs`, the automation browsers block) resolves the Director with
  `TryResolveOwnedDirector`, which looks it up **in the request's own tenant** (`registry.Get(reqTenant, id)`): a
  Director of another account answers 404. It then sends `browsers-list` to that Director and forwards its answer
  verbatim; a Director that is not connected answers 502 with "The Director on <machine> is not connected right now,
  so the command was not delivered."
- `SessionKeyGuard` is applied only to **session keys** (`AuthMiddleware.AuthenticateSession`). An owner's Cockpit
  sign-in is not a session key, so the guard does not apply to it. (For a session key, `IsBrowserRoute` allows
  `GET /directors/{id}/browsers` anyway.)

No route was opened or widened.
