Mission: Resource Monitor

Mission document v3 · Architect seat · devthrottle repository · 2026-10-15 · Go given 2026-10-15 · Delivery Lead driving

Summary

The mission: every Director measures its machine's CPU, memory and disk on Windows, Linux and macOS. It shows them in a toolbar meter and a detail screen, warns when one is maxing out, and logs them on the Gateway. The Cockpit then shows the whole fleet's capacity, so factories can be placed where there is room.

New in version 2: "Why is it slow?" You asked for diagnostics the Director runs itself. On top of the meter, the Director continuously works out which resource programs are stalled waiting on: CPU, memory or disk. It names the cause and the culprit, for example "Slow because of the disk: the hard drive sdc is 75% busy, 26 ms per write; mostly dotnet test in session 140". It keeps a 24-hour local recording, so a slowdown can be explained after it has passed. Agents can ask for the same verdict through a command.

All four of your earlier decisions follow my recommendations:

  • Usage is shown per session from the start.
  • The Gateway keeps 1-minute history for 30 days, then hourly history for a year.
  • On a warning, the icon changes colour and one banner appears.
  • The Director side is built first, then the Cockpit fleet view.

The work has 4 phases. Phases 2 and 3 run in parallel once phase 1's interface is fixed. It ends merged to main. Releasing the Director and deploying the Gateway stay your decision.

It takes in issue #2811, the open "memory first" toolbar meter, and builds on the memory probe that already exists from #2818.

1The mission

Every Director measures its machine (CPU, memory, disk and what each session uses), shows it and warns on it in the toolbar, and logs it on the Gateway. The fleet can then see its capacity and place factories where there is room.

2The why

In your words:

"When we start building factories, we want to know how much we're using so we can load balance the different factories and different machines." … "So I don't have to use task manager or anything else. And we can log it centrally."
  • Factories run on machine capacity, and nobody can see it. The Gateway knows which sessions run where, but not what they cost the machine. Without that you can't decide where the next factory goes, which machine is overloaded, or what a factory costs to run.
  • The Director should know why the machine is slow, not just how busy it is. On 2026-10-15 devlinux was "super slow". CPU and memory looked healthy. Linux's pressure figures showed programs stalled waiting on the disk 32% of the time, against 0.06% for CPU and 0.17% for memory. The cause was a spinning hard drive inside the root volume (sdc, 75% busy, 26 ms per write) while both SSDs sat idle. Finding that took a session running shell commands by hand. The Director should say it unprompted.
  • Slowness looks like the product's fault. This morning devlinux had 26 GiB of 39 GiB memory available and was 80% CPU-idle, yet the load was 19 to 23. Processes were waiting on the disk, and nothing in the Director said so. Issue #2811 records the same thing on a customer's 16 GB laptop on 2026-09-11.

3The goal

When this mission ends, all of these are true and shown in the QA report:

  1. On Windows, Linux and macOS, the toolbar meter's CPU, memory and disk figures agree with the operating system's own monitor, within 5 percentage points.
  2. Pushing a resource past its limit turns the meter amber or red and shows one banner within 70 seconds. Bringing it back down clears the warning. This is shown for CPU, memory and disk activity.
  3. Clicking the meter opens the detail screen, which shows usage by session and by process. A session's figure includes the child processes it started.
  4. Every machine's 1-minute summaries appear in the Gateway's database. A Director cut off from the Gateway for 10 minutes sends the missing minutes when it reconnects, leaving no gap.
  5. The Cockpit fleet view lists every machine with its spare capacity, and every factory (Mission) with its average and peak cost.
  6. The sampler itself costs under 0.5% of one core, as measured.
  7. The slowness diagnosis names the right cause. On devlinux, with its hard drive in the root volume, it says "disk", names sdc as the spinning hard drive and names the busiest process and session. Under a CPU load it says "CPU". With memory tight it says "memory". The same command gives the same verdict to an agent.
  8. When a platform can't be read, the meter says "cannot read" and logs why. It never shows a made-up or zero value.

5Design

Probes (Core)→5 s samples, last hour in memory→Toolbar meter + detail screen→1-min summary over the existing Gateway stream→gateway_stats table→Cockpit fleet view

The pieces

PieceWhereWhat it does
Resource probessrc/CcDirector.Core/Machine/, alongside MachineMemoryProbeCPU (total and busiest core), disk busy and I/O wait, disk read and write speed, free space per volume, swap, network, and per-process-tree CPU and memory. Each reads the operating system directly and starts no subprocess. Results are cached for 1 s. The text-parsing logic is pure functions, so it can be unit-tested from captured /proc output and the like.
VerdictsResourcePressure, built the same way as MemoryPressureOne pure function per resource gives Normal, Tight or Critical, using the limits in section 5b. A resource must stay over the limit for 60 s to count. Memory keeps its existing, tested limits.
Stall readings (the core of "why is it slow")Core, with the probesHow much of the time programs are frozen waiting on each resource.
Linux: /proc/pressure/{cpu,memory,io}.
Windows: processor queue length, disk seconds per transfer and queue length, and hard page faults per second (performance counters).
macOS: the kernel's memory-pressure level, run-queue load, and the IOKit disk-time statistics.
Also: a count of processes stuck waiting on the disk, and each physical disk with whether it is spinning or solid-state.
Slowness diagnosisCore, a pure function like MemoryPressureTurns the stall readings into one verdict: not slow, or slow because of CPU / memory / disk / a combination. Each verdict carries its evidence (the figures), the culprit (process, session and, for disk, the physical disk and its type) and a plain next step. Shown in the banner, at the top of the detail screen, and in a new "Diagnosis" tab with the 24-hour timeline.
Background recordingDirector, localKeeps 24 hours of 5-second samples on local disk, written once a minute in one append so the recorder doesn't load a slow disk, and pruned automatically. "What made it slow at 08:26?" can be answered afterwards, even with no Gateway.
Diagnose commandAn agent-discoverable action (it appears in cc-devthrottle actions; the builder settles its name)Returns the current verdict plus the last hour of history as text or JSON. A session asked "why is this machine slow?" runs this one command instead of improvising shell commands.
SamplerDirector background jobSamples every 5 s and keeps a 1-hour ring buffer. It builds the 1-minute summary, raises crossing events, and holds up to 24 h of summaries while the Gateway can't be reached.
Toolbar meterMainWindow.axaml, right-hand group, before CockpitThree bars (CPU, memory, disk), each coloured on its own, with a tooltip. It shrinks to percentages on a narrow window (#2812).
Warning bannerDirectorAppears once per resource each time that resource crosses into amber or red. It names the biggest user and offers "Show resources" and "Dismiss".
Detail screenNew Director windowTiles with a 1-hour history, plus tabs for sessions, processes, disks and history. A session row expands into its process tree, and a process can be ended from there (with a confirmation).
Gateway contract and storageGateway.Contracts, a new hub method beside PushSnapshot, a new table in gateway_stats keyed by tenantStores 1-minute machine rows and session rows, runs an hourly roll-up, and deletes 1-minute rows after 30 days and hourly rows after a year. The migration only adds tables.
Cockpit fleet viewapps/cockpitLists machines with their peak, average and spare capacity, and factories (Missions) with their average and peak cost.

6Phases

Phase 1: Probes and verdicts (Core). Tech Lead: yes.

Three Developers in parallel, one per operating system, against one shared IResourceProbe interface. The Tech Lead fixes the interface on day one, before anyone else builds on it. Includes per-process-tree attribution: on Windows that means checking whether a child process that detaches from its parent is still counted; on macOS the disk statistics come from IOKit. Adds the stall readings, physical-disk type detection, ResourcePressure and the slowness-diagnosis function, each with exhaustive unit tests. The devlinux readings recorded on 2026-10-15 become a test fixture that must produce the verdict "disk, sdc spinning hard drive".

Done when: the parser tests pass on recorded output, and each platform's live test reads real, non-zero values on a real machine of that kind.

Phase 2: Director interface (meter, banner, detail screen). Tech Lead: yes. Runs in parallel with phase 3.

Starts against a fake probe as soon as phase 1's interface is fixed. Developers: (a) the sampler, meter and banner, (b) the detail screen and the Diagnosis tab, (c) the 24-hour local recording and the diagnose command.

Done when: there is a QA report with screenshots: normal, amber, red, the banner, the warning clearing, a narrow window, "cannot read", and the detail screen with a session expanded.

Phase 3: Gateway logging. Single Developer, no Tech Lead. Runs in parallel with phase 2.

The contract, the hub method, the migration (adds tables only), the roll-up and deletion job, and the Director's offline buffer with catch-up after reconnecting.

Done when: the Gateway tests show summaries stored, rolled up and deleted on schedule, and a 10-minute disconnect leaves no gap.

Phase 4: Cockpit fleet view. Single Developer. Starts after phase 3 merges.

Reads the Gateway: machines by spare capacity, and factories (Missions) by cost.

Done when: the Cockpit tests pass, and screenshots against a local Gateway seeded with 3 machines show the view.

Final: cross-platform QA (Delivery Lead)

On a Linux, a Windows and a macOS Director, depending on your answer above. Covers the flow and every failure case in section 7.

7The check

What counts as proven: tests pass, and real numbers on a real machine agree with that machine's own monitor, and each warning is shown firing and clearing under a real load. A test run alone doesn't prove the meter matches the machine.

# 1. Build and unit/integration tests (every phase)
dotnet build cc-director.sln -c Release
dotnet test src/CcDirector.Core.UnitTests
dotnet test src/CcDirector.Core.Tests        --filter "Category=Resources"
dotnet test src/CcDirector.Avalonia.Tests    --filter "Category=Resources"
dotnet test src/CcDirector.Gateway.UnitTests --filter "Category=Resources"
cd apps/cockpit && npm test

# 2. Live load check, run on each platform (new harness, built in phase 2)
dotnet run --project tools/harnesses/resource-load-proof -- --cpu --disk --memory --report out/

The load harness (it reuses CpuLoad from DeliveryQualification) does these things in turn and writes a screenshot and a reading for each:

  1. Records the meter's figures next to the operating system's own figures, at idle.
  2. Puts the CPU under full load and expects red within 70 s, then removes the load and expects the warning to clear.
  3. Writes to disk continuously and expects disk activity to go red. Then stops.
  4. Allocates memory until the machine is Tight and expects amber. Then frees it.
  5. Blocks the Gateway for 10 minutes, then unblocks it, and expects no gap in the stored minutes.
  6. Measures the sampler's own CPU over 10 minutes and expects under 0.5% of one core.
  7. Runs the diagnose command after each load and expects the matching verdict ("CPU", "disk", "memory"). On devlinux at idle-with-builds it expects "disk, sdc spinning hard drive".

Failure cases that must be in the QA report:

  • A probe that can't read shows "cannot read" and logs why, never 0.
  • The Gateway is down for a long time; the buffer caps at 24 h and drops the oldest.
  • A session's child process outlives the session.
  • The clock jumps.
  • The window is narrow.

8Merge plan

  • Each Developer's pull request merges to main once it passes review. Review is by Codex, or Pi on GLM-5.3 if Codex wrote the code. No long-lived branch.
  • Why that is safe here:
    • The probes are new files with no caller until phase 2.
    • The Gateway migration only adds tables.
    • The new hub method is ignored by older Gateways. A Director checks that the Gateway supports it before sending.
    • An older Director simply never calls the new method.
  • The meter appears in the toolbar when phase 2 merges. Nobody gets it until you cut a Director release.
  • One worktree per workstream, cut from origin/main.

What this rests on, and what is not proved

Read in the code today:

  • MachineMemoryProbe and MemoryPressure, the memory reading and tested limits for Windows, Linux and macOS.
  • The toolbar in MainWindow.axaml, with Cockpit and Settings in the right-hand group.
  • The Director's Gateway stream methods (PushSnapshot, PushDelta and others) in GatewayStreamClient.cs.
  • The gateway_stats PostgreSQL schema, which already has a tenant column.
  • The CpuLoad harness.
  • The Cockpit app at apps/cockpit.
  • Issue #2811, which is open.
  • The style guides in docs/.

Not proved:

  • No code is written.
  • That the Windows performance counters and the macOS signals give a stall verdict as clean as Linux's pressure figures. On Linux the reading is direct; on the other two the verdict is built from proxies, and the QA has to show they agree with what the machine feels like.
  • That the existing stream can take a 1-minute summary without changes to how it connects and authenticates. I believe so, from the method names, but haven't traced it.
  • That per-process-tree attribution is reliable on Windows when child processes detach. This is phase 1's first risk.
  • That the macOS disk-busy reading through IOKit works.
  • The CPU, disk and swap limits. They are proposals until the QA has run them.
