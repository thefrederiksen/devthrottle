Mission: Resource Monitor

Mission document v5 · devthrottle repository · issue #2811 · 2026-11-06 · supersedes v3 of 2026-10-15 · Go given 2026-11-06 · Implementation Lead driving

Summary

The mission: every Director measures its machine's memory and processor on Windows, Linux and macOS. It shows both as two bars in the toolbar between the Director name and the Cockpit button, warns with a banner when either maxes out, opens a detail screen showing usage per session, keeps 24 hours of five-second samples on local disk, and sends the Gateway a summary every five minutes. The Cockpit's existing Fleet → Machines page gains processor, memory and spare-capacity columns, and an expanded machine shows cost per factory.

Behind the two bars, the slowness diagnosis also reads the disk, so a disk-bound machine is still named as disk-bound even though no bar shows disk. That is the owner's decision of 2026-11-06 and it is the reason the diagnosis is worth having: on 2026-10-15 devlinux was unusable with 26 GiB of 39 GiB free and 80 per cent of the processor idle, so a memory-and-processor meter alone would have shown two green bars on a dead machine.

What changed since v3. v3 measured processor, memory and disk, and sent a one-minute summary. The owner narrowed it on 2026-11-06 to memory and processor, sent every five minutes. Section 11 records exactly what that supersedes. The narrowing removes the riskiest platform work in the mission, because the disk busy reading was the one figure nobody had proved on macOS.

Where it actually stands. The owner approved v3 on 2026-10-15 and the shared probe interface merged the same day (#4016). Then the mission stopped for three weeks: the three platform pull requests — #4019 Linux, #4020 Windows, #4035 macOS — were opened on 2026-10-15 and never reviewed, never merged, with no continuous integration result, and phases 2, 3 and 4 never started. Nothing a user can see was ever built and nothing reaches the Gateway today.

The goal of this run is one quality assurance report that shows the whole thing working — not a merge and not a release. The owner's words: "the goal should be to create a QA report that shows this all working." Section 8 is what that report has to carry.

The work has four phases. Phases 2 and 3 run in parallel once phase 1's interface is fixed. Releasing the Director to the fleet, and deploying the Gateway migration to production, stay the owner's decisions, made separately.

Questions

No questions. The owner answered all three scope questions and gave the go on 2026-11-06. Nothing in this document is open. The three things that remain his are not questions but acts: restarting the Director when there is a new build to look at, releasing the Director, deploying the Gateway, and starting the stopped devlinux Director so the Linux quality assurance can run.

1The mission

Every Director measures its machine — memory, processor, and what each session's whole process tree costs — shows it and warns on it in the toolbar, keeps a local recording of it, and sends a five-minute summary to the Gateway. The fleet can then see its spare capacity and place factories where there is room, and the Director can answer "why is this machine slow?" without anybody running shell commands by hand.

2The why

In the owner's words:

"When we start building factories, we want to know how much we're using so we can load balance the different factories and different machines." … "So I don't have to use task manager or anything else. And we can log it centrally."
  • Factories run on machine capacity, and nobody can see it. The Gateway knows which sessions run where, but not what they cost the machine. Without that nobody can decide where the next factory goes, which machine is overloaded, or what a factory costs to run.
  • The Director should know why the machine is slow, not just how busy it is. On 2026-10-15 devlinux was "super slow". Memory and the processor looked healthy. Linux's own pressure figures showed programs stalled waiting on the disk 32 per cent of the time, against 0.06 per cent for the processor and 0.17 per cent for memory. The cause was a spinning hard drive inside the root volume (sdc, 75 per cent busy, 26 milliseconds per write) while both solid-state drives sat idle. Finding that took a session running shell commands by hand. The Director should say it unprompted.
  • Slowness looks like the product's fault. That same morning devlinux had 26 GiB of 39 GiB available and was 80 per cent processor-idle, yet the load average was 19 to 23. Nothing in the Director said why. Issue #2811 records the same thing on a customer's 16 GB laptop on 2026-09-11.

3The goal

When this mission ends, all of these are true and shown in the quality assurance report:

  1. On Windows, Linux and macOS, the toolbar meter's memory and processor figures agree with the operating system's own figure for the same quantity — the share of time the processor was busy — within 5 percentage points. On Linux that is free and /proc/stat, on macOS Activity Monitor, and on Windows the "% Processor Time" counter in Performance Monitor.

    Why this no longer names Task Manager, changed 6 November 2026. Windows 11's Task Manager headline figure is "% Processor Utility", which scales by clock speed rather than by time. Measured on SOREN_NORTH: under turbo it read 100 while the processor was 67 to 89 per cent busy by time — up to 33 points apart. The criterion as first written demanded that two different quantities agree within 5 points, which no correct probe could ever satisfy on a machine that boosts. The probe reports busy-by-time, the same quantity as Linux and macOS, and against "% Processor Time" it agrees within 0.58 points over 16 rounds at 67 to 99 per cent load. One quantity on all three platforms is the point of the meter; a figure that matched Task Manager would read correctly on Windows and mean something different from the other two.

    The owner still sees a difference, and the report must show it. The owner's own words for this mission were "so I don't have to use task manager" — so when the Director reads 70 and Task Manager reads 100 on the same machine, that gap needs explaining rather than hiding. The quality assurance report carries both figures side by side on a boosting Windows machine, with the explanation, so the decision about whether the Director should also offer the clock-scaled figure is made on the evidence and by the owner.

  2. Pushing a resource past its limit turns the meter amber or red and shows one banner within 70 seconds. Bringing it back down clears the warning. This is shown for the processor and for memory.
  3. Clicking the meter opens the detail screen, which shows usage by session and by process. A session's figure includes the child processes it started.
  4. Every machine's five-minute summaries appear in the Gateway's database, each carrying average, peak and any amber or red crossing. A Director cut off from the Gateway for 10 minutes sends the missing windows when it reconnects, leaving no gap.
  5. The Cockpit fleet view lists every machine with its spare capacity, and an expanded machine shows each registered factory's average and peak cost, grouped by the session's Factory value (a factory is not a Mission).
  6. The sampler itself costs under 0.5 per cent of one core, as measured over 10 minutes.
  7. The slowness diagnosis names the right cause. Under a processor load it says "CPU". With memory tight it says "memory". And it names a disk-bound machine as disk-bound, proved two ways because devlinux has changed underneath this mission: the recorded readings of 2026-10-15 must still produce exactly "disk, sdc spinning hard drive", and a live verdict under a deliberate disk load must name whichever disk is actually busy at the time. The same command gives the same verdict to an agent.
  8. When a platform cannot be read, the meter says "cannot read" and logs why. It never shows a made-up or zero value. This is a named failure case in section 8, not an edge case.

5c-i. The ruling on what the diagnosis may read, and what it may claim

Decided by the Implementation Lead on 2026-11-06, inside the owner's instruction, not referred back to him. Two Developers reached the same conclusion independently from measurement, on different platforms, which is why it is settled here rather than reopened with him.

What the narrowed per-disk reading keeps, for the diagnosis only: name, kind, busy percentage (nullable), milliseconds per read, milliseconds per write, and average queue depth. It is never rendered as a bar, never stored as a Gateway column and never shown in the Cockpit. It reaches the owner only as words inside a diagnosis. Volumes, free space, disk byte rates and the network reading are dropped as planned.

Why this is inside the instruction rather than around it. The owner banned the disk as a meter and banned one specific reading - "not the IOKit disk-busy reading that was never proved on macOS". Milliseconds per operation is not that reading. It is a different quantity, and it was measured on this Mac mini against iostat in the same windows: 0.000 ms idle, 0.052 with one flushing writer, 1.099 with one writer flat out, 15.785 with four contended. Main had already made the busy percentage nullable for exactly that reason, so on macOS the busy figure stays null and the latency figure carries the signal. Without these figures a disk-bound Mac could never be called disk-bound - two green bars on a dead machine, which is the devlinux failure of 2026-10-15 reproduced on a Mac, and the one thing the diagnosis exists to prevent. On Linux, /proc/pressure/io is a whole-machine figure: it can say the machine is stalled on the disk but not which disk, so without the per-disk figures the verdict degrades from "sdc is 75 per cent busy at 26 milliseconds per write" to "the only spinning disk", which is not a diagnosis. A written phase-1 ruling of 2026-10-15 already rested the macOS disk verdict on milliseconds per read and write; the 6 November narrowing was not written against it, and this keeps both intact.

Per-process disk read and write rates stay, as diagnosis evidence. This paragraph exists because the sentence above - "disk byte rates are dropped" - was written about the per-disk reading, whose throughput did go out with the meter, and read on its face as dropping the per-process figures too. It does not. ProcessReading.DiskReadBytesPerSecond and DiskWriteBytesPerSecond are kept on the same terms as everything else here: diagnosis-only, nullable, never a bar, never a tile, never a Gateway column, never in the Cockpit. Without them the approved sentence in 5i cannot be finished: "the hard drive sdc is 75 per cent busy … mostly dotnet test in session 140". A diagnosis that names the disk but not the process thrashing it names half the cause, and the half it drops is the half somebody can act on.

But bytes per second is weak evidence, and the diagnoser must treat it as such. Many small random writes will stall a spinning disk at a very low byte rate, so a high rate is not required for a process to be the culprit and a low one does not clear it. It supports "mostly X" and must never become a threshold. The disk verdict still comes from the stall figure where the platform publishes one, and from latency where it does not.

The wording rule, which is part of the ruling. The platforms do not measure the same thing, so they may not claim the same thing. Linux measures stall directly and may say "programs were stalled waiting on the disk 32 per cent of the time". macOS and Windows may not - macOS publishes no stall figure for any resource and its process states carry no uninterruptible-disk-wait, and Windows has only performance-counter proxies. They say "the disk is answering slowly", from latency, and must never be written as though a stall percentage had been measured. A platform that cannot tell says CouldDiagnose false with the reason, which means not known and never "fine". The macOS and Windows latency thresholds are unproved - one machine, one internal solid-state disk, and no spinning disk has ever been measured on a Mac - so they are proposals, recorded as proposals in the quality assurance report, and never hard-coded as though established.

6The five-minute logging contract

QuestionAnswer
How often does the Director sample?Every five seconds, locally. The live meter and the 60-second warning rule both need this, and the send interval does not change it.
How often does it send?Every five minutes. One message carrying one machine row and one row per session.
What is in a row?Average, peak and any amber or red crossing inside the window, for memory and the processor. Four numbers plus a crossing note instead of two, so a 90-second spike is not averaged away.
How does it travel?A new hub method beside the existing PushSnapshot, on the Gateway stream the Director already holds open. No new connection and no new authentication.
What if the Gateway is unreachable?The Director buffers up to 24 hours of five-minute rows and sends the missing windows on reconnect, so a 10-minute outage leaves no gap. Past 24 hours the oldest are dropped, and the local recording still has them.
Where is it stored?New tables in the gateway_stats schema, keyed by tenant. The migration only adds tables.
How long is it kept?Five-minute rows for 90 days, then an hourly roll-up for two years. An hourly job rolls up and deletes.
How big does that get?About 8,600 machine rows per machine per month — a fifth of v3's one-minute design. Four machines for 90 days is well under a million rows. At a fifth of the row count the same storage buys three times the history, which is why retention grew from v3's "30 days then a year".
What about an older Gateway or Director?A Director checks that the Gateway supports the method before sending; an older Gateway ignores it and an older Director never calls it. Nobody gets the meter until the owner cuts a Director release.
What does the sampler cost?Under 0.5 per cent of one core, measured over 10 minutes. Each probe reads the operating system directly and starts no subprocess.

One thing five minutes does not change, and one it does. It does not change the warnings: those are decided locally from five-second samples, so a banner still appears within 70 seconds of a resource maxing out, and the Cockpit's status column reflects it on the next send. What it does change is after-the-fact precision on the Gateway — the finest grain anyone can query centrally becomes five minutes. The Director's own 24-hour recording keeps every five-second sample, so the full detail of a slowdown is on the machine; it is just not in the Cockpit.

7Phases

Phase 1: Probes and verdicts (Core). Tech Lead: yes.

It starts by closing #4019, #4020 and #4035 and re-cutting narrow pull requests from the same branches (the owner's answer, 2026-11-06). The branches stay. The memory, processor and stall code is lifted out; the disk-meter, network and per-volume code is dropped. The Tech Lead fixes the interface first — the narrowing means ResourceSample loses its disk-meter, volume and network parts while the disk stall reading stays — before anyone else builds on it.

Then three Developers in parallel, one per operating system, behind the already-merged IResourceProbe. Includes per-process-tree attribution (on Windows, whether a child process that detaches from its parent is still counted), ResourcePressure, and the slowness-diagnosis function, each with exhaustive unit tests. The devlinux readings recorded on 2026-10-15 stay a test fixture that must produce the verdict "disk, sdc spinning hard drive".

Done when: the parser tests pass on recorded output, and each platform reads real, non-zero values on a real machine of that kind.

Phase 2: Director interface (meter, banner, detail screen). Tech Lead: yes. Runs in parallel with phase 3.

Starts against a fake probe as soon as phase 1's interface is fixed. Three Developers: (a) the sampler, the two-bar meter and the banner; (b) the detail screen and the Diagnosis tab; (c) the 24-hour local recording and the diagnose command. This is the restart point: when there is a Director build with the meter in it, the owner is asked to restart, told what to look for, and waited for.

Done when: there are screenshots of normal, amber, red, the banner, the warning clearing, a narrow window, "cannot read", and the detail screen with a session expanded.

Phase 3: Gateway logging. One Developer, no Tech Lead. Runs in parallel with phase 2.

The contract, the hub method, the migration (adds tables only), the five-minute summary, the roll-up and deletion job, the Gateway-side fold of the display verdict, and the Director's offline buffer with catch-up after reconnecting. Proved against a local Gateway. Deploying to production is the owner's separate decision, through the deploy-hosted-gateway skill and nothing else.

Done when: the Gateway tests show rows stored, rolled up and deleted on schedule, and a 10-minute disconnect leaves no gap.

8The check

What counts as proven: tests pass, and real numbers on a real machine agree with that machine's own monitor, and each warning is shown firing and clearing under a real load. A test run alone does not prove the meter matches the machine.

# 1. Build and tests (every phase)
dotnet build cc-director.sln -c Release -p:EnableWindowsTargeting=true
dotnet test src/CcDirector.Core.UnitTests        --filter "Category=Resources"
dotnet test src/CcDirector.Core.Tests            --filter "Category=Resources"
dotnet test src/CcDirector.Avalonia.Tests        --filter "Category=Resources"
dotnet test src/CcDirector.Gateway.UnitTests     --filter "Category=Resources"
cd apps/cockpit && npm test
# On Windows, the whole gate: .\scripts\test-local.ps1

# 2. Live load check, run on each platform (new harness, built in phase 2)
dotnet run --project tools/harnesses/resource-load-proof -- --cpu --memory --report out/

-p:EnableWindowsTargeting=true is needed on Linux and macOS, where a plain solution build stops with NETSDK1100 on the two Windows-only projects. The PowerShell gate scripts\test-local.ps1 runs on Windows only.

The load harness (it reuses CpuLoad from DeliveryQualification) does these in turn and writes a screenshot and a reading for each:

  1. Records the meter's figures next to the operating system's own, at idle.
  2. Pins the processor and expects red within 70 seconds; then removes the load and expects the warning to clear.
  3. Allocates memory until the machine is Tight and expects amber; then frees it and expects the warning to clear.
  4. Blocks the Gateway for 10 minutes, then unblocks it, and expects no gap in the stored five-minute rows.
  5. Measures the sampler's own processor cost over 10 minutes and expects under 0.5 per cent of one core.
  6. Runs the diagnose command after each load and expects the matching verdict. On devlinux at idle-with-builds it expects "disk, sdc spinning hard drive".

Everything the quality assurance report must carry:

  • The meter's memory and processor figures within 5 percentage points of the operating system's figure for the same quantity: Activity Monitor on macOS, the "% Processor Time" counter on Windows, and free with /proc/stat on Linux. Not Task Manager's headline processor figure — see the note on success criterion 1.
  • On a Windows machine that boosts its clock: the Director's figure and Task Manager's "% Processor Utility" side by side, with the measured gap and the explanation, so the owner can decide whether the clock-scaled figure is also wanted.
  • Screenshots: normal, amber, red, the banner, the warning clearing, a narrow window, "cannot read", and the detail screen with a session expanded.
  • Five-minute rows in the Gateway's database, and a 10-minute disconnect that leaves no gap after reconnect.
  • The Cockpit fleet view against a local Gateway seeded with three machines.
  • The sampler's own cost under 0.5 per cent of one core, measured over 10 minutes.
  • The diagnosis naming the right cause: "CPU" under a processor load, "memory" when programs are STALLING on memory — not merely when the level reads Tight, which is a pressure level and not a cause, and which no amount of allocating will turn into one (the quality assurance plan's "Tight is not a cause" section has the proof per platform) — and the disk named two ways - the recorded 2026-10-15 devlinux readings still producing "disk, sdc spinning hard drive" as a regression test, plus a live verdict under a deliberate disk load naming whichever disk is busy. Why two: devlinux's root volume now sits on sda and sdb only, sdc is out of it and reads 0 per cent busy, so the 2026-10-15 accident can no longer be reproduced live. A live proof under a load we created is better evidence than a lucky reproduction of an old accident.
  • Each platform's disk wording matching what it actually measured - see the wording rule in 5c.
  • A probe that cannot read shows "cannot read" and logs why — never 0, never a made-up number.
  • The buffer capping at 24 hours; a session's child process outliving the session; the clock jumping.

The report is one self-contained HTML file published with cc-dev-reports open. A file path handed over instead of a published report is the defect that tool exists to stop.

9Merge plan

  • Each Developer's pull request merges to main once it passes review. No long-lived branch. One worktree per workstream, cut from origin/main — never the shared checkout.
  • The reviewer is never the writer, and never the same agent family. The reviewer order is the one fixed by the owner on 2026-09-28 and written down in CLAUDE.md; this document does not restate it, so it cannot drift from it. A Developer never picks its own reviewer. The gate is a green scripts\test-local.ps1 plus that review — nothing waits on a continuous integration result.
  • Why merging early is safe here:
    • The probes are new files with no caller until phase 2.
    • The Gateway migration only adds tables.
    • The new hub method is ignored by an older Gateway, and an older Director never calls it.
  • The meter appears in the toolbar when phase 2 merges. Nobody outside the fleet gets it until the owner cuts a Director release.

10Where it ends

One quality assurance report that shows the whole thing working, with the code merged to main behind it. Releasing the Director, and deploying the Gateway migration and hub method to production, are the owner's decisions, made separately. No session deploys on its own, and no session deploys to Europe.

The four things that are the owner's and not this mission's: restarting the Director when there is a new build to look at (he offered), releasing the Director, deploying the Gateway, and starting the stopped devlinux Director without which the Linux check cannot run.
