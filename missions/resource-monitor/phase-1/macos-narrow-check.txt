WHAT THIS FILE IS, AND WHAT THE OTHER TWO ARE. This is the record for the probe as it ships after
the owner narrowed the mission on 2026-11-06. The two files beside it - macos-check.txt and
macos-live-reading.txt - are the 15 October record of the WIDER probe on the closed pull request
4035, and they still describe readings this code no longer takes (volumes, free space per volume,
network throughput, disk read and write speeds). They are kept because the review of 4035 cites
them as evidence, not because they describe what ships. macos-disk-busy-risk.txt is still current:
it is the measurement that settled what the IOKit disk-time counter means, and the narrowed disk
type is built on its conclusion.

The solution has two projects that only build for Windows, so the build carries the switch the
error message itself names. scripts/test-local.ps1 is PowerShell and cannot run on a Mac.

     busiest five, as a share of the whole machine:
         10.44%  node (process 49497)
          9.75%  esbuild (process 49505)
          3.35%  bash (process 49513)
          1.73%  mdworker_shared (process 49499)
          1.40%  RustDesk (process 835)

   Every figure is non-zero and real. Three things in that reading are worth naming:

   - "in the system volume" is the IOKit walk working. The system volume's own device is an Apple
     file system volume inside a container synthesized on a partition, so without walking up to the
     hardware no disk would ever be marked as the one the machine runs from.
   - 181 of 502 processes are listed WITH THEIR FIGURES NULL rather than left out. An ordinary user
     is refused the processor time and memory of another user's process. The old probe took the list
     from the same call it took the figures from and so dropped them entirely - which on 15 October
     lost the two busiest processes on this machine, both Spotlight indexing as root, out of a set
     reporting that it had read fine.
   - BusyPercent is absent from the disk line because it is null on this platform, and the time per
     operation carries the signal instead. That is the finding of macos-disk-busy-risk.txt.

5. THE PROCESSOR, AGAINST THE MACHINE'S OWN MONITOR

   Four consecutive ten-second windows, with "top -l 5 -s 10 -n 0" started alongside so its interval
   ticks line up one-for-one with the probe's windows. top reports idle, so the busy figure is
   100 minus idle.

     window   the probe      top        difference
        1      61.75 %     61.83 %        0.08
        2      69.71 %     69.73 %        0.02
        3      94.93 %     94.30 %        0.63
        4      89.77 %     89.54 %        0.23

   Worst disagreement 0.63 percentage points, against a requirement of 5, over a load that moved
   from 62 up to 95 per cent - which is the range the amber and red limits sit in, so it is the
   range that matters most.

   MEASURED AGAIN AFTER THE CLOCK CHANGE. An earlier run of the same protocol read 0.01, 0.05, 0.00
   and 0.42 points over a load falling from 66 to 48. That run was against the wall-clock interval,
   and the figures above are against the monotonic one that ships, so these are the ones to quote.
   Both pass the same way, which is the point: the clock change fixed a failure case that needs the
   clock to step, and it did not move the ordinary reading.

   THE WINDOWS HAVE TO BE LINED UP OR THE COMPARISON MEANS NOTHING. A first attempt compared one
   probe window against whatever tick top happened to print and read 32 percentage points apart on a
   machine that was swinging between 30 and 78 per cent busy. That was the measurement being wrong,
   not the probe: once the windows were matched the two agree to within half a point. A single
   unaligned window on a moving machine can disagree by any amount and proves nothing in either
   direction.

6. MEMORY, AGAINST THE MACHINE'S OWN COUNTERS

   The right counterpart is vm_stat, not top. top's "used" counts the compressor and cached files,
   which is a different quantity; the probe reports what MachineMemoryProbe has reported since the
   issue 2818 fix - free plus inactive plus purgeable pages, in the same spirit as Linux's
   MemAvailable. So the check is against the page counts that figure is built from.

     run    probe used %    vm_stat used %    difference
      1        76.33            76.11           0.22
      2        79.65            79.80           0.15
      3        80.88            80.54           0.34

   Worst disagreement 0.34 percentage points, against a requirement of 5. The remaining gap is the
   fraction of a second between the probe's read and vm_stat's, during which the machine really does
   move - which is also why the figure lands sometimes above it and sometimes below.

7. THE CLOCK, AND A REGRESSION TEST THAT WAS CHECKED AGAINST THE DEFECT

   Wall-clock time STAMPS a sample; only a monotonic clock MEASURES an interval. This probe originally
   did both off DateTime.UtcNow, which was finding 8 of the review of pull request 4035 - declined
   there, then fixed in the shared interface for the memory probe, with the rule written to cover the
   resource probes too. This probe now follows it: it takes a TimeProvider, ages its cache and
   measures every interval with GetTimestamp and GetElapsedTime, and uses the wall clock only for
   ResourceSample.TakenAtUtc. Its per-second rates go through the shared ResourceRate rather than a
   division written here.

   Why it matters: time synchronisation steps the wall clock backwards routinely. Under the old code a
   step back of more than a second made the cached sample look as though it came from the FUTURE, and
   the probe went on serving that one stale reading until the wall clock caught up - a five-second
   meter showing a machine that is filling up as though nothing were happening.

   THE TEST WAS CHECKED AGAINST THE DEFECT, NOT JUST WRITTEN. I reintroduced wall-clock cache aging
   and ran it:

     with the defect present   Failed: 1   "Assert.NotSame() Failure: Values are the same instance"
     with the defect fixed     Passed: 1

   A regression test that passes either way certifies nothing, so it was worth the two minutes to
   confirm this one actually fails on the behaviour it is named for.

8. WHAT THESE CHECKS DO NOT COVER

   - ONE MACHINE, ONE DISK, ONE KIND OF DISK. An Apple M4 with a single internal solid-state disk.
     No spinning hard drive has ever been measured on macOS, so the Rotational branch of the medium
     type is covered by a committed fixture and by the code path, not by hardware.
   - NO INTEL MAC. The entry-point binding that review finding 4 is about rests on the exported
     symbol tables read on this machine, not on a reproduction. Measured here: libsystem_kernel
     exports _statfs, _statfs$INODE64 and _statfs64, with the last two at the same address and the
     plain name at a different one in the Intel slice - which is exactly the trap, and why the
     binding names statfs64.
   - NO EXTERNAL OR NETWORK VOLUME, so a disk appearing or disappearing mid-sample is untested.
   - THE PowerShell GATE DID NOT RUN. It cannot run on a Mac.
   - THE WALL CLOCK WAS ONLY STEPPED IN A TEST, never on the real machine. The clock rule is proved
     against a driven TimeProvider, not by letting time synchronisation correct this Mac mid-sample.
   - THE LIMITS ARE NOT TESTED HERE. What counts as amber or red for the processor, and what counts
     as a slow millisecond-per-write on macOS, are proposals until the phase 2 load harness runs
     them on all three platforms. This file says the figures are right, not that the thresholds are.
