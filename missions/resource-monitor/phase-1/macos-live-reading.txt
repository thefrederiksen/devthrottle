TWO HONEST CAVEATS ABOUT THE COMPARISONS ABOVE

  1. top's processor window and the probe's are not the same window. Both are about a second long and
     they overlap, but they do not start together, so a point or two of difference is the measurement
     and not a defect. The same is true of iostat, which averages over its own one second ticks while
     the probe averages over its whole interval.

  2. ps's %CPU column is a DECAYING AVERAGE over up to a minute of real time, not an instantaneous
     rate like the probe's. So cc-director agreeing to within 0.2 points is partly luck, and the
     claude process reading 3.0% against ps's 5.7% is not a disagreement - it is a process whose use
     changed during the minute ps was averaging over. The per-process figure that IS pinned exactly is
     in the live tests: two threads spinning flat out in the test process read as very close to 200%
     of a core, which is what two cores' worth means.

A KNOWN LIMITATION OF THE PROCESS NAME, WHICH NEEDS A DECISION

The name comes from PROC_PIDTBSDINFO, as the mission's brief for this task specified. For most
processes it is exactly what the owner would want - cc-director, dotnet, RustDesk, probeharness - but
it is the process's own short name, and some programs set it to something unhelpful. In the list
above, the Claude Code session at process 62661 reports its name as "2.1.300", which is its version
number; ps shows /Users/soren/.local/bin/claude for the same process, because ps reads the process
arguments through a different call (KERN_PROCARGS2) rather than this structure.

That matters for the mission, because naming the culprit is the point: "mostly 2.1.300" tells the
owner nothing. It is raised rather than fixed here because the brief named this structure as the
source, and reading the arguments instead is a separate decision with its own cost - KERN_PROCARGS2
is a per-process sysctl, so it would add one more call for each of 420 processes on every sample.
Recommendation: keep this name, and have the detail screen fall back to the executable path for the
processes it is about to show, which is a handful rather than all of them.

WHAT THIS LIVE READING DOES NOT COVER

  - A QUIET MACHINE. Everything above was read on a machine doing ordinary work. The warning
    thresholds, the amber and red states and the banner are phase 2's load harness, not this.
  - A SPINNING HARD DRIVE. There is none on this Mac, so DiskKind.Spinning is exercised by a unit
    test and by the code path, never by hardware on this platform.
  - A SECOND PHYSICAL DISK, an external disk, or a network volume. One internal disk, ten volumes.
  - SWAP IN USE. This machine has no swap file at all, so the swap figures are proved readable and
    proved zero, and never proved against a machine that is swapping.
